## 1. 결론

**“매핑 76개가 존재하므로 56+20개가 모두 의미 있게 반영된다”는 결론은 성립하지 않는다.** 저장, 점수 집계, 해시 기반 변주, 의미 단서 보존, 실제 표현을 구분해야 한다.

- 56개 본문항: 3개 합성 시드 × KO/EN × 56개 = **336개 A/B 비교**. V4 32/64-bit fingerprint를 통제한 대조에서 Q14·Q57·Q65·Q77의 선택 변경은 보고서 섹션/프로그램 내용 변화로 관측되지 않았다. 나머지 52개에서 내용 변화가 있다는 사실도 곧 의미 해석의 타당성을 증명하지 않는다.
- 조건부 20개: 3개 합성 시드 × KO/EN × 20개 = **120개 자유문 A/B 비교**. 대조에서 Q40만 execution_profile 내부 변화가 있었고, 20개 모두 VII 표시 모델 및 프로그램 내용 변화는 관측되지 않았다.
- 원문 보존: 실제 autosave/submit 함수와 복원 대입문을 합성 SDK/REST/단체 큐에 연결해 **20개 전체의 저장·복원·제출 payload 동일성**을 확인했다. 실제 Firebase 서버 규칙·로그인·결제·운영 제출 검사가 아니다.
- **채점 결함:** 20개 모두 질문 유형 인덱스에 없어 `likert`로 취급된다. 일반 자유문은 `raw=null`로 제외되지만 문자열 `1`은 0, `5`는 1로 집계되고 공백 문자열도 0으로 집계된다. 자유문 내용을 숫자화하는 방식은 문항의 의도와 맞지 않는다.

## 2. 방법과 한계

재현 명령(고객 접속 없음):

```sh
node scripts/audit-four-axis-information.cjs dist/device-guide-review/information-audit.json

TMPDIR=/var/tmp LP_BROWSER_PATH=<Chromium 실행 파일> node scripts/audit-conditional-browser.cjs dist/device-guide-review/conditional-browser-audit.json
```

- 기존 276회 탐색은 복수 선택의 두 번째 값·순서 변경을 다룬다. 새 336회는 본문항별 값 변경, 새 120회는 조건부 자유문 변경을 다룬다. 서로 같은 검사를 중복 합산해 표본 수처럼 표현하지 않는다.
- 실제 ReportEngine, ReportEngineV4, ProgramEngine, careerRules를 사용한다. E는 기존 CareerEngine 모듈을 사용한다.
- 자연 출력과 **V4 fingerprint 두 개만 일정하게 고정한 격리 VM 출력**을 나누어 비교한다. 프로덕션 파일은 변경하지 않는다. 격리 VM에 원래 fingerprint를 넣었을 때 실제 엔진과 같은 결과가 나오는지 매번 검증한다. E 내부의 다른 해시까지 모두 제거한 실험은 아니다.
- 시간·fingerprint 메타데이터를 차이 계산에서 제외한다. 엔진 JSON의 차이를 독자에게 보이는 차이나 의미 적합성으로 간주하지 않는다.
- 두 번 실행한 엔진 감사 JSON은 byte-identical이다. 원응답 mutation을 검사한다. 파일 SHA는 각 감사 JSON에 기록한다.
- 조건부 A/B 문장은 각 부모의 실제 질문에 맞춘 가상 답변이다. 개인별 실제 응답도, 전체 어휘·선택 조합의 완전 탐색도 아니다.
- 조건부 문항의 직접 입력은 이미 획득한 근거지만, 입력한 사람의 의도·인과·우선순위를 모두 안다는 뜻은 아니다. 직접 인용과 의미 해석은 구분한다.

## 4. 코드상 원인

1. `report-engine.js/computeScores`: qTypes는 56개 부모만 구성한다. questionMapping은 76개를 순회하며 누락 유형을 `likert`로 간주한다. Number 변환·clamp 때문에 숫자/공백인 자유문이 점수에 들어간다. mapping.sections는 점수 집계의 연결이지 자유문 해석 템플릿으로의 자동 배선이 아니다.
2. `report-engine-v4.js/fullAnswerFingerprint(64)`: mapping의 모든 키를 순회한다. 20개 직접입력도 시드를 바꾼다. 문구·직업/훈련 예시가 달라져도 직접입력의 의미를 해석했다는 증거는 아니다.
3. `report-engine.js/buildExecutionProfile`: Q40은 명시적 활동 입력으로 붙지만 앞선 선택들과 합친 뒤 `slice(0,3)`으로 제한된다. 영문 사전 미일치, V4 후처리도 별도 손실 지점이다.
4. `report-engine-v4.js` 전략 source의 activities에는 Q39+Q40이 보존되지만, 대표 좌표·후속 프로그램에 원문이 모두 이어지는 것은 아니다.
5. `suvey.html/renderQuestion`: hasOther이면 textarea를 추가한다. `renderOtherInput`은 원문을 answers[otherId]에 넣는다. 부모 기타 해제는 자식 문자열을 지우지 않는다.
6. `_isOtherActive`: 부모가 비어 있지 않고 자식에 값이 남아 있으면 활성으로 처리한다. `_isAnswerEmpty`는 공백만 있는 문자열을 비어 있다고 보지 않는다. placeholder의 ‘선택’과 빈 기타 선택의 진행률 분모 편입을 함께 검토해야 한다.

## 5. 실제 UI·리포트·프로그램 표시 감사

- Chromium 실제 DOM 조작: 20개 × 393/1366px = **40건**. 기타 선택 전 textarea가 보였고, 기타 해제 후에도 문자열을 보존하며 활성으로 판정했다(각40건). 재선택/JSON 복원 뒤 원문이 동일했다. 빈 기타는56/57, 공백 입력은57/57로 판정되는 사례를 확인했다. 줄바꿈·쉼표·슬래시·일본어·HTML 형태 문자열을 textarea의 텍스트로 복원했다.
- 표시 비교: 20개 × KO/EN × report/program × 자연/V4 fingerprint 통제 = **160개 A/B 쌍**. 실제 legacy DOM과 각 화면판/소장판 iframe을 실행하고 조립된 자식 script의 문법, 14지면, payload 불변·쓰기0을 검사했다. 이 루프는 seed0이며 엔진 감사의 세 시드를 모두 렌더한 것은 아니다.
- 통제 후 **80개 표시 비교 쌍 모두 legacy·화면판·소장판의 텍스트 차이 미관측**. Q40도 source 보존과 달리 이번 입력에서 화면 변화/직접 인용으로 이어지지 않았다. 자연 출력의 차이는 이 결과와 구분하며 의미 활용 완료로 세지 않는다.
- 브라우저 감사 첫 시도는 Firebase mock의 getFunctions 누락으로 실패했다. 보완 후 긴 페이지 재사용 실행도102쌍에서 iframe 로드 타임아웃으로 중단했다. 페이지별 리스너/타이머 누적을 제한하도록 문항마다 새 페이지를 열어 **최종160쌍을 완료**했다. 제품 코드는 수정하지 않았고 이전 부분/실패 JSON은 별도 보존했다.
- 외부 요청은 전부 차단/합성 응답했다. UI, 저장 핸들러, 생성·표시 계층을 분리한 감사이며 실제 사용자 로그인부터 제출까지 운영 E2E나 실기기 검사는 아니다.

## 6. 수정 계약 제안 — 별도 승인 필요

### A. 원문과 해석을 먼저 분리한다

- 원응답은 그대로 보존한다. 읽기 전용 중간 근거에 `parentQid / otherQid / rawText / activeState / provenance=direct / parserVersion`을 둔다.
- 분석을 위해 공백 등을 정규화하더라도 원문과 혼동하지 않는다. 쉼표·슬래시를 무조건 분할하지 않는다.
- 활성 상태는 `selected / retained-after-deselection / historical-unknown / empty`를 구분한다. 기존 문자열이 남아 있다는 이유만으로 현재 의도가 확정됐다고 보지 않는다.
- ‘기타 해제’ 시 과거 입력을 자동 삭제하지 않는다. 신규 입력의 활성화 의미와 재선택 복원 UX를 먼저 합의한다.

### B. 자유문을 리커트로 채점하지 않는 신규 버전

- 신규 계산에서 조건부 입력을 명시적 text로 분리하는 안을 우선 검토한다. 자유문 `1`, `5`, 공백을 리커트 응답으로 해석하지 않는다.
- 이 변경은 산식 입력/분모와 결과에 영향을 줄 수 있으므로 새 scoreVersion 및 영향 비교가 필요하다. 이번 배포 승인으로 임의 적용하지 않는다.
- 기존 고유코드·저장 점수·수동 검수본·제출응답을 다시 계산하거나 마이그레이션하지 않는다.

### C. 문맥별 의미 활용과 unknown 처리

- 부모 질문의 역할(상황·가치·회복·표현·활동·주제·환경·리듬·동기·지속·기준·영향·실행·성취·분야)을 유지한다. 모든 직접입력을 범용 키워드 바구니로 합치지 않는다.
- 해석 규칙마다 근거 입력, 영향을 줄 문장/제안, 지원 언어, 미인식 시 처리, 과잉추론 금지 조건을 명시한다.
- 인식하지 못한 자유문은 버리거나 임의 유형으로 확정하지 않는다. 사용자 직접 표현으로 보존하고 필요한 확인 질문을 제안한다. 단순 인용을 의미 이해 완료로 세지 않는다.
- same-career/different-evidence, 두 번째 선택, 순서만 변경, 부정문, 상충 조건, unknown, KO/EN/혼합문자, 쉼표·슬래시, HTML문자, 빈/공백 입력을 회귀 계약에 넣는다.
- Q14·Q57·Q65·Q77은 현재 사용 경로와 정보 가치를 우선 재검토한다. 문항을 바로 삭제하거나 선택지를 고치지 않는다.

### D. 배포 경계

PR331의 해설서·동의 CSS 배포는 위 문제의 수정 배포가 아니다. 후속 감사 PR은 문서·도구만 포함한다. 질문/점수/개인화 생성 변경은 영향 비교와 별도 승인 후 신규 결과부터 적용하는 방안을 검토한다. 기존 고객 저장 자료 재생성은 별개다. Firebase Hosting/Auth/Functions/RTDB/Firestore, 가격·단체 계약·승인 V8·미디어를 유지한다.

## 7. 후속 사용자 승인 및 구현 후보 (2026-09-22)

사용자는 신규 채점 버전, 기타 해제/원문/활성 규칙, 직접입력 문맥과 복수 응답의 해석·실행 연결 구현을 승인했다. §1~6은 승인 전 감사 이력이다.

- `input-v2` / `scores-v2-text-excluded` / `evidence-reader-v1`로 명시한다. 새 UI로 저장/제출하는 세션 메타에 버전을 적고 E→V4→P에 전달한다. 버전 없는 과거 제출과 저장 결과는 기존 경로다. 자동 마이그레이션/DB 조회/고객 재계산은 없다.
- 점수: qTypes의 otherId를 text로 지정해 비숫자뿐 아니라 숫자·공백도 분자/분모에서 제외한다. 문항/매핑 JSON 및 기존 가중치는 변경하지 않는다.
- 활성: 명시적인 ‘기타’ 선택만 인정한다. 해제하면 문자열을 지우지 않고 입력창을 비활성화하며 새 의미 근거에서 제외한다. 빈/공백 선택 입력은 임의 필수 문항으로 세지 않는다. 원문 재선택/복원을 테스트한다.
- 복수 선택: 전체 선택을 정본 보기 순서로 정규화한다. 이 순서를 사용자의 우선순위로 설명하지 않는다. 원래 원응답은 수정하지 않는다. 원응답 fingerprint는 그대로, 의미 생성에 쓸 정규화 fingerprint는 별도다.
- 네 축: 성향×복수 기준, 표현 방식×관계 기준, 활동×성취 기준, 시작 이유×지속 조건을 연결한다. 보조 문항 Q14/Q65/Q31/Q47/Q49/Q75/Q77도 짧은 설명과 근거에 연결한다. 새 `evidenceReader`는 기존 `axisReaderView`의 대표 좌표 문구보다 우선한다.
- 자유문: 20개 부모 문맥별 역할·실행 확인 질문을 정의한다. 자유문을 그대로 보존하고 발췌를 표시하며, 숨은 동기나 심리·직업 능력을 추론하지 않는다. **이 1차 구현은 규칙 기반 문맥 연결이다. 임의 자유문의 전체 의미를 이해하는 자연어 분석기나 검증된 개인화 척도가 아니다.** 같은 부모의 미묘한 내용 차이에 서로 다른 실행 방법까지 자동 추론하지 않는다.
- 길이 계약: 기본 지면에는 축별 첫 직접입력의 일부와 제한된 보조 단서를 표시하고 생략을 알린다. 전체 선택·직접입력·활성 상태·문맥별 실행은 온라인 `응답 근거` 대화상자에서 확인한다. 모든 직접입력을 기본 지면이나 PDF에 반복하지 않는다. 이 노출 순서는 중요도 순위가 아니다.
- 프로그램: 분기 안내, 3주 실천, 모듈3개, 다음 단계가 새 계획을 사용한다. 전체 직접입력 실험은 근거 창에 보존한다. 나머지 기존 장기 목표·효과·추적 구조까지 새 모델로 전환한 것으로 주장하지 않는다.
- 실패 계약: 새 모듈/해석 생성 실패 시 구버전 결과로 대신 저장하지 않는다. E/V/P 입력 및 보고서 mutation 없음, 기존 버전 출력 비교, 원응답 식별자 유지, 선택순서 변화, 비활성 원문 변화, 직접입력 A/B, 20개 KO/EN·3시드, 실제 UI40건과 리포트/프로그램8조건을 검사한다.
