# 파이스 에이전트 협업 업무 매뉴얼 v0.1

- 제정: 2026-09-14
- 상태: Q90에서 시범 적용하는 초안. 운영 방식 전환은 대표 승인, 효율 향상 효과는 아직 미검증.
- 목적: 크레딧을 적게 쓰는 것 자체가 아니라, 고객 자산과 품질을 지키면서 검수된 목표를 더 적은 총비용으로 달성한다.
- 사명: **발견 → 살아냄 → 남김**.
- 관계 문서: [인생포트폴리오 제작규칙서](../제작규칙서_v2.0_최종본.md). 제작규칙서는 제품을 만드는 기준, 본 문서는 그 기준을 지키며 사람과 에이전트가 협업하는 운영 절차다. 제품 규칙·평가 계약을 본 문서로 변경하지 않는다.

## 1. 왜: 전략과 최적화의 기준

리처드 루멜트의 전략 핵심인 진단·추진 방침·일관된 행동을 실무에 적용한다. 아래는 회사의 적용안이며 책의 직접 인용이 아니다.

1. **진단:** 목표 달성을 막는 현재 장애 하나를 증거로 특정한다. 도구·인력·예산 부족으로 추정부터 하지 않는다.
2. **추진 방침:** 장애를 없애는 가장 작은 완결 작업을 선택한다. 기준을 낮추거나 검수를 생략해 비용을 줄이지 않는다.
3. **일관된 행동:** 실행자·독립 검수자·인계 대상·완료조건을 연결하고, 승인된 범위 안의 실행은 이어 간다.

최적화 대상은 `검수된 성과 / 전체 투입비용`이다. 메시지 수, 보고서 수, 에이전트 가동 인원, 낮은 단일 호출 비용은 성과가 아니다. 불필요한 대기·재시작·맥락 복구·중복 검수가 총비용을 키우는지 함께 본다.

## 2. 무엇을: 작업 계약과 권한

### 2.1 완료 단위 작업 계약

발주 전에 다음 항목을 하나의 작업 카드에 기록한다. 기존 카드가 있으면 재사용한다.

| 필수 항목 | 기록 내용 |
|---|---|
| 목표와 완료조건 | 어떤 증거가 있으면 누가 완료 판정하는가 |
| 현재 장애 | 확인된 사실, 미확정 가설, 마지막 실패 증거 |
| 기준 자료 | 기존 파일·메시지·해시·평가 계약 참조 |
| 보존·금지 범위 | 고객 자료, 권리, 운영 환경, 비공개 입력 등 |
| 책임 분리 | 실행 책임자, 독립 검수자, 최종 승인자, 다음 담당자 |
| 실행 범위 | 사전 승인된 조치와 별도 승인이 필요한 경계 |
| 비용·재시도 | 총한도, 경고선, 조회 담당, 실행 시도와 중단조건 |
| 인계 조건 | 필요한 산출물, 수신자, 실제 호출 방법, 수락 증거 |

새 작업 전에 전체 과거를 다시 읽지 않는다. 최신 승인·완료 대장·마지막 장애·필요한 변경부부터 읽고, 불일치가 있을 때만 범위를 넓힌다.

### 2.2 역할과 책임

| 역할 | 책임 | 하지 않는 일 |
|---|---|---|
| 총괄 | 목표·우선순위·예산·권한 결정, 최종 승인, 예외 해결 | 이미 검수된 전체 코드를 반복 검수하거나 모든 작은 인계를 중계 |
| 실행 책임자 | 최소 수정, 구문·기술 검사, 승인 범위 연속 실행, 증거·직접 인계 | 자기 변경의 독립 수락, 실패 검사 우회 |
| 독립 검수자 | 변경 위험과 완료조건 검증, 수락 또는 구체적 반례 제시 | 같은 환경을 이유 없이 재생성, 근거 없는 조건 추가 |
| 방법론 담당 | 고정 평가 계약과 증거의 정합성 확인 | 결과를 보고 기준을 변경, 미측정을 점수로 대체 |
| 전문 지원 | 현재 필요한 비교·보안·법률·영업 산출물 제공 | 의존 입력이 없는 상태에서 같은 초안을 반복 작성 |

제품 평가의 author/executor/reviewer/judge1/judge2/adjudicator 분리는 별도 계약을 따른다. 위 관리 역할을 이유로 평가 역할을 임의 합치지 않는다.

### 2.3 승인 경계

- 조건부 승인은 **정확한 범위·버전·사전조건**을 명시한다. 코드나 계획이 바뀌면 새 해시와 승인 관계를 남긴다.
- 승인 범위 내 수정·구문 검사·인계는 작은 단계마다 재승인받지 않는다.
- 별도 승인 대상으로 정한 실제 검증·생성·운영 배포·고객 데이터/결제권 변경은 독립된 경계다. 앞 단계의 승인이 뒤 단계로 전파되지 않는다.
- 승인 요청은 정확한 실행 대상과 검수 증거를 묶어 한 번에 제출한다. 총괄은 도착한 실제 승인 요청을 우선 처리한다.

## 3. 어떻게: 실행과 인계

### 3.1 실행 흐름

`목표 고정 → 최소 변경·구문 검사 → 독립 검수 → 조건부 승인 범위 실행 → 증거 인계 → 최종 게이트 판정 → 다음 단계`

실행 전 저비용 검사로 구문 오류·필수 파일·계획 불일치를 먼저 제거한다. 전체 실행 제한시간과 상태 관측 간격을 분리하며, 출력이 없다는 사실만으로 정체나 실패라고 판정하지 않는다.

### 3.2 진짜 병렬화

- 병렬 작업은 입력 의존성이 없고 서로 다른 산출물을 만들 때만 할당한다.
- 검수자는 실행자의 변경부가 도착하면 이어받는다. 기다리는 동안 별도 전체 검수 환경을 만들지 않는다.
- 비교 근거·표현 제한 등 사전 준비는 기존 자료로 진행할 수 있다. 점수·우위·공개 승인은 실제 결과 이후다.
- 준비물이 이미 있는 담당자를 단지 화면에 가동 인원을 늘리려고 다시 호출하지 않는다.

### 3.3 인계 프로토콜

인계자는 다음을 짧게 남기고 수신자를 실제로 호출한다.

```text
작업 ID / 달성한 완료조건 또는 남은 장애:
산출물 위치·버전·해시 / 검사 결과:
검수·승인 ref와 적용 범위:
다음 담당자 / 지금 수행할 조치:
남은 예산 상태 / 실행 시도 수 / 보존 대상:
```

- GenTeam에서는 실제 @mention과 발신 receipt를 확인한다. 게시만 하고 수신자가 실행할 것이라고 가정하지 않는다.
- creator-only 등 호출 제한이 있으면 해당 advisory와 필요한 호출만 총괄에게 전달한다. 권한을 우회하지 않는다.
- 보드의 `in_progress`는 관리 상태이지 실행 프로세스 증거가 아니다. 별도로 `발신됨 / 실행증거 있음 / 의존대기 / 승인대기 / 안전·예산차단`을 구분한다.
- `in_review`는 산출물이 검수 대상으로 도착한 상태, `done`은 지정 검수자의 완료조건 수락 후에만 사용한다. 작업 카드 완료와 제품 게이트 완료도 구분한다.
- 총괄은 의미 있는 인계 시점에 실제 결과를 회수한다. 발신 성공만으로 작업 완료를 보고하거나 짧은 주기로 반복 조회하지 않는다.

## 4. 비용 관리: 경고선과 총한도 분리

1. 대표가 승인한 **완료 단위 총한도**와 기준 잔액을 고정한다. 기준을 자동 재설정하지 않는다.
2. 경고선은 낭비 점검 지점이다. 경고선 도달만으로 실행·검수·인계를 중지하거나 재승인을 요구하지 않는다.
3. 총한도 도달 시에는 신규 유료 작업을 중지한다. 이미 실행 중인 작업은 데이터 보존과 안전한 종료를 우선하고, 추가 지출 승인을 자동으로 가정하지 않는다.
4. 비용 조회 책임자는 한 명으로 정한다. 비용 큰 실행 전·실제 장애·최종 인계에서 조회하며 모든 담당자가 반복 조회하지 않는다.
5. 계정 잔액 차이는 다른 작업과 지연 반영을 포함할 수 있다. 작업별 정확한 과금이나 하드 차단, 한도 준수를 보장하지 않는다. 가능하면 기존 사용 내역의 실제 귀속 자료로 사후 대조한다.
6. 할인 표시만으로 모든 모델·도구에 같은 할인율이 적용된다고 가정하지 않는다.
7. 재시도는 원인이 확인되고 수정 근거가 있을 때만 허용한다. 실행 시도 제한은 별도로 유지한다. 구문 검사와 문서 인계를 전체 준비 실행 횟수로 혼동하지 않는다.

종료·중지 사유는 **완료, 명시적 승인 경계, 안전 위험, 해결 경로 없는 반복 실패, 총한도 도달, 대표의 중지 지시**다. 단순한 1회 보고 제출은 핵심 완료 단위 작업의 종료 사유가 아니다.

## 5. 품질·고객 자산·정보 보존

- 실제 서비스 구조는 Static HTML/JavaScript + Firebase RTDB/Cloud Functions다. 기본 개발 템플릿으로 덮어쓰거나 임의 이전하지 않는다.
- 기존 고객 결과, 고유코드, 결제권, 저장된 리포트·프로그램·PDF 참조를 보존한다.
- 임시 복사본과 원자료는 보존 의무가 다르다. 정확한 회수 목록과 원본 동일성, 파일·링크·권한, 사용 중인 프로세스·FD·mount 등을 확인한 뒤 승인 범위만 회수한다.
- 원답안·개인정보·비공개 입력을 총괄·검수자·모델에게 불필요하게 공유하지 않는다. 지정 실행자의 기계적 검사 결과를 해시·타입·개수·동일성 boolean 등으로 인계한다.
- 생성자와 평가자의 결과 접근을 분리하고 봉인·블라인드 계약을 지킨다.
- 미측정·비적용·비교 불가를 숨기지 않는다. 비교군은 동일 접근 범위와 근거 수준으로 비교한다.

## 6. 검증: 효율을 측정하는 방법

| 지표 | 정의·사용 방법 |
|---|---|
| 검수된 완료조건 수 | 최초 고정 분모와 수락 증거 기준. 하위 작업 분할로 부풀리지 않음 |
| 최초 검수 수락률 | 최초 제출에서 수락된 완료 단위 / 최초 검수된 완료 단위 |
| 재작업률 | 반려·재개방된 완료 단위 / 검수된 완료 단위 |
| 인계 대기시간 | 인계 제출부터 다음 실제 실행 증거까지. 자동 계측 없으면 미측정 |
| 완료조건당 비용 | 귀속 가능한 실제 비용 / 수락된 완료조건. 분모 0 또는 귀속 불가면 산출 불가 |
| 결함·보존 위반 | 신규 결함, 기존 결과 손상, 접근·권한 위반 건수 |
| 중복 작업 | 같은 근거·산출물을 이유 없이 재생성하거나 재검수한 사례 |

비용과 품질을 함께 본다. 예산 감소만으로 성공이라고 하지 않으며, 준비 비용을 쓰고 완료조건을 통과하지 못한 경우도 그대로 기록한다. 현재 v0.1의 효율 향상 수치는 미측정이다.

## 7. Q90 시범 적용과 개정 절차

- 업무: `FAISE-20260908-Q90-01`.
- 우선 목표: G13 실제 완료. 이어서 기존판·개선판 7축 평가 → 독립 검수 → 90점 및 필수조건 판정 → 공개 비교표·영업자료 검수.
- 평가 트랙: Q90-ALT-v1, AI/합성 사례/기술 검증 기반. 인간 타당도·기관 인증·영적 평가가 아니다. 인간 모집을 현재 G13의 새 선행조건으로 추가하지 않는다.
- A1 첫인상 직관성, A2 자기인식 정확도·공감, A3 바로 실행가능성, A4 자산화·축적 연결성, A5 전문성·신뢰감, A6 홈페이지 이용 편의성·시각품질은 각 15점, A7 보안 취약성은 10점이다.
- 과거 78점은 5축 점수다. 새 7축 점수와 단순 증감으로 연결하지 않는다. 목표 90을 맞추기 위해 근거·기준을 바꾸지 않는다.
- 예산·실제 승인 ref·진행률·검수 결과는 비공개 운영 대장에 기록한다. 본 매뉴얼은 실시간 대장이나 성능 인증서가 아니다.
- 이번 시범에서는 총괄이 매뉴얼 초안을 작성한다. 문서화를 위해 실행팀에 별도 대형 보고서를 발주하지 않는다.

완료 단위가 끝나면 기존 기록에서 `효과 있었던 조치 / 낭비 / 재발 방지 규칙 / 근거`만 짧게 추출한다. 검증된 규칙을 다음 버전에 반영하며 미검증 제안과 구분한다. v1.0 확정은 시범 결과와 대표 검토 이후다. 문서 작성 자체로 Q90 게이트를 완료 처리하지 않는다.
