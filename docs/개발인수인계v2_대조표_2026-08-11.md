## 2. S-2 결제 권위 — 규칙 실측

`database.rules.json` `/payments/$uid`:

```
.read     = auth != null && auth.uid === $uid
.write    = auth != null && auth.uid === $uid && (!data.exists() || data.child('paid').val() !== true)
.validate = newData.hasChildren(['paid','createdAt']) || newData.hasChild('_pending')
/paid .validate = newData.isBoolean() && newData.val() === true
```

읽는 그대로의 귀결:

1. 로그인한 사용자는 자신의 `payments/{uid}` 를 **직접 create 할 수 있다.**
2. `validate` 는 `paid` 가 **반드시 `true`** 여야 통과한다(`false` 는 오히려 거부된다).
3. 따라서 **결제 없이 `paid:true` 를 만드는 경로가 규칙상 열려 있다.**
4. 기존 `paid:true` 의 덮어쓰기만 차단된다(1회성).

`/additionalPayments/$uid` 는 `.write=false` 로 서버 전용이다 — 이쪽은 이미 올바른 형태이며, `/payments` 가 legacy 로 남은 것으로 보인다.

**판정: v2 지적 정확. S-2 는 CRITICAL.**

### 2-1. 다만 — 규칙만 잠그면 매출이 끊긴다

서버 검증 경로는 **이미 존재한다**:

| 함수 | 역할 |
|---|---|
| `confirmPayplePayment` (L4312) | Payple 인증결과를 서버에서 재검증 → `admin.database().ref('payments/'+uid).update(...)` |
| `capturePaypalOrder` (L355 부근) | PayPal 캡처 검증 후 동일 노드 기록 |
| `confirmAdditionalPayplePayment` / `captureAdditionalPaypalOrder` | `additionalPayments` 기록 (이미 서버 전용) |

그런데 `payment-success.html` `persistPaidToRtdb()` (L1065) 의 주석은 이렇게 말한다:

> - PayPal: Firebase Functions(capturePaypalOrder)가 이미 RTDB에 기록. 이 페이지에서는 검증만 수행.
> - **Payple: 기존 흐름 그대로 클라이언트에서 paid:true 기록.**

즉 **PayPal 은 이미 서버 권위이고, Payple(KO ₩19,900) 만 클라이언트 쓰기에 의존**한다.
`.write=false` 로 바꾸면 **KO 결제 고객이 결제 후 검사에 진입하지 못한다.**

**⇒ S-2 는 규칙 1줄 수정으로 끝나지 않는다.** 필요한 순서:

1. `confirmPayplePayment` 가 실제로 모든 KO 결제 흐름에서 호출되는지 실측 (호출 실패 시 클라이언트 폴백에 의존하고 있을 가능성)
2. Rules Emulator 로 서버 기록 경로만 통과함을 확인
3. `payment-success.html` 을 "기록"에서 "서버 상태 조회"로 전환
4. 규칙 `.write=false` 적용
5. 기존 유료 사용자 접근 회귀 0건 확인

**이 순서를 지키지 않고 규칙만 잠그는 것은 대표님의 안정성 필수 원칙 위반이다. 따라서 이번 사이클에서는 실측 보고까지만 하고 변경하지 않는다.**

### 5-1. 실측 A/B/C/D

기준 응답(likert 전부 3 · 선택형 전부 첫 보기 1개)에서 조건만 바꿔 4축 점수를 비교했다.

| A 기준 | 71.4286 | 79.4872 | 68.3438 | 78.5455 |

읽히는 사실 3가지:

1. **D — 다중선택 문항의 보기를 1개 고르든 전부 고르든 4축 점수가 완전히 같다.** 선택 *내용*과 *개수*는 정량 4축에 기여하지 않는다.
2. **B — 기타입력에 어떤 문장을 써도 점수가 변하지 않는다.** 텍스트는 `Number()` 로 `NaN` → `isFinite` 실패 → `null` 결측 처리.
3. **C — 그러나 기타입력에 `"5"` 라고 쓰면 점수가 올라간다.** `mapping.questionMapping` 에는 otherId 20개가 등록돼 있지만 `questions.json` 에는 해당 문항 타입이 없어 `qTypes[qid]` 가 `undefined` → **기본값 `"likert"` 로 폴백**되고, 리커트 척도로 채점된다.

3번은 v2 PR-SCORING "기타 자유입력 default-likert 폴백 제거" 가 지목한 바로 그 경로다. **의도된 설계가 아니다.**

### 5-2. 함의

- 4축 점수는 **혼합 형성형 지수**이며, 리커트 34문항이 실질적 변동을 만들고 선택형 22문항은 상수에 가깝다.
- 따라서 **4축 점수를 심리측정적 정확성의 근거로 제시할 수 없다.**
- 다만 **선택 내용이 버려지는 것은 아니다** — 선택형 응답은 키워드 추출·서술 생성·fingerprint 에 사용된다(`report-engine.js` L385 이하, `answerFingerprint`). 즉 **점수에는 안 들어가고 서술에는 들어간다.** 이 구분이 IX 지면에 명시되어야 한다.

**v2 의 "86/100과 fingerprint 일치는 출시 증거가 아니다" 는 타당하다.** 나의 G1~G31 게이트는 *표현 품질*을 측정하며, 이 5건은 *콘텐츠 계약*의 실패다. 서로 다른 층위이고, 내 게이트가 이 5건을 덮지 않는다 — **「게이트에 없는 검사는 사각지대다」의 새로운 실례**다.
