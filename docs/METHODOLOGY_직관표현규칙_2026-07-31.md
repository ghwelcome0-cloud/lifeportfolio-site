## 1. 왜 어려웠는가 — "상충 목표"를 "3중 제약" 아래서 동시 달성

### 1.1 근본 원인: 고유성과 직관성은 상충한다
- **고유성**: 고객마다 다른 76문항 원본 응답에서 파생된, 그 사람만의 문장.
- **직관성**: 누구에게나 즉시(3초) 이해되는 보편적 표현.
- 이 둘은 방향이 반대다. 고유할수록 표현이 거칠어지고(응답 조각의 접합), 직관적일수록 일반화되어 고유성이 옅어진다.
- **우리는 둘 다 "최고점"을 요구**했기 때문에, 쉬운 문제가 어려운 문제가 되었다.

### 1.2 난도를 곱연산으로 키운 6가지 요인
| # | 요인 | 왜 어려웠나 |
|---|---|---|
| ① | **생성이 아니라 정제** | 자유 생성(LLM식)이면 쉬우나, 우리는 결정론(같은 응답=같은 리포트)이 필수 → 응답 파생 조각을 "조립"해야 함. 자유도 없는 상태에서 자연스러움 만들기가 더 어렵다. |
| ② | **실화면 ↔ 코드 위치 괴리** | 눈에 보이는 문장과 그것을 만든 코드가 3~4단계(엔진→v4→매핑→렌더) 떨어져 있어, 한 문장 고치기 전에 파이프라인 역추적부터 필요. |
| ③ | **3중 제약 동시 통과** | 문장 하나 바꿀 때마다 (a)직관성 5축 (b)fingerprint 불변 (c)§7 비노출 을 **동시에** 만족해야 함 → 경우의 수 곱연산. |
| ④ | **한국어 접합의 함정** | 조사(을/를·이/가)·어미·문장 조각 결합 시 부자연스러움이 크게 드러남. 영어보다 조립 난도 높음. |
| ⑤ | **직관성 = 수동 검증** | 문법·§7·md5는 자동 검증되나 "첫인상에 꽂히는가"는 사람이 육안 판정 → 렌더→캡처→육안→재수정 루프에 시간·크레딧 소모. |
| ⑥ | **재료 품질 편차** | 엔진 출력(예: coreOneLine) 자체가 거친 경우, 렌더로 감싸도 한계. |

### 1.3 결론
어려웠던 것은 실력 부족이 아니라 **문제 자체의 구조적 난도**다. 그리고 이 난도를 통과한 규칙이 곧 **경쟁자가 쉽게 복제할 수 없는 해자(moat)** 다.

## 2. 직관 표현 규칙 5원칙 (핵심 지식화 산물)

### 원칙 ① 값의 나열이 아니라 "한 문장의 각인"
- 사람은 리스트가 아니라 **한 문장·한 이름표**를 기억한다.
- 각 핵심 지점 최상단에 **[진단명 배지] + [응답이 남긴 한 문장]** 을 각인.
- 예: `가치 설계자` / "멀리 보고 소중한 것을 밝혀 주는 사람."
- 구현 근거: 리포트 dashx `dxintro__badge` + `dxintro__line`; 프로그램 Ⅰ `glance-oneline__diag` + `glance-oneline__q`.

### 원칙 ② 재료를 그대로 붙이지 말고 "골격으로 재구성"
- 긴 문장/표는 안 읽힌다. **눈이 구조를 먼저 읽고 글을 나중에 읽게** 만든다.
- 변환 규칙:
  - "라벨: 값" → 아이콘 카드
  - "A→B→C" → 번호 스텝(타임라인)
  - 수치 → 막대(bar)
  - 리스크 → "이럴 때 → 이렇게 회복" 대응 카드
- 구현 근거: Stage-2 #7(qpurpose/qdo/qflow/qbench), #8(accrue/modc__done), #10(eff-card), #11(nstep2/risk2), 리포트 #5(vi-task/axis-bar).

### 원칙 ③ 리포트와 프로그램은 같은 '나'를 가리킨다 — 단일 원천(SSOT)
- 같은 사람인데 두 산출물의 표현이 다르면 신뢰가 깨진다.
- 각인·한 줄은 **같은 엔진 필드(`mission_vision._slots`)를 공유** → 항상 자동 일치. 재작성·인칭치환 금지.
- 구현 근거: #6-fix — 프로그램이 `summary.coreOneLine`(화면에 없는 긴 문장)이 아니라 리포트 화면과 동일한 `diag_badge`/`intro_line`을 쓰도록 정정.

### 원칙 ④ 표현은 바꾸되 진단은 안 바꾼다 — 렌더/데이터 레이어 분리
- 직관성을 높이려다 점수·지문이 흔들리면 상품 근간이 무너진다.
- **렌더 레이어(HTML문자열+CSS)** = fp 무관 · **데이터 레이어(엔진 .js)** = fp 증명 의무.
- fp 증명 절차: 변경 후 저장 → `git stash push -- <엔진>` → before 재생성 → `git stash pop` → diff(신규 필드+타임스탬프만 차이면 통과). KYS fp=1879861072 유지.

### 원칙 ⑤ 고객 대면에서 원본 세계관(§7)은 완전히 지운다 — 3중 방어선
- 도메인 8단어(종교·교육·경영·콘텐츠·선교·목회·신학·교회) + 종교 6단어(기독교·성경·예배·하나님·신앙·복음) 비노출. "신념·가치"는 허용.
- 3중 스크럽: (1) program gx-head (2) program 리빙북 (3) report dashx — **동시 수정 필수**.

## 3. 파이프라인의 상품적 의미 — "고유성의 상품화"

```
76문항 응답 데이터  →  지문(fingerprint) 결정  →  매핑 규칙(응답→항목)
    (고유성의 원천)         (같은 사람=같은 결과)        (무엇을 말할지)
                                                          ↓
 리포트 상품 (고객이 받음)  ←  제작규칙(직관 5원칙)  ←  각 항목·페이지
    (고유성의 상품화)             (어떻게 보여줄지)
```

### 왜 이것이 차별점인가
- **일반 진단 = 분류**: 유형 N개 중 하나를 배정(미리 써둔 N개 문장 중 택1).
- **인생포트폴리오 = 조합의 고유성**: 76문항 조합 → 지문 → 그 사람만의 문장을 **매번 조립**.
- 그래서 "각 사람의 고유성"을 상품으로 보여줄 수 있고, 그래서 어렵고, 그래서 아무나 못 만든다.
- 수개월이 걸린 것은 느려서가 아니라 **세상에 없던 파이프라인을 처음부터 설계**했기 때문. 검사지·매핑·제작규칙·렌더가 각각 독립 자산이면서 넷이 맞물려야 상품이 나오는 구조 = 진입장벽.

## 5. 대외 활용 로드맵 (고객 신뢰 자산화)

1. **블로그(고객 언어)**: "고유성 × 직관성을 어떻게 만들었나" — 심층리서치 5축 비교(전/후 점수) + 우리가 지운 것/놓은 것을 편지의 결로. *(§7 준수: 종교색 비노출)*
2. **유튜브 롱폼**: 파이프라인(검사지→매핑→제작규칙→리포트) 시각화 + 개발 여정 다큐.
3. **투자자료**: 3장 "고유성의 상품화" = 해자 논증.

> 대외 공개물은 반드시 §7 스크럽(원분야/종교색 비노출)을 통과시킬 것. 내부 방법론(이 문서)과 대외 메시지(블로그/영상)는 언어를 분리한다.
