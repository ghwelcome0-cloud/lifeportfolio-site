# Firestore·RTDB 접근 규칙 판정 — 담당자 지적 HIGH 3건 검증

작성: 2026-08-28 · 근거: `database.rules.json` (420행) · `firestore.rules` (302행) · `functions/index.js` 직접 열람

⑦축 발주(`3286455`) 회신에서 보안 담당(`agent_czb0fzmv02dk`)이 접근 통제 항목3을 "최소권한 부분 준수, 5점 불가(4/5)"로 판정하며 HIGH 3건을 지적했다.
**남의 판정을 그대로 옮기지 않고 규칙 파일과 실제 호출 코드를 직접 열어 한 건씩 사실 여부를 확정했다.**
결과: **3건 중 1건은 과장, 2건은 사실.**

---

## 0. 먼저 — 이 문서가 다루는 위험의 성질

RTDB 규칙은 "누가 어느 경로에 무엇을 쓸 수 있는가"만 정한다.
여기서 문제가 되는 것은 **외부인이 남의 데이터를 보는 것이 아니다.** 세 지적 모두 `auth.uid === $uid` 조건이 걸려 있어 **남의 계정 데이터에는 접근할 수 없다.** 이것은 확인했다.

문제는 다른 종류다 — **본인이 자기 데이터를 규칙이 의도하지 않은 방식으로 바꿀 수 있는가.**

---

## 1. 지적 ①: "결제 경로에서 클라이언트가 paid=true 를 만들 수 있다"

### 판정: **과장. 이미 방어가 있다.**

규칙 원문 (`payments/$uid/.write`):
```
auth != null && auth.uid === $uid && (!data.exists() || data.child('paid').val() !== true)
```

`data.child('paid').val() !== true` — **이미 `paid=true` 인 문서는 클라이언트가 더 쓸 수 없다.** 즉 결제 완료 상태를 덮어쓰거나 되돌리는 것은 규칙이 차단한다.

그리고 `payments/$uid` 에는 `"$other": { ".validate": false }` 가 있다 — **정의되지 않은 임의 키를 넣을 수 없다.** 이 방어는 5개 경로 중 `payments` 에만 있다.

실제 호출 경로도 확인했다.
- 클라이언트(`mypage.html` L736·744, `checkin-21.html` L842): **읽기만** 한다 (`get`)
- 쓰기는 Cloud Functions (`functions/index.js` L355 `admin.database().ref('payments/'+uid).update(...)`) — 서버가 결제사 응답을 검증한 뒤 기록

### 남는 실제 위험 (작지만 0은 아니다)
최초 생성 시점에는 문서가 없으므로 `!data.exists()` 가 참이 되어, 이론상 클라이언트가 **결제 없이 최초 1회 `paid=true` 를 만들 수 있다.** `paid` 의 `.validate` 가 `newData.val() === true` 여서 값 자체도 통과한다.

**그러나 이것이 곧 무료 이용은 아니다.** 리포트 생성은 Functions 가 별도로 판정한다(L188·L284 에서 서버가 `payments/{uid}/paid` 를 다시 읽는다). 즉 클라이언트가 자기 노드에 `true` 를 심어도, 서버가 결제사 원장을 대조하는 지점을 통과해야 한다. **다만 그 대조가 모든 경로에서 빠짐없이 일어나는지는 이 문서에서 측정하지 않았다.**

### 권고
`payments` 쓰기를 **서버 전용(`.write: false`)으로 바꾸고**, `_pending` 예약만 클라이언트에 허용한다. 이미 Functions 가 `_pending` 을 쓰고 있어(L240) 구조 변경 폭이 작다.
**선행 조건:** 클라이언트가 `payments` 에 쓰는 코드가 정말 0건인지 전수 확인 + 에뮬레이터 정상/차단 대조. 이것 없이 바꾸면 결제가 멈출 수 있다.

## 2. 지적 ②: "리포트·프로그램을 본인이 마음대로 고칠 수 있다"

### 판정: **사실.**

```
reports/$uid/.write  = auth != null && auth.uid === $uid
programs/$uid/.write = auth != null && auth.uid === $uid
```

조건이 "본인인가"뿐이다. **리포트 본문·점수·해석 문장 전부를 본인이 다른 값으로 바꿀 수 있다.**
`$sid` 하위에 `editCount < 999` 라는 제한이 있으나 이것은 **998회까지는 허용**한다는 뜻이다.

그리고 `reports/$uid` 와 `programs/$uid` 에는 **`$other` 차단이 없다** — 임의의 새 키를 추가할 수 있다.

### 왜 이것이 우리 사업에 중요한가
우리는 ⑤축(전문성·신뢰감)을 올리려고 **"계산 재현성이 증명됨"** 을 리포트 IX장에 공개했다(`f86d316`). 같은 응답이면 같은 결과가 나온다는 주장이다.

그런데 저장된 리포트를 본인이 고칠 수 있다면, **"이 리포트는 엔진이 계산한 그 값이다"** 를 우리가 보장하지 못한다. 즉 이 규칙 구멍은 보안 문제이면서 동시에 **⑤축 신뢰 주장의 구멍**이다.

악용 시나리오는 남의 데이터 탈취가 아니다 — 자기 리포트를 유리하게 고쳐 캡처해 유통하는 것, 또는 B2B 고객사가 소속 직원 결과를 조작하는 것이다.

### 권고
생성 산출물(`reports`, `programs`)은 **서버 전용 쓰기**로 바꾼다. 클라이언트가 필요한 것은 읽기와 "재생성 요청"이며, 재생성은 Functions 를 통하면 된다.
**선행 조건:** `regenerate.html` 등이 직접 쓰는지 전수 확인.

## 3. 지적 ③: "users 경로에 임의 자식을 추가할 수 있다"

### 판정: **사실.**

`users/$uid` 정의 키는 6개(`email`, `displayName`, `createdAt`, `lastLogin`, `reports`, `programs`)인데 **`$other` 차단이 없고 부모 레벨 `.validate` 도 없다.**
⇒ 정의되지 않은 임의 이름의 자식을 무제한 추가할 수 있다.

### 실측한 방어 유무 (5개 경로 비교)

| 경로 | `$other` 차단 | 쓰기 조건 |
|---|---|---|
| `payments/$uid` | **있음** | 본인 + `paid!==true` |
| `reports/$uid` | **없음** | 본인 |
| `programs/$uid` | **없음** | 본인 |
| `users/$uid` | **없음** | 본인 |
| `responses/$uid` | **없음** | 본인 |

`payments` 에만 방어가 있다. 나머지 4개는 같은 패턴의 구멍이 있다.

### 위험의 크기
남의 데이터를 볼 수는 없다. 실제 위험은 **저장 공간 남용**(본인 노드에 대량 데이터 투입 → 과금 증가)과 **데이터 오염**(우리 코드가 예상하지 않은 키가 섞여 화면이 깨짐)이다. 즉 정보 유출형이 아니라 비용·안정성형 위험이다.

`config` 는 `.read: auth != null` / `.write: false` 로, 쓰기는 막혀 있으나 **로그인한 누구나 읽을 수 있다.** 여기에 공개해도 되는 값만 있는지는 **미측정**이다.

## 4. 종합 판정

| 지적 | 담당자 판정 | 내 검증 결과 |
|---|---|---|
| ① 결제 `paid=true` | HIGH | **과장** — 덮어쓰기 차단·`$other` 차단 있음. 최초 1회 생성 여지만 남음 |
| ② 리포트·프로그램 조작 | HIGH | **사실** — ⑤축 재현성 주장과 직접 충돌 |
| ③ `users` 임의 자식 | HIGH | **사실** — 단, 유출형이 아니라 비용·안정성형 |

**항목3 = 4/5 는 유지가 타당하다.** 담당자 결론(5점 불가)에 동의한다. 다만 근거는 3건이 아니라 2건이며, ①은 등급을 낮출 근거가 아니다.

**⑦축 81.00 유지**도 그대로 둔다. 규칙을 아직 고치지 않았으므로 점수를 올릴 근거가 없다.

## 5. 왜 지금 고치지 않는가

`database.rules.json` 과 `firestore.rules` 는 **성역(read-only)** 이다. 이유는 결제·로그인·리포트 저장이 모두 이 파일 하나에 걸려 있어, 잘못 조이면 **고객이 결제를 못 하거나 리포트를 못 받는다.** 되돌리기 전까지 매출이 멈춘다.

배포헌법 최상위 규범이 **"확실하지 않으면 배포하지 않는다"** 이므로, 대표님 승인 + 아래 선행 작업 없이는 손대지 않는다.

### 승인 시 작업 순서 (제안)
1. 호출자 전수 조사 — `payments`·`reports`·`programs`·`users` 에 **쓰는** 코드를 한 줄씩 목록화
2. 에뮬레이터 대조 — 정상 동작이 통과하는지 + 조작 시도가 차단되는지 **양쪽** 확인 (통과만 보면 거짓 초록불)
3. `$other` 차단 4곳 추가 (위험 낮고 효과 확실 — 여기부터)
4. `reports`·`programs` 서버 전용화 (⑤축 재현성 주장 보강)
5. `payments` 서버 전용화 (가장 조심스러움 — 결제 중단 위험)

**3번만 해도 지적 ③이 해소되고 ⑤축 주장이 단단해진다. 결제 흐름을 건드리지 않으므로 위험이 가장 낮다.**

## 6. 미측정 (정직 고지)

- 실제 악용 발생 여부 — 로그 분석 미실시
- 조작 시도가 정말 통과하는지 — 에뮬레이터 실행 미실시 (규칙 문면 판정만)
- `config` 에 비공개 값이 있는지 — 내용 미확인
- Firestore 302행 전량 — `payments` client create 와 "서버 전용" 주석 불일치는 담당자 지적을 **아직 검증하지 않았다**
- 서버가 결제를 재대조하는 경로가 빠짐없는지 — Functions 전체 흐름 미추적
