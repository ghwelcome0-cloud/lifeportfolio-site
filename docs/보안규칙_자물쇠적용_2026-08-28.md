## 0. 한 문장 요약

승인받은 4곳 중 **3곳에 자물쇠를 달았고, 실제로 잠기는 것을 에뮬레이터로 증명**했습니다.
남은 1곳(`responses`)은 **구조상 같은 방식이 불가능**하다는 사실을 실행 중에 발견했습니다. 제 사전 판정이 틀렸습니다.

## 1. "자물쇠"가 무엇인가 (용어 풀이)

우리 데이터베이스는 `users/홍길동/이름` 처럼 서랍 구조입니다.
규칙 파일에는 "이 서랍에는 **이름, 이메일, 가입일**만 넣을 수 있다"고 적혀 있습니다.

그런데 **"적어놓지 않은 서랍은 어떻게 하나"** 를 명시하지 않으면, 파이어베이스는 **그냥 통과시킵니다.**
즉 누군가 `users/홍길동/등급 = 관리자` 라는, 우리가 설계하지도 않은 서랍을 만들어 넣을 수 있습니다.

`"$other": { ".validate": false }` 한 줄이 그 구멍을 막습니다.
뜻: **"내가 이름을 적어둔 서랍 외에는 전부 거부"**. 이것을 이 문서에서 **자물쇠**라고 부릅니다.

---

## 2. 승인 4곳 중 3곳 적용 · 1곳 적용 불가 — ★ 제 사전 판정 정정

### 2-1. 무엇이 틀렸는가

이전 보고에서 저는 승인 대상을 이렇게 적었습니다.

> `reports`, `programs`, `users`, `responses` — 4경로에 `$other` 추가

실행하려고 실제 구조를 뜯어보니, **`responses` 는 같은 방식이 성립하지 않습니다.**

| 경로 | 그 층에 있는 것 | 자물쇠 가능? |
|---|---|---|
| `users/$uid` | 이름이 정해진 키 6개 (email, displayName, createdAt, lastLogin, reports, programs) | **가능** |
| `reports/$uid/$sid` | 이름이 정해진 키 15개 | **가능** |
| `programs/$uid/$sid` | 이름이 정해진 키 13개 | **가능** |
| `responses/$uid` | `_active` 1개 + **`$sid` 와일드카드** | **불가능** |

**왜 불가능한가 (쉬운 설명):**
`$sid` 는 "여기 오는 서랍 이름은 **아무거나 다 받는다**"는 뜻입니다. 진단 회차마다 새 아이디가 생기니 그래야 맞습니다.
`$other` 는 "이름 안 적힌 서랍은 **다 막는다**"는 뜻입니다.
**한 층에 "다 받는다"와 "다 막는다"를 동시에 놓을 수 없습니다.** 서로 정반대이고, 파이어베이스는 한 층에 와일드카드를 하나만 허용합니다.

**그럼 `responses` 는 지금 안전한가:** 부분적으로 안전합니다. 실측 결과 아래 층에는 이미 자물쇠가 있습니다.

```
responses/$uid/$sid            → $other 있음 ✅
responses/$uid/$sid/meta       → $other 있음 ✅
responses/$uid/$sid/qlog/$qid  → $other 있음 ✅
```

즉 **응답 내용 자체는 이미 잠겨 있습니다.** 열려 있는 것은 `responses/$uid` 바로 아래에 엉뚱한 이름의 새 서랍을 만드는 행위이며, 이는 `$sid` 로 취급되어 **"status 를 반드시 가져야 한다"** 는 조건에 걸립니다. 완전히 열린 것은 아닙니다.

**남은 위험과 처리:** 그래도 `status` 만 넣으면 쓰레기 데이터를 만들 수 있습니다. 이건 자물쇠가 아니라 **다른 방식(키 형식 제한)** 으로 막아야 하며, 별건으로 올립니다(§6).

### 2-2. 무엇을 왜 이렇게 정정했는가

저는 이전 윈도우에서 "4경로 모두 `$other` 없음 → 4개 추가"라고 보고했습니다.
그 판정은 **`$other` 라는 글자가 있는지만 세어본 결과**였습니다. 같은 층에 다른 와일드카드가 있는지는 보지 않았습니다.
이것이 우리 결함 사전의 **DF(개수·이름으로 추론 금지, 열어보고 판정)** 에 해당합니다. 제가 그 함정에 다시 걸렸습니다.

**대표님께 드리는 정확한 숫자: 승인 4건 중 3건 적용 완료, 1건 적용 불가(방식 변경 필요).**

## 3. 실제 변경 내용 — 6줄 추가, 삭제 0줄

배포헌법 제14조(교체가 아닌 추가)를 지켰습니다.

```diff
  "users": { "$uid": {
+       "$other": { ".validate": false },
        "programs": { ...

  "reports": { "$uid": { "$sid": {
-         "report": {}
+         "report": {},
+         "$other": { ".validate": false }

  "programs": { "$uid": { "$sid": {
-         "program": {}
+         "program": {},
+         "$other": { ".validate": false }
```

| 항목 | 값 |
|---|---|
| 삽입 줄 | **6** |
| 삭제 줄 | **0** (쉼표 추가로 2줄이 diff 에 뜨지만 내용 삭제는 없음) |
| **`payments` 접촉** | **0줄 — 결제 경로는 손대지 않았습니다** |
| JSON 유효성 | 통과 |

**중간에 한 번 되돌린 일:** 처음에 파이썬으로 JSON 을 다시 써넣었더니 **서식이 87줄 바뀌었습니다.** 내용은 같지만 성역 파일에 그런 대규모 변경을 남기면 나중에 "무엇이 진짜 변경인지" 알 수 없습니다. 되돌리고 **텍스트 6줄 삽입**으로 다시 했습니다.

## 4. ★ 증명 — "달았다"가 아니라 "잠긴다"를 보였습니다

자물쇠를 달았다는 말만으로는 아무것도 증명되지 않습니다(결함 BT — 거짓 초록불).
**두 가지를 동시에** 보여야 합니다.

| 무엇을 | 왜 필요한가 |
|---|---|
| **양성**: 정상 저장은 여전히 성공 | 이걸 빼면 "고객이 리포트를 저장 못 하는" 사고가 남 |
| **음성**: 엉뚱한 키는 거부 | 이걸 빼면 "잠갔다고 착각"하는 거짓 초록불 |

### 4-1. 실측 결과 (파이어베이스 에뮬레이터, 2026-08-28)

```
=== 1단계: 규칙 파일 정적 감사 ===
  OK   reports/$uid/$sid                 자물쇠 있음
  OK   programs/$uid/$sid                자물쇠 있음
  OK   users/$uid                        자물쇠 있음
       responses/$uid                    적용 불가 — 와일드카드 $sid 와 충돌
  OK   payments/$uid          (미접촉)    자물쇠 있음
  OK   payments/$uid/_pending (미접촉)    자물쇠 있음

=== 2단계: 에뮬레이터 양성·음성 실측 ===
  PASS  users 정상키만 (양성)          기대=allow 실제=allow (HTTP 200)
  PASS  users 미정의키 혼입 (음성)      기대=deny  실제=deny  (HTTP 401)
  PASS  users 미정의키 단독 (음성)      기대=deny  실제=deny  (HTTP 401)
  PASS  reports 정상키만 (양성)         기대=allow 실제=allow (HTTP 200)
  PASS  reports 미정의키 혼입 (음성)     기대=deny  실제=deny  (HTTP 401)
  PASS  programs 정상키만 (양성)        기대=allow 실제=allow (HTTP 200)
  PASS  programs 미정의키 혼입 (음성)    기대=deny  실제=deny  (HTTP 401)
  PASS  타인 uid 쓰기 (음성·통제군)      기대=deny  실제=deny  (HTTP 401)
  PASS  비로그인 쓰기 (음성·통제군)       기대=deny  실제=deny  (HTTP 401)
  PASS  payments 미정의키 (음성·회귀)    기대=deny  실제=deny  (HTTP 401)

요약: 양성 3/3 · 음성 7/7 · 실패 0
```

### 4-2. ★★ 가장 중요한 증거 — 자물쇠가 **원인**임을 보였습니다

위 결과만으로는 "원래 막혀 있던 것"과 "자물쇠가 막은 것"을 구분할 수 없습니다.
그래서 **자물쇠를 떼어낸 옛 규칙으로 에뮬레이터를 다시 띄워** 같은 시도를 했습니다.

| 시도 | 자물쇠 **없을 때** | 자물쇠 **있을 때** | 판정 |
|---|---:|---:|---|
| `users/…/role = "admin"` | **200 (뚫림)** | **401 (막힘)** | 자물쇠가 원인 ✅ |
| `reports/…` 에 `injected` 키 | **200 (뚫림)** | **401 (막힘)** | 자물쇠가 원인 ✅ |
| `programs/…` 에 `injected` 키 | **200 (뚫림)** | **401 (막힘)** | 자물쇠가 원인 ✅ |
| `payments/…` 에 `hacked` 키 | **401** | **401** | 원래부터 안전 (미접촉) |

**이 표가 이번 작업의 핵심 증거입니다.** 왼쪽 열이 없으면 "원래 안전했는데 자물쇠 덕분이라고 착각"할 수 있었습니다.

### 4-3. 실측 중 스스로 잡은 거짓 빨간불 1건

첫 실행에서 **양성 0/3 · 음성 7/7** 이 나왔습니다. 즉 "정상 저장도 전부 거부"였습니다.
그대로 믿었다면 **"자물쇠가 서비스를 망가뜨린다"** 는 잘못된 결론으로 승인 작업을 되돌렸을 것입니다.

원인은 규칙이 아니라 **제 검사 코드**였습니다. 에뮬레이터는 `auth_variable_override` 만으로는 로그인으로 인정하지 않고, `Authorization: Bearer owner` 헤더가 함께 있어야 `auth != null` 이 됩니다.
헤더를 붙이자 양성 3/3 이 나왔습니다. **규칙은 처음부터 정상이었고, 측정기가 틀렸습니다.**

## 5. ★ 별건 발견 — 에뮬레이터가 기존 규칙의 정규식을 거부

작업 중 에뮬레이터가 이 오류로 기동을 거부했습니다.

```
database.rules.json:12:125: Illegal regular expression, 'whitespacechar' not found
```

`users/$uid/email` 의 이메일 검사식에 쓰인 `\s`(공백 문자) 를 에뮬레이터 파서가 모릅니다.

| 확인 항목 | 결과 |
|---|---|
| 제 변경 때문인가 | **아니다.** 변경 **전** 파일로도 같은 오류 발생 (실측) |
| 라이브 서비스는 문제 있는가 | **없다.** 실서버는 정상 작동 중이며 이 규칙으로 배포되어 있음 |
| 원인 | 에뮬레이터 파서와 실서버 파서의 차이 |
| 이번 처리 | **저장소 파일은 손대지 않았다.** `/tmp` 검증용 사본에서만 `contains('@')` 로 바꿔 에뮬레이터를 띄웠다 |
| 남는 영향 | 이 검사식이 있는 한 **에뮬레이터를 CI 에 넣을 수 없다** |

⇒ 별건 과제로 올립니다(§6). 성역 파일이라 대표님 승인 없이 건드리지 않습니다.

## 6. 대표님 결정이 필요한 사항 (신규 3건)

| # | 사안 | 선택지 |
|---:|---|---|
| 1 | `responses/$uid` 는 자물쇠 방식이 불가능 | (가) 지금 상태 유지 (아래 3층은 이미 잠김) / (나) 키 형식 제한 규칙을 새로 설계 |
| 2 | 이메일 검사식이 에뮬레이터와 안 맞음 | (가) 그대로 둠 — 에뮬레이터 검증은 계속 수동 / (나) 실서버·에뮬레이터 양쪽에서 통하는 식으로 교체(성역 변경) |
| 3 | `reports/$sid` 는 **998회 편집 허용** (`editCount < 999`) | (가) 유지 / (나) 상한 하향 (예: 10회) |

**#3 설명:** 리포트를 998번까지 고칠 수 있다는 뜻입니다. 우리는 ⑤축에서 **"같은 응답이면 같은 리포트가 나온다(계산 재현성)"** 를 공개했는데, 998번 수정이 가능하면 그 주장과 어긋나 보일 수 있습니다. 다만 실제로는 **본인만** 고칠 수 있고 서버가 값을 다시 확인합니다.

| ⑦축 점수 변화 | **미측정** — 자체 채점으로 올렸다고 주장하지 않습니다(§8.3 원칙) |

## 8. 검증 재현 방법

```bash
# 1) 에뮬레이터 기동 (이메일 정규식 치환 사본 필요 — §5 참조)
/home/user/webapp/node_modules/.bin/firebase emulators:start --only database --project lifeporfolio

# 2) 자기검사만 (에뮬레이터 불필요, CI 에서 도는 것)
npm run rules:matrix:selftest      # 14/14

# 3) 양성·음성 전량 실측 (에뮬레이터 필요)
npm run rules:matrix               # 양성 3/3 · 음성 7/7
```

**미측정을 통과로 두지 않는 장치:** 에뮬레이터가 없으면 이 스크립트는 exit 0 이 아니라 **exit 2** 를 냅니다. "측정 못 했으니 통과" 를 만들지 않기 위해서입니다.

## 9. 자기 반박

1. **에뮬레이터는 실서버가 아니다.** 파서가 다르다는 증거를 §5 에서 직접 확인했다. 따라서 이 검증은 "실서버에서도 그럴 것"의 **근사치**다.
2. **양성 케이스가 3개뿐이다.** 실제 저장 흐름은 더 복잡하다. 대표 케이스만 확인했다.
3. **`responses` 를 "이미 안전"으로 결론 낼 근거가 부족하다.** 아래 3층에 자물쇠가 있다는 구조 사실만 확인했고, 공격 시나리오를 실행해보지 않았다.
4. **⑦축 점수를 올려 적지 않았다.** 자체 채점으로 상승을 주장하지 않는다는 원칙(§8.3)을 따른다.
5. **제 사전 판정이 1건 틀렸다.** 4곳 전부 가능하다고 보고했으나 3곳만 가능했다. 원인은 글자 수만 세고 구조를 안 본 것이다.
