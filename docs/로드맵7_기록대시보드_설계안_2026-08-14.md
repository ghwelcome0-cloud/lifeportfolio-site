# 기록 대시보드 설계안 (로드맵 7 · ④ 자산화·축적 연결성)

- 문서 지위: 설계안 (구현 착수 전 검토용)
- 작성일: 2026-08-14
- 목적 축: ④ 자산화·축적 연결성 (88 → 95 목표 · 현재 우리가 벤치마크 최고)
- 상태: **설계 단계** — 구현 착수 여부는 대표님 판단

---

## 1. 지금 무엇이 비어 있는가

우리 결과물은 리포트와 실행프로그램이다. 둘 다 **한 번 받고 끝나는 형태**다.
고객이 3개월 뒤 무엇을 했는지 우리는 모르고, 고객도 자기 기록을 다시 볼 자리가 없다.

④축이 88점인데도 만점이 아닌 이유가 이것이다. 우리는 **자산을 만들어 주기만 하고,
자산이 쌓이는 자리를 주지 않는다.** 쌓이는 자리를 만드는 것이 ④축의 유일한 구조적 수단이다.

부수 효과가 더 크다. 계속 들어오는 자리가 있으면
- 재검사 파일럿(로드맵 4)의 참가자를 모으기 쉬워진다
- 실제 행동 자료가 쌓여 예측 연구의 재료가 된다
- 재구매·구독 모델의 근거가 생긴다

---

## 2. 두 갈래 — 무엇을 먼저 만드는가

| | A안 Notion 템플릿 | B안 웹 대시보드 |
|---|---|---|
| 제작 기간 | 1~2주 | 2~3개월 |
| 제작 비용 | 거의 없음 | 개발 비용 발생 |
| 고객 진입 | Notion 계정 필요 | 우리 사이트 로그인 |
| 우리가 보는 자료 | **못 본다** (고객 사본) | 본다 (동의 시) |
| 수정·개선 | 템플릿만 갱신 | 배포 필요 |
| 이탈 위험 | Notion 정책 변경에 종속 | 우리가 통제 |

### 권고 — A안을 먼저, B안을 뒤에

이유:
1. **A안은 이번 달에 낼 수 있다.** ④축 개선을 곧바로 시작한다.
2. **A안이 B안의 설계도가 된다.** 고객이 실제로 어느 칸을 채우고 어느 칸을 비우는지
   먼저 보고 나서 웹을 만들면, 안 쓰는 화면을 만들지 않는다.
3. B안을 먼저 만들면 **라이브 서비스에 로그인·개인정보 저장 기능이 붙는다.**
   현재 고객에게 위험을 주는 변경이므로, 검증 없이 손대지 않는다.

★ 안정성 원칙 적용: B안은 기존 결제·검사 흐름과 **분리된 경로**로 만든다.
대시보드 장애가 검사·결제를 멈추게 하는 구조를 만들지 않는다.

---

## 3. A안 — Notion 템플릿 구성

리포트의 어느 부분과 이어지는지 함께 적는다. 이어지지 않는 칸은 만들지 않는다.

### 3.1 첫 화면 (고정 · 고객이 안 고치는 칸)

| 칸 | 내용 | 출처 |
|---|---|---|
| 고유코드 | 64비트 hex | 리포트 표지 |
| 검사일 | 날짜 | 검사 시점 |
| 상위 2분야 | 분야명 2개 | 리포트 I장 |
| 한 문장 정체 | 융합 문장 | 리포트 II장 |
| 내 방향 | 비전 문장 | 리포트 V장 |

→ 고객이 대시보드를 열면 **자기가 누구였는지 3초 안에 다시 본다.**
이게 ①축(첫인상 직관성)과도 이어진다.

### 3.2 실행 기록 (고객이 채우는 칸 · 핵심)

실행프로그램의 완료 기준을 그대로 항목으로 옮긴다.

| 칸 | 형태 | 비고 |
|---|---|---|
| 항목 | 실행프로그램 항목명 | 미리 채워 둔다 |
| 완료 기준 | 문장 | 미리 채워 둔다 (판정 불변) |
| 상태 | 안 함 / 하는 중 / 마침 | 고객 선택 |
| 마친 날 | 날짜 | 고객 입력 |
| 증거 | 링크·파일·한 줄 | 고객 입력 |

★ **증거 칸이 자산화의 실체다.** 상태만 체크하면 체크리스트일 뿐이고,
증거가 붙으면 **포트폴리오**가 된다. 우리 서비스 이름이 인생포트폴리오인 이유와 맞는다.

### 3.3 분기 되돌아보기 (3개월마다 1장)

| 질문 | 형태 |
|---|---|
| 이번 3개월에 마친 것 | 자동 집계 (마침 개수) |
| 가장 남는 한 가지 | 한 줄 |
| 방향이 바뀌었는가 | 예 / 아니오 + 이유 |
| 다음 3개월에 할 하나 | 한 줄 |

★ "방향이 바뀌었는가" 는 로드맵 4 의 **제외 판정 문항과 같은 역할**을 한다.
대시보드가 재검사 파일럿의 자료 수집 창구가 된다.

### 3.4 만들지 않는 칸

- 점수·등급 표시 → 자평 점수는 대외 노출 금지 (용어분리지침 §3.3)
- 다른 사람과 비교 → 고유성 원칙 위반. 비교하면 유형이 된다.
- 자동 조언 생성 → 엔진은 규칙 기반이고 대시보드는 기록 자리다. 섞지 않는다.

---

## 4. B안 — 웹 대시보드 (뒤에)

A안 3~6개월 운영 후 착수 판단. 그때 볼 것:

1. 고객이 실제로 다시 열었는가 (열지 않으면 웹으로 만들어도 안 열린다)
2. 어느 칸을 채우고 어느 칸을 비웠는가 → 비운 칸은 웹에서 뺀다
3. Notion 계정이 진입 장벽이었는가

### 4.1 기술 전제 (지금 확정해 둘 것)

- **기존 라이브 경로와 분리** — `/report` `/program` `/suvey` 를 건드리지 않는다
- 저장은 Firebase (이미 쓰는 스택). 새 인프라를 늘리지 않는다
- 로그인은 검사 시 발급한 고유코드 + 이메일 대조. 새 비밀번호 체계를 만들지 않는다
- 대시보드가 죽어도 검사·결제는 산다 (독립 실패)

---

## 5. 개인정보

- A안: 고객 자기 Notion 에 있다. **우리는 자료를 갖지 않는다** → 위험 최소
- B안: 우리가 보관한다 → 수집 항목·보관 기간·파기 절차를 약관에 먼저 반영해야 한다
  ⇒ B안 착수 전 `terms-revision-draft.md` · `privacy-policy-revision-draft.md` 갱신이 선행 조건

---

## 6. 착수 순서

```
1  A안 Notion 템플릿 제작           1~2주   ← 즉시 가능
2  기존 고객에게 안내 (선택 제공)      +1주
3  3~6개월 사용 관찰
4  B안 착수 판단 (관찰 결과 근거)
5  B안 착수 시 약관·개인정보 개정 선행
```

---

## 7. 이 설계가 ④축을 올리는 근거

④축은 "결과물이 자산으로 쌓이는가"를 본다.
지금은 PDF 2개다 — 받는 순간이 최고점이고 이후 내려간다.
기록 자리가 있으면 **시간이 갈수록 자료가 늘어난다.** 방향이 반대가 된다.
벤치마크 중 이런 자리를 가진 곳은 Full Focus 뿐이며 우리보다 낮은 80점이다.
A안만으로도 우위가 벌어진다.
