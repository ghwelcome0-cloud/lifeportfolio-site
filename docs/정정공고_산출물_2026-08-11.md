# 산출물 정정 공고 — 2026-08-11

> **왜 이 문서를 남기는가.** 내가 대표께 드린 산출물 중 다섯 건에
> 사실과 다른 수치·표현이 들어 있었다. 결론이 같아도 근거가 틀렸으면 틀린 것이다
> (결함 CM · 부록 제12조). 산출물을 회수할 수는 없으므로, **무엇이 틀렸고
> 무엇이 맞는지를 한 자리에 남긴다.** 이후 이 문서가 해당 산출물보다 우선한다.

**정정 원칙**
- 실측하지 않은 수치는 쓰지 않는다.
- 내부 계산값을 고객 지면·대외 문서에 노출하지 않는다(`internal_only`).
- 대체된 문서는 폐기하지 않고 `superseded` 로 표시해 이력을 남긴다(축적 원칙 B).

## C-1 · 제작규칙서 v2.0 모체 L1091 — 문항 수 산술 오류

| 구분 | 내용 |
|---|---|
| **위치** | `docs/제작규칙서_v2.0_최종본.md` 제12부 머리말 |
| **틀린 표기** | 「11개 영역 · 56 본문항 + 14 기타입력 + 메타 = 76문항」 |
| **문제** | 56 + 14 = 70. 「+ 메타」로 6을 채운다는 뜻이나 메타는 문항이 아니다. 산술이 성립하지 않는다. |
| **실측** | `data/questions.json` → `sections[].questions` = **56** (11개 영역)<br>`data/mapping.json` → `questionMapping` = **76키**<br>차분 **20** = `Q8·Q15·Q20·Q22·Q27·Q29·Q32·Q34·Q40·Q42·Q48·Q50·Q56·Q58·Q64·Q66·Q72·Q74·Q76·Q78` |
| **정정** | 「11개 영역 · 본문항 56 + 기타입력 20 = `mapping.questionMapping` 76키」 |
| **상태** | ✅ **모체 문서에 반영 완료** (2026-08-11) |

## C-2 · 심층리서치 프롬프트 v2 L30 — 조합 수 「10^58」

| 구분 | 내용 |
|---|---|
| **틀린 표기** | 응답 조합 공간 「10^58」 (다른 자리에서는 「10^53」) |
| **문제** | ① 같은 개념에 두 값이 쓰였다 ② 이론적 조합 상한이지 **실제 변별 능력이 아니다** ③ 외부 리서치에 넘어가면 검증 불가능한 주장으로 인용된다 |
| **사실** | 엔진이 실제로 보장하는 것은 **64bit fingerprint** 이며, 규칙 기반 결정론적 산출이다(난수 호출 0회). 40시드 표본에서 **고유코드 160/160 불변**을 실측했다. |
| **정정** | 조합 상한 수치는 **대외 문서에서 사용하지 않는다.** 필요하면 「64bit 고유코드」와 「40시드 160/160 불변 실측」만 쓴다. |
| **상태** | 🔴 **대외 고지 필요** — 이미 심층리서치에 전달된 프롬프트이므로 회수 불가. 결과물 수령 시 해당 수치 인용분을 걷어낸다. |

## C-3 · 5축 재평가 보고서 — 점수 71.6 → 95.2

| 구분 | 내용 |
|---|---|

| **문제** | 이 숫자들은 **내가 내 작업을 스스로 채점한 내부 지표**다. 외부 기준·표본·검증자가 없다. 그럼에도 보고서 형식이라 객관 지표처럼 읽힌다. |
| **사실** | 실측 근거가 있는 것은 게이트 통과 수치뿐이다 — D-4 **86/86**, G16 badPages **0**(32뷰), G21 **24/24**×2, G26·G27·G28 fail **0**, G32 fail **0**(8종). |
| **정정** | 5축 점수 전량 **`internal_only`** 로 격하. 대외 문서·고객 지면·투자 자료에 인용하지 않는다. 품질 근거가 필요하면 **게이트 실측치**를 쓴다. |
| **상태** | 🔴 **표시 필요** — 보고서는 폐기하지 않고 머리에 `internal_only` 를 명기한다. |

## C-4 · 벤치마킹 순위표 — `superseded`

| 구분 | 내용 |
|---|---|
| **틀린 위치** | 경쟁 서비스 대비 순위·등급 표 |
| **문제** | 평가 시점의 공개 정보에 기댄 상대 순위이며, **경쟁사 내부 지표는 확인할 수 없다.** 「1위」·「최고」류 표현은 P1 정직성 제약이 영구 금지한 표현이다. |
| **정정** | 순위표 전체를 **`superseded`** 로 표시. 대체 서술은 상대 순위가 아니라 **우리가 실제로 보장하는 것**만 적는다 — 규칙 기반 결정론, 64bit 고유코드, 응답 기반 산출(A안), 게이트 실측 통과. |
| **상태** | 🔴 **표시 필요** |

## C-5 · 배포 헌법 — 「push = 배포」 서술

| 구분 | 내용 |
|---|---|
| **틀린 표기** | 「main 에 push 하면 라이브에 반영된다」 |
| **문제** | **현행과 다르다.** PR #228 이후 배포 경로가 3단으로 분리됐다. |
| **현행 (2026-08-11 실측)** | ① `main` 직접 push **불가** — ruleset `main-one-person-safe-mode`(PR 필수 · 승인 0명 · required check 2건)<br>② PR merge 는 **저장소 반영일 뿐 배포가 아니다**<br>③ 라이브 반영은 `Promote Firebase Hosting Live` **수동 dispatch** 로만 일어난다 (검수된 아티팩트 + main 재빌드 manifest 대조 + `production-live` 환경) |
| **정정** | 「push = 배포」를 「**merge = 저장소 반영 · dispatch = 배포**」로 고쳐 쓴다. **"확실하지 않으면 배포하지 않는다"** 원칙은 그대로다. |
| **상태** | 🔴 **배포 헌법 문서 갱신 필요** |
