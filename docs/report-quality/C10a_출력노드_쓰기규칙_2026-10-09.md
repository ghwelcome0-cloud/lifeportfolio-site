## 왜 필요한가 (쉬운 설명)
INPUT-VALIDATION(#374)은 "응답(answers)이 잘못됐으면 `submitted`로 못 바꾼다"까지 막았습니다.
그런데 리포트·프로그램 **결과 노드**(`reports/$uid/$sid`, `programs/$uid/$sid`, 인덱스 `users/$uid/reports|programs/$sid`)는
"로그인한 본인이면 쓸 수 있다"였습니다. 즉 검사 화면을 거치지 않고 결과만 직접 써 넣는 길이 열려 있었습니다.
C10a는 그 길을 **규칙 자체**에서 닫습니다: 결과 노드를 쓰려면 같은 `$sid`의 응답 `status`가 `submitted` 또는 `completed`여야 합니다.

## ① 규칙 변경 (`database.rules.json`, 바뀐 문자열 4개 — `scripts/_diary-release-delta.cjs`에 [후, 전] 쌍 등록)
공통 조건 `COND` = `(!newData.exists() || responses/$uid/$sid/status === 'submitted' || … === 'completed')`
- `reports/$uid/$sid/.write`: 기존 조건 뒤에 `&& COND`
- `users/$uid/reports/$sid/.write`: 기존 조건 뒤에 `&& COND`
- `programs/$uid/.write`: `auth.uid === $uid` → `auth.uid === $uid && !newData.exists()` (서브트리 통째 삭제 = 탈퇴 경로만), `programs/$uid/$sid/.write` 신설 = `auth.uid === $uid && COND`
- `users/$uid/programs/.write`: 같은 방식(삭제 전용 + `$sid` 신설)

`!newData.exists()`는 삭제를 허용하기 위한 것입니다(마이페이지 리포트 삭제 3노드 동시 null, 탈퇴 전체 wipe).
b2b 분기(`reports` 쓰기 규칙의 `b2b_access/surveySid !== $sid` 등)는 그대로이며, 조건은 뒤에 AND로 붙기만 했습니다.

## ② report-loading fail-closed (`report-loading.html`)
이전: 검증 모듈이 없거나 예외가 나면 `console.warn` 후 **그냥 생성 진행**(fail-open).
이후: 모듈 없음 / `validateAll`이 함수가 아님 / 예외 / 판정(`ok` boolean) 없음 → `showError(report_loading.err_validation_unavailable)` 후 `return` (생성·쓰기 0회).
i18n 키 `report_loading.err_validation_unavailable` ko/en 추가.
단위 게이트(`scripts/test-group-report-flow.cjs`) `validation-fail-closed-{개인,단체}-{missing,throws,no-verdict,invalid}` 8건: 리포트 null, 이동 0, 진행률 25 미도달, PUT/인덱스/서버 호출 0.
기존 흐름 테스트들은 최소 합성 세션(`{Q1}`)을 쓰므로 통과 판정 stub을 명시적으로 주입합니다(stub 없이는 이제 실패 — 그것이 fail-closed의 증거).
