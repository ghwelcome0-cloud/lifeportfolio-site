## 0. 이 문서가 존재하는 이유 — 한 번 크게 틀렸기 때문

직전 보고에서 우리는 **"정지 화면 60.2% → 0.0%"** 라고 보고했습니다.
그 수치 자체는 사실입니다. 정본 검사 도구가 실제로 0건을 반환했습니다.

그런데 대표님이 이렇게 지적하셨습니다.

> **"46초 구간에 나오는 영상이 일시정지 되는 모습이 끊김이 있어요."**

재조사 결과 **도구가 46초 구간을 애초에 검사하지 않았다**는 것이 밝혀졌습니다.

| | 내용 |
|---|---|
| 검사 규칙 | 프레임 간 화소차 **< 0.35** 이면 "정지" |
| 46초 구간 실제 | 아주 미세하게 움직여서 **0.35 를 간신히 넘김** |
| 결과 | 기계 판정 = "움직임" → **후보 목록에 아예 오르지 않음** |
| 사람 눈 | **"멈춰 있다"** |

**"0건"은 "결함이 없다"가 아니라 "검사 대상이 아니었다"는 뜻이었습니다.**

새 자(尺)로 다시 재니 같은 성질의 결함이 **8건 48.5초, 본편의 12.0%** 있었습니다.
46초는 그중 **1건**일 뿐이었고, 가장 큰 것은 **375.5~405.0초 — 영상 마지막 30초 전체**였습니다.
엔딩이 통째로 정지처럼 보이고 있었는데, 우리는 그것을 "0건"이라고 보고하고 있었습니다.

> 규칙을 지키는 것보다 **왜 그 규칙이 생겼는지 아는 것**이 중요합니다.
> 근거를 모르면 상황이 조금만 달라져도 같은 사고가 반복됩니다.

## 1. 제작 규칙 — 5단계 (이 순서를 바꾸지 마십시오)

```
 STEP 1  콘텐츠 유형 분류      → 어디에 모션이 "필요한가"를 정한다
 STEP 2  소재 기하 측정        → 어디까지 확대해도 "안 잘리는가"를 정한다
 STEP 3  구간 확정             → 어디서 어디까지가 "한 화면인가"를 정한다
 STEP 4  렌더                  → 만든다
 STEP 5  이중 검수 (기계 + 눈) → 됐는지 판정한다
```

각 단계는 **앞 단계의 산출물이 있어야** 시작할 수 있습니다.
순서를 건너뛰면 반드시 되돌아옵니다 (§6 의 실패 사례 4건이 전부 그렇습니다).

## 2. STEP 1 — 콘텐츠 유형 분류 (가장 중요)

### 2.1 왜 유형부터 나누는가

**모든 정지가 결함이 아닙니다.**

| 유형 | 화면 예 | 정지했을 때 | 조치 |
|---|---|---|---|
| **SLIDE** | 흰 배경 + 큰 텍스트 | **정상** — 읽는 시간이다 | ❌ 모션 넣지 말 것 |
| **PHOTO** | 인물, 사물, 실사 사진 | **결함** — 영상이 멈춘 것처럼 보인다 | ✅ 반드시 모션 |
| **MIXED** | 인포그래픽, 일러스트+글 | 길면 결함 | ⚠️ 4초 이상일 때만 |

슬라이드에 카메라를 움직이면 **글자가 흔들려서 읽기 나빠집니다.**
실제로 63.5~68.0초(슬라이드)에 모션을 넣었다가 반려했습니다(§6-D).

### 2.2 분류 공식 (변경 금지)

```python
# 320x180 축소 프레임 기준
flat = (국소표준편차 < 2.0 인 화소 비율)   # 평평한 면적 = 단색 배경 비율
uc   = (24단계 양자화 후 고유 색 수)        # 색 다양성

def kind(frame):
    if flat > 0.62 and uc < 55:  return "SLIDE"   # 넓은 단색 + 색 적음
    if flat < 0.45 or  uc > 80:  return "PHOTO"   # 질감 많음 or 색 많음
    return "MIXED"
```

> ⚠️ **이 임계값을 임의로 바꾸지 마십시오.**
> 롱폼 22블록 + 추가 7구간, 총 29구간에서 검증된 값입니다.
> 바꾸면 과거 판정과 비교가 성립하지 않습니다.

### 2.3 실제 분포 (롱폼 v14 · 참고선)

| | flat | uc |
|---|---|---|
| SLIDE 실측 | 0.73 ~ 0.86 | 31 ~ 53 |
| PHOTO 실측 | 0.37 ~ 0.79 | 99 ~ 271 |
| MIXED 실측 | 0.60 ~ 0.90 | 55 ~ 73 |

**`uc` 가 100 을 넘으면 거의 확실히 사진입니다.** 가장 빠른 눈대중 기준입니다.

## 3. STEP 2 — 소재 기하 측정 (잘림 방지)

### 3.1 왜 필요한가

**"모든 컷을 10% 확대" 같은 일괄 값은 반드시 사고를 냅니다.**

피사체가 화면 가장자리에 붙어 있으면 조금만 확대해도 잘립니다.
롱폼 46초 구간이 정확히 그랬습니다.

| 구간 | 좌 여백 | 우 여백 | 안전 최대 배율 |
|---|---|---|---|
| **44.1-50.9 (46초 구간)** | **0.2%** | 13.7% | **1.0347** ← 확대 여력 3.5% 뿐 |
| 70.5-80.3 | 1.9% | 0.2% | 1.0583 |
| 153.1-157.9 | 22.8% | 24.7% | 1.2787 |
| 179.5-183.9 | 11.7% | 12.0% | 1.0961 |
| 375.5-405.1 | 9.1% | 17.3% | 1.2165 |

같은 영상 안에서도 안전 배율이 **1.03 ~ 1.28** 로 8배 넘게 차이납니다.
**소재를 보지 않고 정한 파라미터는 사고를 만듭니다.**

### 3.2 측정 절차

1. 구간에서 **13장**을 균등 샘플링
2. 각 장에서 **잉크 경계상자(ink bbox)** 를 구한다
   - Sobel 경계강도 > 14.0 인 화소를 "내용"으로 본다
   - 행/열 누적 프로파일에서 전체의 0.20% 미만인 줄은 잡음으로 버린다
3. 13장 bbox 의 **합집합** 을 취한다 (한 장이라도 잘리면 안 되므로)
4. 팬 이동폭을 고려해 안전 최대 배율을 역산한다

```python
def max_zoom_for(bbox, pan_span):
    px = pan_span; py = pan_span * 0.6      # 세로 팬은 가로의 60%
    x0, y0, x1, y1 = bbox                    # 0~1 정규화
    need_w = 2.0 * max(abs(0.5 - px - x0), abs(x1 - (0.5 + px)))
    need_h = 2.0 * max(abs(0.5 - py - y0), abs(y1 - (0.5 + py)))
    return 1.0 / max(need_w, need_h)
```

5. **적용 배율 = min(전역 상한 1.10, 측정된 안전 배율)**

### 3.3 팬 방향 결정

```python
# 여백이 넓은 쪽을 "버린다" — 좁은 쪽으로는 갈 수 없다
if abs(L - R) < 0.010:  방향 = drift_in / drift_out   # 좌우 대칭 → 줌만
else:                   방향 = drift_right if L > R else drift_left
```

## 4. STEP 3 — 구간 확정 (경계 설정)

### 4.1 함정: 화면이 바뀌는 방식은 2가지다

| 사건 | 화면 | 처리 |
|---|---|---|
| **컷(cut)** | 완전히 다른 화면으로 전환 | 여기서 **끊어야 한다** |
| **요소 등장** | 같은 화면에 항목 하나가 나타남 | 끊으면 **안 된다** |

인접 프레임 화소차 하나로는 **둘을 구분할 수 없습니다.**

실제 사례 — 47.000초 지점:

```
인접 프레임차 17.96  (임계 12.0 초과)  →  1차 판정: "컷"   ❌ 오판
```

### 4.2 해법: 두 번째 지표를 도입한다

**기준 프레임(±0.60초) 대비 누적 화소차**로 재측정합니다.

```
46.20초 기준 프레임과 비교:
  44.00 → 21.6      45.00 → 22.6
  46.00 →  4.7  ★   47.00 →  5.5  ★   48.00 →  5.5  ★   50.00 →  6.2  ★
  51.00 → 55.2  ← 진짜 컷
```

46.0~50.5 는 전부 **같은 화면**입니다. 47.00 은 그 위에 요소 하나가 나타난 것뿐입니다.

```python
ADJ_TOL  = 12.0   # 인접차 — "후보"만 만든다
SAME_TOL = 25.0   # 기준 대비 누적차 — 이 아래면 "같은 화면"

acc = |frame(t + 0.60) - frame(t - 0.60)|.mean()
is_cut = (acc >= SAME_TOL)
```

> **규칙: 인접차는 후보 생성용으로만 쓴다. 컷 확정은 반드시 누적차로 한다.**

### 4.3 경계는 컷만이 아니다

이미 모션을 넣은 블록의 **경계도 벽**입니다. 넘어가면 이중 적용됩니다.

```python
lo = max([lo] + [끝 for 시작, 끝 in 기처리구간 if 끝 <= a + 0.05])
hi = min([hi] + [시작 for 시작, 끝 in 기처리구간 if 시작 >= b - 0.05])
```

### 4.4 컷이 없어도 유형이 바뀌면 자른다 ★

**가장 놓치기 쉬운 규칙입니다.**

70.400초에는 컷이 없습니다. 그러나 콘텐츠 유형이 바뀝니다.

```
63.5 ~ 68.0   SLIDE  (flat 0.73 / uc  53)   정지가 정상
70.5 ~ 78.0   PHOTO  (flat 0.79 / uc 141)   정지가 결함
```

이 둘을 **한 계획으로 렌더하면 실패합니다.** 실제로 실패했습니다(§6-D).

> **규칙: 컷 경계 + 기처리 블록 경계 + 콘텐츠 유형 경계 — 3가지 모두를 벽으로 삼는다.**

## 5. STEP 5 — 이중 검수 (기계 + 눈)

### 5.1 게이트 3종 — 전부 통과해야 한다

| 게이트 | 무엇을 보는가 | 통과 조건 |
|---|---|---|
| **T-1 잘림** | 소재 밖을 샘플링했는가 | 가장자리 유지율 ≥ 0.90 |
| **T-2 정지** | 완전히 멈춘 프레임이 있는가 | **1.5초(7.5프레임) 연속** 으로 화소차 < 0.35 인 구간 = 0 |
| **T-3 급변** | 이동이 너무 빠른가 | 초당 이동 ≤ 16.0px |
| **★T-4 저모션** | **충분히 움직이는가** | **2초 광류 p95 중앙값 ≥ 1.5px** |

**T-4 가 이번에 새로 만든 게이트입니다.** 이것이 없어서 46초를 놓쳤습니다.

### 5.2 T-4 의 임계 1.5px 은 어디서 나왔는가 (지어낸 값이 아님)

엔진 설계 상수에서 **역산**했습니다.

```
2초 동안의 줌  = ZOOM_RATE 0.009 × 2 = 1.8%  → 320px 폭 기준 가장자리 이동 ≈ 2.9px
2초 동안의 팬  = PAN_RATE  0.0055 × 2 = 1.1% → 320px 폭 기준 이동         ≈ 3.5px
⇒ 엔진이 정상 작동한 구간은 2초 p95 가 3~5px 이어야 한다
```

**실측 검증**: 롱폼 807개 측정점의 중앙값 = **3.231px** — 설계값과 일치했습니다.

```
1.5px = 설계 기대치의 절반 미만 = "엔진이 걸리지 않았다"
```

### 5.3 T-2 판정 시 주의 — 1프레임은 정지가 아니다

렌더러 자체 검사는 **1프레임이라도** 임계 미만이면 경고를 냅니다. 이는 **과보수적**입니다.

**정본 판정은 "1.5초(7.5프레임) 연속"입니다.**

실제 사례 — 70.5-80.3초 구간(Y02):

```
렌더러 자체 검사 : 48개 측정점 중 1개가 0.3397 (임계 0.35 를 0.0103 차이로 스침) → 경고
정본 판정        : 연속 1프레임(0.2초)뿐 → 정지 ★0건★
기승인 29블록 대조: t2_min p10 = 0.531, 0.40 미만이 이미 2건 (승인된 것)
⇒ 수용
```

> **규칙: 렌더러 경고는 "확인하라"는 신호이지 "실패"가 아니다.**
> **판정은 반드시 정본 도구(1.5초 연속 규칙)로 한다.**

### 5.4 눈 검수 — 비전 모델 사용 시 필수 주의 ★

**프레임을 여러 장 따로 넘기면 안 됩니다.**

실제로 46초 구간 검증에서 46.0s / 48.0s / 50.0s 세 장을 넘겼더니
**세 장 모두 "MOTION VISIBLE: NO"** 라는 답이 돌아왔습니다.

그런데 화소 실측은 정반대였습니다.

| 46초 구간 2초 이동량 | 개선 전 | 개선 후 |
|---|---|---|
| 45.0 → 47.0초 | 1.27px | **4.08px** (3.2배) |
| 47.0 → 49.0초 | 1.60px | **7.47px** (4.7배) |

응답을 확인하니 **3장이 각각 독립 응답으로 처리**되어 있었습니다.
모델은 세 장을 나란히 놓고 본 적이 없습니다.
**"동일하다"는 진술은 비교의 결과가 아니라 추측이었습니다.**

> **규칙: 비교 판정을 모델에게 맡기지 말고, 비교 결과 자체를 한 장의 이미지로 구워서 넘긴다.**
> 차분맵(frame difference heatmap)을 개선 전/후 2행으로 배치하면
> 모델은 한 이미지 안에서 비교할 수밖에 없습니다.
> 이 방식으로 다시 물으니 **"MOTION INCREASED: YES"** 로 정확히 답했습니다.

## 6. 실패 사례 4건 — 그대로 반복하지 마십시오

### A. 인접 화소차만으로 컷을 판정 → 같은 화면을 두 동강

47.000초의 인접차 17.96 을 컷으로 오판. 실제로는 요소 등장.
**→ 기준 프레임 대비 누적차(§4.2)로 재판정해야 함**

### B. 이미 처리한 구간을 다시 후보로 집계

225.5-227.5초가 저모션으로 잡혔습니다. 그런데 그 구간은 **이미 모션이 들어간 블록 내부**였습니다.

```
해당 블록(215.6-240.4) 내부 분포:  min 1.498 · p50 2.772 · 1.5px 미만 비율 2.2%
다른 정상 블록:  B07 min 1.503 / B12 min 2.074 / B20 min 2.406
```

임계 1.500 을 **0.002px** 차이로 스친 **사인파의 골짜기**였습니다.
모션은 사인파이므로 골짜기에서 느려지는 것이 설계상 당연합니다.

**→ 기처리 구간과 겹치는 후보는 먼저 제외한다**
**→ 이상치를 봤으면 "고칠 것"이 아니라 "측정 방식 탓인지"부터 묻는다**

### C. 안전 구간이 기존 블록을 침범

컷 간격이 넓어 안전 구간이 56.50-80.30 까지 벌어져 기존 블록 3개와 겹쳤습니다.
**→ 기존 블록 경계도 벽으로 삼는다 (§4.3)**

### D. SLIDE + PHOTO 를 한 계획으로 렌더 ★가장 값비싼 실패

63.50-80.30(16.8초)을 통째로 렌더 → **T-2 정지 5건, 광류 2.114 로 실패.**

원인 2가지가 동시에 작용했습니다.
1. 구간이 길어 진폭이 희석됨 (scale 0.35 까지 축소됨)
2. **정지가 정상인 슬라이드에까지 카메라가 움직임**

**→ SLIDE 부분(63.5-68.0)을 잘라내고 PHOTO 부분(70.5-80.3, 9.8초)만 재렌더**
**→ 결과: T-2 5건 → 1건, 광류 2.114 → 2.464 로 개선**

### 8.1 남은 2건 5.0초(1.2%) 의 정체 — 둘 다 "고칠 것"이 아니다

**(a) 225.5-227.5초 — 오탐**

사인파의 골짜기였습니다. 상세는 §6-B.

**(b) 76.0-79.0초 — 소재의 구조적 제약 (측정은 정확함)**

광류 p95 가 0.895px 로 임계 1.5px 에 미달합니다.
**"안 움직인 것"인지 "더 못 움직이는 것"인지**를 가르기 위해
**서로 다른 두 방법**으로 교차 검산했습니다.

| 방법 | 측정 해상도 | 결과 |
|---|---|---|
| Farneback 광류 p95 | 320px 폭 | **0.895px** |
| 위상상관 평행이동 | 1280px 폭 → 320 환산 | **0.897px** |

**소수점 셋째 자리까지 일치했습니다.** 측정 오류가 아니라 실제 값입니다.

그런데 **원본 해상도(1280px) 기준 실제 이동량**은 이렇습니다.

| 창 | 개선 전 | 개선 후 | 배율 |
|---|---|---|---|
| 74.0→76.0s | 1.66px | **4.50px** | 2.7배 |
| 76.0→78.0s | 1.20px | **3.08px** | 2.6배 |
| 77.0→79.0s | 0.60px | **3.18px** | **5.3배** |

**사람이 보는 1280px 화면에서는 3.08~4.50px 이동하고 있습니다.**
그럼에도 임계를 못 넘는 이유는 소재의 여백입니다.

```
좌 여백 1.9%  ·  우 여백 0.2%   →  확대 여력 5.8%
안전 최대 배율 zmax_safe = 1.0583   (전역 상한 1.10 이 아니라 소재가 정한 값)
⇒ 팬으로 이동할 수 있는 폭 자체가 물리적으로 좁다
```

**더 키우면 우측 잉크가 잘립니다(여백 0.2%).**
**잘림은 정지보다 나쁜 결함입니다.** 따라서 여기서 멈추는 것이 옳습니다.

⇒ **결론: 실질 잔여 결함 0건.** 2건 모두 조치 대상이 아닙니다.

> **여기서 얻은 규칙**: 게이트 미달을 봤을 때 곧바로 재렌더하지 마십시오.
> **① 다른 방법으로 교차 검산**해 측정이 맞는지 보고,
> **② 소재의 물리적 한계인지**를 확인하십시오.
> 한계인데 억지로 밀어붙이면 정지 대신 잘림이 생깁니다.

>
> 이 개정이 필요했던 이유는 단순합니다. 우리는 8개월 동안 **"AI 에게 카메라 무빙을 말로 설명"**
> 하고 있었고, 그것은 원리적으로 불가능한 일이었습니다. 문제는 프롬프트 문장력이 아니라
> **AI 에게 공간을 알려주는 채널이 없었다는 것**이었습니다.

### ⑬ 컷 내부 모션 의무 + 원근 시차 필수 (CEO-51 근거)

대표님 지시 원문:

> "맞네. **컷 안에서 움직여야 하네!** 그리고 **정지 구간이 없어요.** 맞아요. **원근 시차**도
> 그렇고요. 벽을 통과하고, 바닥 슬래브의 아랫면이 보이는 것처럼 우리도 우리의 상황에 맞게
> 표현을 했어야 해요."

따라서 모든 컷은 다음 3개를 **동시에** 만족해야 합니다.

| 요건 | 정의 | 판정 방법 |
|---|---|---|
| **컷 내부 모션** | 전환(이음새)이 아니라 **컷 한가운데**에서 화면이 변한다 | 컨택트시트에서 같은 컷의 첫/중/끝 프레임의 **구도가 다른가** |
| **원근 시차** | 근거리 물체가 원거리 물체보다 **빠르게** 이동하고, 물체가 **서로를 가린다** | 컨택트시트에서 **가려짐이 벗겨지는가**(뒤에 있던 것이 새로 드러나는가) |
| **정지 구간** | 컷 시작부에 카메라가 멈춘 구간이 있다 | `hold_frac` 0.15~0.35 (R2: 최소 29프레임) |

**금지.** 켄번즈 확대(zoompan)만으로 위 3개를 만족시킬 수 없습니다.
확대는 아핀 변환이고, 아핀 변환에는 **가려짐 변화가 원리적으로 없습니다.**

### ⑭ 색상 코딩 3D 프리비즈를 Video-to-Video 구조 레퍼런스로 쓴다

#### ⑭-1. 원리 — 무엇이 문제였고 무엇이 해법인가

AI 비디오에는 두 근본 결함이 있습니다.

1. **카메라 무빙을 제어할 수 없다** — 말로 아무리 정밀하게 써도 모델이 제멋대로 움직입니다
2. **피사체가 모핑된다** — 프레임이 진행되며 형태가 붕괴합니다

실패 사례(튜토리얼 원문 · 이 정도로 정밀하게 써도 실패합니다):

```
The camera starts behind him at eye level, then sweeps around his right side,
rising as it circles about ninety degrees, tilting down while it passes overhead,
accelerating hard through the turn, then dropping low behind his back and
settling just above the grass, tilted up.
```

**해법.** 카메라 무빙과 공간을 **말로 전달하지 않고, 3D 로 계산해서 영상으로 전달합니다.**

```
Blender (단순 도형 + 원색)  ──렌더──▶  프리비즈 mp4
                                          │  @Video1 = 구조(카메라·원근·타이밍)
실사 plate ───────────────────────────────┤  @Image1 = 질감(빛·재질·환경)
                                          ▼
                                  AI 생성기 (Video-to-Video)
                                          ▼
                            3D 가 계산한 완벽한 원근 + 실사 질감
```

**핵심.** AI 는 "상상"하지 않습니다. 3D 소프트웨어가 **계산한** 원근법과 무빙을 그대로
유지한 채 **질감만 교체**합니다. 그래서 패럴랙스가 계산으로 보장됩니다.

#### ⑭-2. 3대 규칙 (튜토리얼이 "가장 중요"라고 명시)

1. **피사체는 단순 도형으로.** 디테일 모델링은 AI 실사 생성과 **간섭**해 품질을 떨어뜨립니다.
2. **피사체는 색으로 구분한다.** 마젠타/시안/옐로/레드 등 **채도 높은 원색**.
3. **역할 구분을 확실하게.** 한 색에 두 역할을 겹치지 않습니다.

> 3번이 가장 자주 위반됩니다. "이 색이 무엇이 될지"를 프롬프트에서 1:1 로 지정해야
> AI 가 색을 역할로 읽습니다. 색이 겹치면 AI 가 두 물체를 하나로 합칩니다.

#### ⑭-3. 프리비즈 렌더 설정 — 반드시 이 값으로 (실측 근거)

프리비즈는 **발광(emission) 원색**이므로 **광선 추적이 필요 없습니다.** 따라서:

```python
S.render.engine = 'CYCLES'; S.cycles.device = 'CPU'
S.cycles.samples = 1              # 발광이므로 1샘플로 충분
S.cycles.max_bounces = 0          # 반사·굴절 없음
S.cycles.use_denoising = False    # 노이즈가 없으므로 불필요
S.render.resolution_x = 832; S.render.resolution_y = 468
```

**실측 속도 계층 (같은 샌드박스 · 2코어 · RAM 3GB · GPU 없음):**

| 설정 | 속도 | 판정 |
|---|---|---|
| 1920x1080 / 48spp / 일반 씬 | 115초 초과 (타임아웃) | ✗ |
| 1280x720 / 8spp / 발광 | **10.3 s/frame** (500초 = 34시간) | ✗ |
| **832x468 / 1spp / 발광** | **0.196 s/frame** (500초 = 약 40분) | **✓ 채택** |

**교훈.** 같은 엔진(Cycles CPU)인데 **52배** 차이가 납니다.
"Cycles 는 느리다"가 아니라 **"프리비즈에 불필요한 설정을 켜두면 느리다"** 였습니다.

**EEVEE 는 이 환경에서 불가합니다.** `EGL_BAD_MATCH` (GPU 없음) → llvmpipe 재시도 → OOM(3GB).
따라서 Cycles CPU + 위 설정이 **유일한 성립 경로**입니다.

#### ⑭-4. 프리비즈 세트 규칙 — 검은 구멍 방지

카메라가 배경 밖을 보면 프레임에 **검은 영역**이 생기고, AI 는 그것을 그대로 검게 재현합니다.

```
세트는 카메라 궤적보다 넉넉하게 세운다.
  바닥  16 x 12 m       (카메라 최대 반경의 2배 이상)
  벽    후면 + 좌 + 우, 높이 4.4 m
```

우리 v1 프리비즈에서 프레임 1·48 상단에 검은 구멍이 났고, 세트를 위 크기로 키워 해소했습니다.

#### ⑭-5. Video-to-Video 프롬프트 골격 (이 구조를 그대로 씁니다)

```
[1행] 실사 톤 + 장면 + 촬영 스타일. 한 컷 연속.

@Video1 is the CAMERA AND SPATIAL reference: follow its camera path, framing,
perspective and timing 1:1 frame for frame. Its coloured flat planes are position
markers for real objects, and its small red blocks are position markers for
glowing highlighted words.

@Image1 is the environment, lighting and texture reference: <plate 설명>.

Color-based proxy replacement:
  the magenta plane becomes <역할1>,
  the cyan plane becomes <역할2>,
  the yellow plane becomes <역할3>,
  the dark plane becomes <바닥>,
  the brown walls become <배경>,
  the red cylinder becomes <소품>,
  the three small red blocks become <강조 요소 + 그 움직임의 의미>.

[카메라 서술] The camera holds still at the start, then <무빙>, keeping true 3D
perspective parallax: the near <A> slides across frame faster than the far <B>,
and the <A>s occlude each other as the camera passes.

No text overlays, no captions, no subtitles.
```

**필수 5요소.** ① `@Video1 = CAMERA AND SPATIAL reference` 명시 ② `1:1 frame for frame`

**(a) 글자 PNG 는 반드시 RGBA · 배경 알파 0.**
불투명 검은 배경 PNG 를 그대로 emission 으로 붙이면 화면에 **검은 카드**가 나타나고,
AI 는 그것을 "검은 판"으로 해석합니다(4세대 pv4 에서 실제 발생).

**(b) 머티리얼 — 알파가 MixShader 를 구동해야 합니다.**

```python
def texflat(name, path):
    """emission material driven by an image texture -> the GLYPH becomes structure."""
    m = bpy.data.materials.new(name); m.use_nodes = True
    nt = m.node_tree; nt.nodes.clear()
    tc = nt.nodes.new('ShaderNodeTexCoord')
    tx = nt.nodes.new('ShaderNodeTexImage')
    tx.image = bpy.data.images.load(path)
    tx.interpolation = 'Closest'      # 글자 경계를 뭉개지 않는다
    tx.extension = 'EXTEND'
    e  = nt.nodes.new('ShaderNodeEmission'); e.inputs[1].default_value = 1.0
    tr = nt.nodes.new('ShaderNodeBsdfTransparent')
    mx = nt.nodes.new('ShaderNodeMixShader')
    o  = nt.nodes.new('ShaderNodeOutputMaterial')
    nt.links.new(tc.outputs['UV'],    tx.inputs['Vector'])
    nt.links.new(tx.outputs['Color'], e.inputs[0])
    nt.links.new(tx.outputs['Alpha'], mx.inputs[0])   # ★핵심: 알파가 믹스를 구동★
    nt.links.new(tr.outputs[0], mx.inputs[1])         # 0 -> 투명
    nt.links.new(e.outputs[0],  mx.inputs[2])         # 1 -> 발광 글자
    nt.links.new(mx.outputs[0], o.inputs[0])
    m.blend_method = 'BLEND'
    return m

def add_tex(name, loc, sc, path):
    bpy.ops.mesh.primitive_plane_add(size=2, location=loc)
    ob = bpy.context.object; ob.scale = sc; ob.name = name
    ob.data.materials.append(texflat(name, path))
    return ob
```

| 스케일 | `(0.30*(1+0.9v), 0.15*(1+0.9v), 1.0)` | 2:1 글자 비율 유지 |

**(d) 프롬프트에 ⑭-5 의 `NOT a marker` 선언을 반드시 병행합니다.**
구조(UV 텍스처)와 선언(프롬프트) **둘 다** 있어야 합니다. 하나만으로는 해소되지 않습니다.

### 교훈 165 — 구조로 전달하되, 그것이 "교체 대상"인지 "최종물"인지도 전달해야 한다

**교훈 162 의 완결편입니다.**

교훈 162 에서 우리는 *"구조로 전달되지 않은 것은 통제되지 않는다"* 를 배웠습니다.
그래서 한글 글자를 UV 텍스처로 프리비즈에 심었습니다 — **구조로 전달했습니다.**
그런데도 위험이 남았습니다. 왜냐하면:

```
프리비즈에 들어간 것은 AI 에게 기본적으로 전부 "프록시(교체 대상)" 로 해석된다.
그것이 색깔 평면이든, 원기둥이든, 한글 글자든 마찬가지다.
```

색상 코딩 프리비즈의 **전제 자체가 "이 도형들은 진짜가 아니다, 바꿔라"** 이기 때문입니다.
따라서 글자를 아무리 정확히 그려 넣어도, AI 는 그것마저 "무언가로 바꿔야 할 표식"으로 읽습니다.

**처방 — 프롬프트에서 예외를 명시적으로 선언합니다.**

```
The RED KOREAN TEXT visible in @Video1 is NOT a marker — it is the actual final text
and must be reproduced EXACTLY as the identical Korean word, same glyphs, same position,
same rotation, same scale, frame for frame.
Preserve the Korean characters exactly as shown in @Video1 — do not translate,
do not substitute Latin letters, do not invent new words.
```

**검증.** BEFORE `Report` / `Renes` (오철자 영문) → AFTER **「조율자」** (정확한 한글).
동일 모델·동일 설정·동일 plate. 바뀐 것은 **프리비즈의 글자 텍스처 + 이 두 문장**뿐입니다.

**일반화.**

| 프리비즈 안의 요소 | AI 에게 무엇인가 | 프롬프트 처리 |
|---|---|---|
| 색깔 평면·원기둥·큐브 | **프록시** — 실물로 교체 | `the magenta plane becomes …` |
| 한글 글자·로고·수치 | **최종물** — 그대로 보존 | `… is NOT a marker — it is the actual final …` |

> 구조로 전달하는 것만으로는 부족합니다.
> **"이것은 바꿔라" 와 "이것은 그대로 둬라" 를 갈라서 말해야** 통제가 완성됩니다.

### 교훈 166 — GenTeam 에이전트는 본문의 `@이름` 텍스트로는 깨어나지 않는다

**증상.** 전담 채널 `previz-3d-pipeline` 에 교본과 과업을 2회 발송했고 둘 다 `status: ok` 였는데,
**에이전트 회신이 하나도 오지 않았습니다.** 발송 실패가 아니었습니다.

**원인.** 채널을 폴링해 보니 제 메시지 바로 뒤에 시스템 메시지가 붙어 있었습니다.

```json
{"kind": "system_message",
 "content": "The agents here reply only when @mentioned. @ a teammate to get an answer.",
 "metadata": {"digital_employee": {"event": "agents_mentions_only", "importance": "high"}}}
```

본문에 `@3D Motion Director …` 라고 **텍스트로** 썼지만, 그것은 멘션으로 파싱되지 않습니다.
메시지는 채널에 남았지만 **에이전트를 깨우는 이벤트가 발생하지 않았습니다.**

**처방.** `gsk genteam send` 의 **`--mentions` 플래그**로 agent_id 를 넘깁니다.

```bash
gsk genteam send --args-file order.json \
  --mentions agent_pt2dn9rvtxrc agent_fmzqbh39p4k3 agent_4gettwpxdxp6
```

- 여러 명을 **공백으로 나열**할 수 있습니다(멤버 추가와 달리 1명씩 나눌 필요 없음).
- 응답의 `data.mentions` 배열에 3명이 들어갔는지로 확인합니다.
- 캐노니컬 토큰 `@[name](id)` 은 **자동으로 본문 앞에 붙습니다.** 직접 쓰지 마십시오.
- 대상은 **이미 채널 멤버**여야 합니다.

**검증.** 재발주 mid `3044026` · `mentions` 3명 인식 · `status ok`.

> 발송 성공(`status: ok`)은 **도달**의 증거일 뿐 **발동**의 증거가 아닙니다.
> 팀에 일을 시킨 뒤에는 반드시 **채널을 폴링해 시스템 메시지를 확인**합니다.
> 경영자가 "지시했다"고 믿는 것과 "지시가 전달됐다"는 것은 다릅니다.
