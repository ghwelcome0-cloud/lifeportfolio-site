## 0. 이 문서가 존재하는 이유 — 한 번 크게 틀렸기 때문

직전 보고에서 우리는 **"정지 화면 60.2% → 0.0%"** 라고 보고했습니다.
그 수치 자체는 사실입니다. 정본 검사 도구가 실제로 0건을 반환했습니다.

그런데 대표님이 이렇게 지적하셨습니다.

> **"46초 구간에 나오는 영상이 일시정지 되는 모습이 끊김이 있어요."**

재조사 결과 **도구가 46초 구간을 애초에 검사하지 않았다**는 것이 밝혀졌습니다.

| | 내용 |
|---|---|
| 검사 규칙 | 프레임 간 화소차 **< 0.35** 이면 "정지" |
| 46초 구간 실제 | 아주 미세하게 움직여서 **0.35 를 간신히 넘김** |
| 결과 | 기계 판정 = "움직임" → **후보 목록에 아예 오르지 않음** |
| 사람 눈 | **"멈춰 있다"** |

**"0건"은 "결함이 없다"가 아니라 "검사 대상이 아니었다"는 뜻이었습니다.**

새 자(尺)로 다시 재니 같은 성질의 결함이 **8건 48.5초, 본편의 12.0%** 있었습니다.
46초는 그중 **1건**일 뿐이었고, 가장 큰 것은 **375.5~405.0초 — 영상 마지막 30초 전체**였습니다.
엔딩이 통째로 정지처럼 보이고 있었는데, 우리는 그것을 "0건"이라고 보고하고 있었습니다.

> 규칙을 지키는 것보다 **왜 그 규칙이 생겼는지 아는 것**이 중요합니다.
> 근거를 모르면 상황이 조금만 달라져도 같은 사고가 반복됩니다.

## 1. 제작 규칙 — 5단계 (이 순서를 바꾸지 마십시오)

```
 STEP 1  콘텐츠 유형 분류      → 어디에 모션이 "필요한가"를 정한다
 STEP 2  소재 기하 측정        → 어디까지 확대해도 "안 잘리는가"를 정한다
 STEP 3  구간 확정             → 어디서 어디까지가 "한 화면인가"를 정한다
 STEP 4  렌더                  → 만든다
 STEP 5  이중 검수 (기계 + 눈) → 됐는지 판정한다
```

각 단계는 **앞 단계의 산출물이 있어야** 시작할 수 있습니다.
순서를 건너뛰면 반드시 되돌아옵니다 (§6 의 실패 사례 4건이 전부 그렇습니다).

## 2. STEP 1 — 콘텐츠 유형 분류 (가장 중요)

### 2.1 왜 유형부터 나누는가

**모든 정지가 결함이 아닙니다.**

| 유형 | 화면 예 | 정지했을 때 | 조치 |
|---|---|---|---|
| **SLIDE** | 흰 배경 + 큰 텍스트 | **정상** — 읽는 시간이다 | ❌ 모션 넣지 말 것 |
| **PHOTO** | 인물, 사물, 실사 사진 | **결함** — 영상이 멈춘 것처럼 보인다 | ✅ 반드시 모션 |
| **MIXED** | 인포그래픽, 일러스트+글 | 길면 결함 | ⚠️ 4초 이상일 때만 |

슬라이드에 카메라를 움직이면 **글자가 흔들려서 읽기 나빠집니다.**
실제로 63.5~68.0초(슬라이드)에 모션을 넣었다가 반려했습니다(§6-D).

### 2.2 분류 공식 (변경 금지)

```python
# 320x180 축소 프레임 기준
flat = (국소표준편차 < 2.0 인 화소 비율)   # 평평한 면적 = 단색 배경 비율
uc   = (24단계 양자화 후 고유 색 수)        # 색 다양성

def kind(frame):
    if flat > 0.62 and uc < 55:  return "SLIDE"   # 넓은 단색 + 색 적음
    if flat < 0.45 or  uc > 80:  return "PHOTO"   # 질감 많음 or 색 많음
    return "MIXED"
```

> ⚠️ **이 임계값을 임의로 바꾸지 마십시오.**
> 롱폼 22블록 + 추가 7구간, 총 29구간에서 검증된 값입니다.
> 바꾸면 과거 판정과 비교가 성립하지 않습니다.

### 2.3 실제 분포 (롱폼 v14 · 참고선)

| | flat | uc |
|---|---|---|
| SLIDE 실측 | 0.73 ~ 0.86 | 31 ~ 53 |
| PHOTO 실측 | 0.37 ~ 0.79 | 99 ~ 271 |
| MIXED 실측 | 0.60 ~ 0.90 | 55 ~ 73 |

**`uc` 가 100 을 넘으면 거의 확실히 사진입니다.** 가장 빠른 눈대중 기준입니다.

## 3. STEP 2 — 소재 기하 측정 (잘림 방지)

### 3.1 왜 필요한가

**"모든 컷을 10% 확대" 같은 일괄 값은 반드시 사고를 냅니다.**

피사체가 화면 가장자리에 붙어 있으면 조금만 확대해도 잘립니다.
롱폼 46초 구간이 정확히 그랬습니다.

| 구간 | 좌 여백 | 우 여백 | 안전 최대 배율 |
|---|---|---|---|
| **44.1-50.9 (46초 구간)** | **0.2%** | 13.7% | **1.0347** ← 확대 여력 3.5% 뿐 |
| 70.5-80.3 | 1.9% | 0.2% | 1.0583 |
| 153.1-157.9 | 22.8% | 24.7% | 1.2787 |
| 179.5-183.9 | 11.7% | 12.0% | 1.0961 |
| 375.5-405.1 | 9.1% | 17.3% | 1.2165 |

같은 영상 안에서도 안전 배율이 **1.03 ~ 1.28** 로 8배 넘게 차이납니다.
**소재를 보지 않고 정한 파라미터는 사고를 만듭니다.**

### 3.2 측정 절차

1. 구간에서 **13장**을 균등 샘플링
2. 각 장에서 **잉크 경계상자(ink bbox)** 를 구한다
   - Sobel 경계강도 > 14.0 인 화소를 "내용"으로 본다
   - 행/열 누적 프로파일에서 전체의 0.20% 미만인 줄은 잡음으로 버린다
3. 13장 bbox 의 **합집합** 을 취한다 (한 장이라도 잘리면 안 되므로)
4. 팬 이동폭을 고려해 안전 최대 배율을 역산한다

```python
def max_zoom_for(bbox, pan_span):
    px = pan_span; py = pan_span * 0.6      # 세로 팬은 가로의 60%
    x0, y0, x1, y1 = bbox                    # 0~1 정규화
    need_w = 2.0 * max(abs(0.5 - px - x0), abs(x1 - (0.5 + px)))
    need_h = 2.0 * max(abs(0.5 - py - y0), abs(y1 - (0.5 + py)))
    return 1.0 / max(need_w, need_h)
```

5. **적용 배율 = min(전역 상한 1.10, 측정된 안전 배율)**

### 3.3 팬 방향 결정

```python
# 여백이 넓은 쪽을 "버린다" — 좁은 쪽으로는 갈 수 없다
if abs(L - R) < 0.010:  방향 = drift_in / drift_out   # 좌우 대칭 → 줌만
else:                   방향 = drift_right if L > R else drift_left
```

## 4. STEP 3 — 구간 확정 (경계 설정)

### 4.1 함정: 화면이 바뀌는 방식은 2가지다

| 사건 | 화면 | 처리 |
|---|---|---|
| **컷(cut)** | 완전히 다른 화면으로 전환 | 여기서 **끊어야 한다** |
| **요소 등장** | 같은 화면에 항목 하나가 나타남 | 끊으면 **안 된다** |

인접 프레임 화소차 하나로는 **둘을 구분할 수 없습니다.**

실제 사례 — 47.000초 지점:

```
인접 프레임차 17.96  (임계 12.0 초과)  →  1차 판정: "컷"   ❌ 오판
```

### 4.2 해법: 두 번째 지표를 도입한다

**기준 프레임(±0.60초) 대비 누적 화소차**로 재측정합니다.

```
46.20초 기준 프레임과 비교:
  44.00 → 21.6      45.00 → 22.6
  46.00 →  4.7  ★   47.00 →  5.5  ★   48.00 →  5.5  ★   50.00 →  6.2  ★
  51.00 → 55.2  ← 진짜 컷
```

46.0~50.5 는 전부 **같은 화면**입니다. 47.00 은 그 위에 요소 하나가 나타난 것뿐입니다.

```python
ADJ_TOL  = 12.0   # 인접차 — "후보"만 만든다
SAME_TOL = 25.0   # 기준 대비 누적차 — 이 아래면 "같은 화면"

acc = |frame(t + 0.60) - frame(t - 0.60)|.mean()
is_cut = (acc >= SAME_TOL)
```

> **규칙: 인접차는 후보 생성용으로만 쓴다. 컷 확정은 반드시 누적차로 한다.**

### 4.3 경계는 컷만이 아니다

이미 모션을 넣은 블록의 **경계도 벽**입니다. 넘어가면 이중 적용됩니다.

```python
lo = max([lo] + [끝 for 시작, 끝 in 기처리구간 if 끝 <= a + 0.05])
hi = min([hi] + [시작 for 시작, 끝 in 기처리구간 if 시작 >= b - 0.05])
```

### 4.4 컷이 없어도 유형이 바뀌면 자른다 ★

**가장 놓치기 쉬운 규칙입니다.**

70.400초에는 컷이 없습니다. 그러나 콘텐츠 유형이 바뀝니다.

```
63.5 ~ 68.0   SLIDE  (flat 0.73 / uc  53)   정지가 정상
70.5 ~ 78.0   PHOTO  (flat 0.79 / uc 141)   정지가 결함
```

이 둘을 **한 계획으로 렌더하면 실패합니다.** 실제로 실패했습니다(§6-D).

> **규칙: 컷 경계 + 기처리 블록 경계 + 콘텐츠 유형 경계 — 3가지 모두를 벽으로 삼는다.**

## 5. STEP 5 — 이중 검수 (기계 + 눈)

### 5.1 게이트 3종 — 전부 통과해야 한다

| 게이트 | 무엇을 보는가 | 통과 조건 |
|---|---|---|
| **T-1 잘림** | 소재 밖을 샘플링했는가 | 가장자리 유지율 ≥ 0.90 |
| **T-2 정지** | 완전히 멈춘 프레임이 있는가 | **1.5초(7.5프레임) 연속** 으로 화소차 < 0.35 인 구간 = 0 |
| **T-3 급변** | 이동이 너무 빠른가 | 초당 이동 ≤ 16.0px |
| **★T-4 저모션** | **충분히 움직이는가** | **2초 광류 p95 중앙값 ≥ 1.5px** |

**T-4 가 이번에 새로 만든 게이트입니다.** 이것이 없어서 46초를 놓쳤습니다.

### 5.2 T-4 의 임계 1.5px 은 어디서 나왔는가 (지어낸 값이 아님)

엔진 설계 상수에서 **역산**했습니다.

```
2초 동안의 줌  = ZOOM_RATE 0.009 × 2 = 1.8%  → 320px 폭 기준 가장자리 이동 ≈ 2.9px
2초 동안의 팬  = PAN_RATE  0.0055 × 2 = 1.1% → 320px 폭 기준 이동         ≈ 3.5px
⇒ 엔진이 정상 작동한 구간은 2초 p95 가 3~5px 이어야 한다
```

**실측 검증**: 롱폼 807개 측정점의 중앙값 = **3.231px** — 설계값과 일치했습니다.

```
1.5px = 설계 기대치의 절반 미만 = "엔진이 걸리지 않았다"
```

### 5.3 T-2 판정 시 주의 — 1프레임은 정지가 아니다

렌더러 자체 검사는 **1프레임이라도** 임계 미만이면 경고를 냅니다. 이는 **과보수적**입니다.

**정본 판정은 "1.5초(7.5프레임) 연속"입니다.**

실제 사례 — 70.5-80.3초 구간(Y02):

```
렌더러 자체 검사 : 48개 측정점 중 1개가 0.3397 (임계 0.35 를 0.0103 차이로 스침) → 경고
정본 판정        : 연속 1프레임(0.2초)뿐 → 정지 ★0건★
기승인 29블록 대조: t2_min p10 = 0.531, 0.40 미만이 이미 2건 (승인된 것)
⇒ 수용
```

> **규칙: 렌더러 경고는 "확인하라"는 신호이지 "실패"가 아니다.**
> **판정은 반드시 정본 도구(1.5초 연속 규칙)로 한다.**

### 5.4 눈 검수 — 비전 모델 사용 시 필수 주의 ★

**프레임을 여러 장 따로 넘기면 안 됩니다.**

실제로 46초 구간 검증에서 46.0s / 48.0s / 50.0s 세 장을 넘겼더니
**세 장 모두 "MOTION VISIBLE: NO"** 라는 답이 돌아왔습니다.

그런데 화소 실측은 정반대였습니다.

| 46초 구간 2초 이동량 | 개선 전 | 개선 후 |
|---|---|---|
| 45.0 → 47.0초 | 1.27px | **4.08px** (3.2배) |
| 47.0 → 49.0초 | 1.60px | **7.47px** (4.7배) |

응답을 확인하니 **3장이 각각 독립 응답으로 처리**되어 있었습니다.
모델은 세 장을 나란히 놓고 본 적이 없습니다.
**"동일하다"는 진술은 비교의 결과가 아니라 추측이었습니다.**

> **규칙: 비교 판정을 모델에게 맡기지 말고, 비교 결과 자체를 한 장의 이미지로 구워서 넘긴다.**
> 차분맵(frame difference heatmap)을 개선 전/후 2행으로 배치하면
> 모델은 한 이미지 안에서 비교할 수밖에 없습니다.
> 이 방식으로 다시 물으니 **"MOTION INCREASED: YES"** 로 정확히 답했습니다.

## 6. 실패 사례 4건 — 그대로 반복하지 마십시오

### A. 인접 화소차만으로 컷을 판정 → 같은 화면을 두 동강

47.000초의 인접차 17.96 을 컷으로 오판. 실제로는 요소 등장.
**→ 기준 프레임 대비 누적차(§4.2)로 재판정해야 함**

### B. 이미 처리한 구간을 다시 후보로 집계

225.5-227.5초가 저모션으로 잡혔습니다. 그런데 그 구간은 **이미 모션이 들어간 블록 내부**였습니다.

```
해당 블록(215.6-240.4) 내부 분포:  min 1.498 · p50 2.772 · 1.5px 미만 비율 2.2%
다른 정상 블록:  B07 min 1.503 / B12 min 2.074 / B20 min 2.406
```

임계 1.500 을 **0.002px** 차이로 스친 **사인파의 골짜기**였습니다.
모션은 사인파이므로 골짜기에서 느려지는 것이 설계상 당연합니다.

**→ 기처리 구간과 겹치는 후보는 먼저 제외한다**
**→ 이상치를 봤으면 "고칠 것"이 아니라 "측정 방식 탓인지"부터 묻는다**

### C. 안전 구간이 기존 블록을 침범

컷 간격이 넓어 안전 구간이 56.50-80.30 까지 벌어져 기존 블록 3개와 겹쳤습니다.
**→ 기존 블록 경계도 벽으로 삼는다 (§4.3)**

### D. SLIDE + PHOTO 를 한 계획으로 렌더 ★가장 값비싼 실패

63.50-80.30(16.8초)을 통째로 렌더 → **T-2 정지 5건, 광류 2.114 로 실패.**

원인 2가지가 동시에 작용했습니다.
1. 구간이 길어 진폭이 희석됨 (scale 0.35 까지 축소됨)
2. **정지가 정상인 슬라이드에까지 카메라가 움직임**

**→ SLIDE 부분(63.5-68.0)을 잘라내고 PHOTO 부분(70.5-80.3, 9.8초)만 재렌더**
**→ 결과: T-2 5건 → 1건, 광류 2.114 → 2.464 로 개선**

사인파의 골짜기였습니다. 상세는 §6-B.

**(b) 76.0-79.0초 — 소재의 구조적 제약 (측정은 정확함)**

광류 p95 가 0.895px 로 임계 1.5px 에 미달합니다.
**"안 움직인 것"인지 "더 못 움직이는 것"인지**를 가르기 위해
**서로 다른 두 방법**으로 교차 검산했습니다.

| 방법 | 측정 해상도 | 결과 |
|---|---|---|
| Farneback 광류 p95 | 320px 폭 | **0.895px** |
| 위상상관 평행이동 | 1280px 폭 → 320 환산 | **0.897px** |

**소수점 셋째 자리까지 일치했습니다.** 측정 오류가 아니라 실제 값입니다.

그런데 **원본 해상도(1280px) 기준 실제 이동량**은 이렇습니다.

| 창 | 개선 전 | 개선 후 | 배율 |
|---|---|---|---|
| 74.0→76.0s | 1.66px | **4.50px** | 2.7배 |
| 76.0→78.0s | 1.20px | **3.08px** | 2.6배 |
| 77.0→79.0s | 0.60px | **3.18px** | **5.3배** |

**사람이 보는 1280px 화면에서는 3.08~4.50px 이동하고 있습니다.**
그럼에도 임계를 못 넘는 이유는 소재의 여백입니다.

```
좌 여백 1.9%  ·  우 여백 0.2%   →  확대 여력 5.8%
안전 최대 배율 zmax_safe = 1.0583   (전역 상한 1.10 이 아니라 소재가 정한 값)
⇒ 팬으로 이동할 수 있는 폭 자체가 물리적으로 좁다
```

**더 키우면 우측 잉크가 잘립니다(여백 0.2%).**
**잘림은 정지보다 나쁜 결함입니다.** 따라서 여기서 멈추는 것이 옳습니다.

⇒ **결론: 실질 잔여 결함 0건.** 2건 모두 조치 대상이 아닙니다.

> **여기서 얻은 규칙**: 게이트 미달을 봤을 때 곧바로 재렌더하지 마십시오.
> **① 다른 방법으로 교차 검산**해 측정이 맞는지 보고,
> **② 소재의 물리적 한계인지**를 확인하십시오.
> 한계인데 억지로 밀어붙이면 정지 대신 잘림이 생깁니다.

> 하고 있었고, 그것은 원리적으로 불가능한 일이었습니다. 문제는 프롬프트 문장력이 아니라
> **AI 에게 공간을 알려주는 채널이 없었다는 것**이었습니다.

### ⑬ 컷 내부 모션 의무 + 원근 시차 필수 (CEO-51 근거)

대표님 지시 원문:

> "맞네. **컷 안에서 움직여야 하네!** 그리고 **정지 구간이 없어요.** 맞아요. **원근 시차**도
> 그렇고요. 벽을 통과하고, 바닥 슬래브의 아랫면이 보이는 것처럼 우리도 우리의 상황에 맞게
> 표현을 했어야 해요."

따라서 모든 컷은 다음 3개를 **동시에** 만족해야 합니다.

| 요건 | 정의 | 판정 방법 |
|---|---|---|
| **컷 내부 모션** | 전환(이음새)이 아니라 **컷 한가운데**에서 화면이 변한다 | 컨택트시트에서 같은 컷의 첫/중/끝 프레임의 **구도가 다른가** |
| **원근 시차** | 근거리 물체가 원거리 물체보다 **빠르게** 이동하고, 물체가 **서로를 가린다** | 컨택트시트에서 **가려짐이 벗겨지는가**(뒤에 있던 것이 새로 드러나는가) |
| **정지 구간** | 컷 시작부에 카메라가 멈춘 구간이 있다 | `hold_frac` 0.15~0.35 (R2: 최소 29프레임) |

**금지.** 켄번즈 확대(zoompan)만으로 위 3개를 만족시킬 수 없습니다.
확대는 아핀 변환이고, 아핀 변환에는 **가려짐 변화가 원리적으로 없습니다.**

### ⑭ 색상 코딩 3D 프리비즈를 Video-to-Video 구조 레퍼런스로 쓴다

#### ⑭-1. 원리 — 무엇이 문제였고 무엇이 해법인가

AI 비디오에는 두 근본 결함이 있습니다.

1. **카메라 무빙을 제어할 수 없다** — 말로 아무리 정밀하게 써도 모델이 제멋대로 움직입니다
2. **피사체가 모핑된다** — 프레임이 진행되며 형태가 붕괴합니다

실패 사례(튜토리얼 원문 · 이 정도로 정밀하게 써도 실패합니다):

```
The camera starts behind him at eye level, then sweeps around his right side,
rising as it circles about ninety degrees, tilting down while it passes overhead,
accelerating hard through the turn, then dropping low behind his back and
settling just above the grass, tilted up.
```

**해법.** 카메라 무빙과 공간을 **말로 전달하지 않고, 3D 로 계산해서 영상으로 전달합니다.**

```
Blender (단순 도형 + 원색)  ──렌더──▶  프리비즈 mp4
                                          │  @Video1 = 구조(카메라·원근·타이밍)
실사 plate ───────────────────────────────┤  @Image1 = 질감(빛·재질·환경)
                                          ▼
                                  AI 생성기 (Video-to-Video)
                                          ▼
                            3D 가 계산한 완벽한 원근 + 실사 질감
```

**핵심.** AI 는 "상상"하지 않습니다. 3D 소프트웨어가 **계산한** 원근법과 무빙을 그대로
유지한 채 **질감만 교체**합니다. 그래서 패럴랙스가 계산으로 보장됩니다.

#### ⑭-2. 3대 규칙 (튜토리얼이 "가장 중요"라고 명시)

1. **피사체는 단순 도형으로.** 디테일 모델링은 AI 실사 생성과 **간섭**해 품질을 떨어뜨립니다.
2. **피사체는 색으로 구분한다.** 마젠타/시안/옐로/레드 등 **채도 높은 원색**.
3. **역할 구분을 확실하게.** 한 색에 두 역할을 겹치지 않습니다.

> 3번이 가장 자주 위반됩니다. "이 색이 무엇이 될지"를 프롬프트에서 1:1 로 지정해야
> AI 가 색을 역할로 읽습니다. 색이 겹치면 AI 가 두 물체를 하나로 합칩니다.

#### ⑭-3. 프리비즈 렌더 설정 — 반드시 이 값으로 (실측 근거)

프리비즈는 **발광(emission) 원색**이므로 **광선 추적이 필요 없습니다.** 따라서:

```python
S.render.engine = 'CYCLES'; S.cycles.device = 'CPU'
S.cycles.samples = 1              # 발광이므로 1샘플로 충분
S.cycles.max_bounces = 0          # 반사·굴절 없음
S.cycles.use_denoising = False    # 노이즈가 없으므로 불필요
S.render.resolution_x = 832; S.render.resolution_y = 468
```

**실측 속도 계층 (같은 샌드박스 · 2코어 · RAM 3GB · GPU 없음):**

| 설정 | 속도 | 판정 |
|---|---|---|
| 1920x1080 / 48spp / 일반 씬 | 115초 초과 (타임아웃) | ✗ |
| 1280x720 / 8spp / 발광 | **10.3 s/frame** (500초 = 34시간) | ✗ |
| **832x468 / 1spp / 발광** | **0.196 s/frame** (500초 = 약 40분) | **✓ 채택** |

**교훈.** 같은 엔진(Cycles CPU)인데 **52배** 차이가 납니다.
"Cycles 는 느리다"가 아니라 **"프리비즈에 불필요한 설정을 켜두면 느리다"** 였습니다.

**EEVEE 는 이 환경에서 불가합니다.** `EGL_BAD_MATCH` (GPU 없음) → llvmpipe 재시도 → OOM(3GB).
따라서 Cycles CPU + 위 설정이 **유일한 성립 경로**입니다.

#### ⑭-4. 프리비즈 세트 규칙 — 검은 구멍 방지

카메라가 배경 밖을 보면 프레임에 **검은 영역**이 생기고, AI 는 그것을 그대로 검게 재현합니다.

```
세트는 카메라 궤적보다 넉넉하게 세운다.
  바닥  16 x 12 m       (카메라 최대 반경의 2배 이상)
  벽    후면 + 좌 + 우, 높이 4.4 m
```

우리 v1 프리비즈에서 프레임 1·48 상단에 검은 구멍이 났고, 세트를 위 크기로 키워 해소했습니다.

#### ⑭-5. Video-to-Video 프롬프트 골격 (이 구조를 그대로 씁니다)

```
[1행] 실사 톤 + 장면 + 촬영 스타일. 한 컷 연속.

@Video1 is the CAMERA AND SPATIAL reference: follow its camera path, framing,
perspective and timing 1:1 frame for frame. Its coloured flat planes are position
markers for real objects, and its small red blocks are position markers for
glowing highlighted words.

@Image1 is the environment, lighting and texture reference: <plate 설명>.

Color-based proxy replacement:
  the magenta plane becomes <역할1>,
  the cyan plane becomes <역할2>,
  the yellow plane becomes <역할3>,
  the dark plane becomes <바닥>,
  the brown walls become <배경>,
  the red cylinder becomes <소품>,
  the three small red blocks become <강조 요소 + 그 움직임의 의미>.

[카메라 서술] The camera holds still at the start, then <무빙>, keeping true 3D
perspective parallax: the near <A> slides across frame faster than the far <B>,
and the <A>s occlude each other as the camera passes.

No text overlays, no captions, no subtitles.
```

**필수 5요소.** ① `@Video1 = CAMERA AND SPATIAL reference` 명시 ② `1:1 frame for frame`

#### ⑭-7. 한글 글자 마커 — 정답 구현 (2026-08-22 실증 · 위 결함 해소)

**(a) 글자 PNG 는 반드시 RGBA · 배경 알파 0.**
불투명 검은 배경 PNG 를 그대로 emission 으로 붙이면 화면에 **검은 카드**가 나타나고,
AI 는 그것을 "검은 판"으로 해석합니다(4세대 pv4 에서 실제 발생).

**(b) 머티리얼 — 알파가 MixShader 를 구동해야 합니다.**

```python
def texflat(name, path):
    """emission material driven by an image texture -> the GLYPH becomes structure."""
    m = bpy.data.materials.new(name); m.use_nodes = True
    nt = m.node_tree; nt.nodes.clear()
    tc = nt.nodes.new('ShaderNodeTexCoord')
    tx = nt.nodes.new('ShaderNodeTexImage')
    tx.image = bpy.data.images.load(path)
    tx.interpolation = 'Closest'      # 글자 경계를 뭉개지 않는다
    tx.extension = 'EXTEND'
    e  = nt.nodes.new('ShaderNodeEmission'); e.inputs[1].default_value = 1.0
    tr = nt.nodes.new('ShaderNodeBsdfTransparent')
    mx = nt.nodes.new('ShaderNodeMixShader')
    o  = nt.nodes.new('ShaderNodeOutputMaterial')
    nt.links.new(tc.outputs['UV'],    tx.inputs['Vector'])
    nt.links.new(tx.outputs['Color'], e.inputs[0])
    nt.links.new(tx.outputs['Alpha'], mx.inputs[0])   # ★핵심: 알파가 믹스를 구동★
    nt.links.new(tr.outputs[0], mx.inputs[1])         # 0 -> 투명
    nt.links.new(e.outputs[0],  mx.inputs[2])         # 1 -> 발광 글자
    nt.links.new(mx.outputs[0], o.inputs[0])
    m.blend_method = 'BLEND'
    return m

def add_tex(name, loc, sc, path):
    bpy.ops.mesh.primitive_plane_add(size=2, location=loc)
    ob = bpy.context.object; ob.scale = sc; ob.name = name
    ob.data.materials.append(texflat(name, path))
    return ob
```

**(c) 배치 규칙 (실측으로 확정).**

| 형상 | 큐브 아님 · **plane** | 글자는 면이지 덩어리가 아님 |
| z 오프셋 | **>= +0.032** | +0.012 는 문서에 파묻힘(pv4 실측) |
| 부상 회전 | `rotation_euler = (v * 1.15, 0, 0)` | 누우면 카메라에서 안 읽힘 |
| 스케일 | `(0.30*(1+0.9v), 0.15*(1+0.9v), 1.0)` | 2:1 글자 비율 유지 |

**(d) 프롬프트에 ⑭-5 의 `NOT a marker` 선언을 반드시 병행합니다.**
구조(UV 텍스처)와 선언(프롬프트) **둘 다** 있어야 합니다. 하나만으로는 해소되지 않습니다.

### 교훈 165 — 구조로 전달하되, 그것이 "교체 대상"인지 "최종물"인지도 전달해야 한다

**교훈 162 의 완결편입니다.**

교훈 162 에서 우리는 *"구조로 전달되지 않은 것은 통제되지 않는다"* 를 배웠습니다.

and must be reproduced EXACTLY as the identical Korean word, same glyphs, same position,
same rotation, same scale, frame for frame.

**일반화.**

| 프리비즈 안의 요소 | AI 에게 무엇인가 | 프롬프트 처리 |
|---|---|---|

> **"이것은 바꿔라" 와 "이것은 그대로 둬라" 를 갈라서 말해야** 통제가 완성됩니다.

## 교훈 167 — 한 컷을 위해 쓴 제스처를 전량에 무조건 적용하면 안 된다

| 정지 구간 (0~60프레임 완전 동일) | ✅ 성공 |
| **글자** | ❌ **붉은 낙서로 뭉개짐** |

### 원인 — 서사가 다른 컷에 같은 제스처를 썼다

`pv5` 의 제스처는 **「세 글자가 한 점으로 수렴」** 이었습니다.
그것이 옳았던 이유는 그 컷의 대사가 이것이었기 때문입니다.

> "나는 어떤 역할을 반복해 왔는가 — **세 프로젝트에서 같은 역할이 반복된다**"

세 개의 문서에 **같은 단어**가 있고, 그것이 **한 곳으로 모이는 것**이 곧 그 문장의 뜻입니다.
[CEO-51] 이 지목한 바로 그 장면입니다.

그런데 이 제스처를 60잡 전체에 무조건 적용하니, 서사가 전혀 다른 컷에서도
글자 평면 3장이 같은 좌표로 이동했습니다. 세 장이 한 점에 겹쳐 쌓이면
생성기 입장에서는 그것이 **글자가 아니라 붉은 덩어리**입니다. 그래서 낙서로 렌더했습니다.

### 처방 — 제스처를 컷의 대사에서 유도한다

제스처는 연출자가 고르는 것이 아니라 **그 컷이 무슨 말을 하는지에서 나옵니다.**

```python
CONVERGE_KEYS = ("반복", "세 프로젝트", "3개 프로젝트", "같은 역할", "공통")
NONE_KEYS     = ("새 정보 금지", "읽히는 글자 금지")

def gesture_of(row_src, cam_row):
    if cam_row["seam_id"].startswith("A8"):          # 리포트 지면 구간
        return "none"
    if any(k in (row_src.get("protect") or "") for k in NONE_KEYS):
        return "none"
    blob = " ".join([cam_row["narr_line"], cam_row["objects"], cam_row["motion_reason"]])
    if any(k in blob for k in CONVERGE_KEYS):
        return "converge"
    return "lift"
```

| 제스처 | 조건 | 화면에서 일어나는 일 | 실측 분포 |
|---|---|---|---|
| `converge` | 대사에 "반복 / 세 프로젝트 / 같은 역할 / 공통" | 글자 **3개**가 한 점으로 수렴 | **5잡** |
| `none` | `protect` 에 "새 정보 금지 / 읽히는 글자 금지", 또는 ACT8 | 글자 **없음** | **9잡** |
| `lift` | 기본값 | 글자 **1개**가 문서 한 장 위에서 제자리 부상 | **46잡** |

**검증**: CEO 가 승인한 A6-02 컷이 이 규칙에서 정확히 `converge` 로 분류되었습니다.
즉 규칙은 승인본을 반려하지 않습니다(교훈 131 준수).

### 부수 교정 — 스케일과 배율

세 장이 겹칠 때 덩어리가 되는 것을 막기 위해 글자 평면을 줄였습니다.

| 항목 | 이전 | 이후 |
|---|---|---|
| 글자 평면 스케일 | 0.30 / 0.15 | **0.26 / 0.13** |
| 부상 배율 (converge) | 0.9 | 0.9 (유지) |
| 부상 배율 (lift) | — | **0.35** (제자리 부상이므로 작게) |

### 프롬프트도 함께 갈라야 한다

프리비즈에 글자가 1개인데 프롬프트가 "three panels ... the RED KOREAN TEXT" 라고
말하면, 생성기는 **없는 두 개를 만들어 냅니다.** 그래서 프롬프트도 3분기했습니다.

```
converge → "There are THREE separate copies of 「조율자」 ... they must never
            merge, overlap or smear into a blob."
lift     → "There is exactly ONE copy of 「방식」 ... do not duplicate it onto
            the other documents, do not add any second word."
none     → "There is NO text of any kind in this shot."
```

게이트로 강제합니다 — `converge` 프롬프트에 one-copy 절이 섞이거나
`lift` 프롬프트에 three-copy 절이 섞이면 `PROMPT GATE FAILED` 로 정지합니다.

> **구조(프리비즈)와 언어(프롬프트)가 같은 것을 말해야 합니다.**
> 하나는 글자 1개를 보여주고 다른 하나는 3개를 요구하면, 생성기는 그 모순을
> 자기 방식으로 메꿉니다. 그 결과가 낙서였습니다.

### 증상

같은 시범 컷의 후반에서 **문서가 화면 아래로 흘러넘쳤습니다.**
카메라가 책상이 아니라 그 위의 빈 공간을 올려다보고 있었습니다.

### 원인 — 전 컷에 같은 시선 종점을 줬다

`camtab.py` 가 80컷 전부에 동일한 값을 넣고 있었습니다.

```python
tgt_start_xyz = [0.0, -0.55, 0.15]
tgt_end_xyz   = [0.0, -0.35, 0.77]     # ← 전 컷 동일
```

`z = 0.77` 이 옳았던 이유는 `pv5` 의 글자가 `z = 0.92` 까지 올라가기 때문입니다.
**글자를 따라 올려다보는 것**이 그 컷의 연출이었습니다.

그러나 `lift` 컷의 글자는 `+0.34` 만 뜨고, `none` 컷에는 글자가 아예 없습니다.
그런 컷에서 `0.77` 을 올려다보면 카메라는 **아무것도 없는 허공**을 향하고,
정작 보여줘야 할 문서는 프레임 밖으로 밀려납니다.

### 처방 — 시선 종점을 제스처에서 유도한다

```python
TGT_END = {
    "converge": [0.0, -0.35, 0.77],   # 글자가 z=0.92 로 모인다 → 함께 올려다본다
    "lift":     [0.0, -0.45, 0.30],   # 글자가 0.34 만 뜬다 → 지면에 머문다
    "none":     [0.0, -0.50, 0.20],   # 글자가 없다 → 책상면을 지킨다
}
```

게이트로 강제합니다 — `tgt_end_xyz != TGT_END[gesture]` 이면 `PLAN GATE FAILED`.

프롬프트에도 프레임 종착지를 명시합니다.

```
lift/none → "The shot ends still looking down at the desk surface; the documents
             remain fully inside the frame at all times and never slide out of
             the bottom."
converge  → "The shot ends looking slightly up, following the words above the
             desk; the documents stay inside the frame."
```

> **카메라가 무엇을 향하는지는 그 컷에 무엇이 있는지에 종속됩니다.**
> 대상이 올라가지 않는데 시선만 올리면, 화면에는 대상이 사라진 빈 하늘이 남습니다.

## 교훈 169 — 유료 대량 착수 전 "1컷 시범 + 컨택트시트 직독" 은 규칙이다

이번에 실제로 아낀 금액을 기록합니다.

| 만약 시범 없이 진행했다면 | 실제 |
|---|---|
| 프리비즈 60잡 전량 렌더 (29분) → **전량 폐기** | 33잡에서 중단 |

4. 시범 컷은 **가장 앞 컷**을 쓴다 — 결함이 있으면 관객이 가장 먼저 보는 곳이다.

> 시범은 비용이 아니라 **보험**입니다.
> 9초로 383초를 지켰습니다.

## 교훈 179 — 반올림은 누적된다: 흡수하지 말고 격자에 스냅하라

이러면 반올림이 누적되지 않고 **모든 경계에서 상쇄**된다. 컷 k 의 종료 인덱스가

| 측정 항목 | 결과 |

| 격자 불연속·겹침 | **0건** |

## 교훈 180 — 자막: 어절 정렬은 「탐욕」이 아니라 「전역 최적」이다

## 교훈 182 — 「경고」로 반환한 결손은 성공으로 보고된다

`master500.py map` 이 두 번째 사실을 알려줬다. ACT1~2 슬롯은 2880프레임인데
`act12.mp4` 는 2583프레임이었다. **297프레임 = 12.375초가 조용히 사라져 있었다.**

행별로 원하는 프레임 수와 실제 조각의 프레임 수를 나란히 실측했다.

```
A1-06  want  96 f   got -1     ← 파일 없음
A1-08  want 107 f   got -1     ← 파일 없음
A2-02  want  96 f   got -1     ← 파일 없음
(나머지 6건은 ±1 프레임 반올림 — 무해)
96 + 107 + 96 = 299 f ≈ 297 f 결손
```

### 근본 원인은 코드 두 줄이었다

```python
# drive500.py:131
if not os.path.exists(src):
    return None, f"{r['sid']}: generated clip not delivered yet ({src})"
```

결손 행을 **에러가 아니라 경고로 반환하고 계속 진행한다.** 그래서 마스터가
12초 짧게 나와도 프로세스는 `rc=0` 으로, 즉 **완료**로 끝난다. 로그에는 경고가
찍혔지만, 경고는 사람이 읽어야만 의미가 생긴다. 프레임 수를 세는 게이트가
없었기 때문에 12초의 소실이 세 세션을 살아남았다.

### 그리고 그 3본은 이미 납품돼 있었다

`_r_v2.json` 을 열어보니 V-2 팀이 그 세 컷을 진작에 납품했고, URL 이 그대로
남아 있었다. 재생성(유료 3회) 대신 **회수(무료)** 했다.

```
A1-06 → files/s/ljUPnTnv    A1-08 → files/s/RZ6wysPV    A2-02 → files/s/pfRWfbN7
실측 3본 전부 7.018 s · 24 fps · 1280x720 · 168 f  (슬롯 4.0~4.46 s 에 충분)
확대 직독 검수 합격 — 문서 더미 컷이라 저품질 글자가 구워진 곳이 없음
```

**「납품 URL 이 있다」와 「디스크에 있다」는 서로 다른 사실이다.** 두 번째를
확인하는 게이트가 없으면 첫 번째는 아무 의미가 없다.

### 결손은 두 번째 결함을 숨기고 있었다

회수한 3본을 넣고 `drive500.py` 를 재실행하자 이번엔 **크래시**했다.

```
ValueError: intentional_transition requires transition_reason
```

`A1-08` 은 `intentional_transition` 정책 행이다 — 스택이 절개되어 내부에서
따뜻한 빛이 나오는 컷이라, 그 대비를 색보정으로 중화하면 안 된다. `cmatch.py`
는 그런 경계에 **이유를 데이터로 명시할 것**을 요구한다. 그런데 이유는 그
액트 헤더의 **산문 주석에만** 있었고, 게이트가 읽는 필드로는 없었다.

**이 게이트는 여태 한 번도 실행된 적이 없었다.** 해당 행의 클립이 없어서
`drive500` 이 그 행을 건너뛰었기 때문이다. 결손이 게이트를 가리고 있었다.

```python
S("A1-08", 56.18, 60.64, "i2v", "A1_WARM", "intentional_transition",
  transition_reason="the sealed stack is cut open at this cut and the interior "
                    "emits warm light; neutralising that contrast would erase "
                    "the reveal the narration is describing",
  expected_warmth_direction="warmer", ...)
```

**규칙: 결손을 경고로 처리하지 마라. 산출물의 프레임 수를 세고, 슬롯과 다르면
실패시켜라. 그리고 결손 행 하나는 그 행에 걸려 있던 게이트 전부를 함께
잠재운다 — 결손을 메우면 잠들어 있던 게이트가 깨어나 그동안 검사되지 않았던
것을 처음으로 검사한다.**

## 교훈 183 — 팀의 권고는 「맞는 지표」로 검증해야 의미가 생긴다

전담 채널에 발주해 둔 과업의 회신 2건이 도착해 있었다. 하나는 카메라 반경
보간 방식에 관한 권고였다.

> 반경은 선형 대신 **로그 보간**으로 두십시오:
> `e=smootherstep(t); r(t)=exp((1-e)*ln(r0)+e*ln(r1)) = r0*(r1/r0)**e`
> 프레임당 상대 반경 변화 `Δln r` 를 균등화해 근거리 중간 구간의 시차 뭉침을
> 줄입니다.

이 권고를 채택하면 60잡 전량 재렌더(약 3시간)가 필요하다. 그러니 **효과의
크기를 정확히 알아야** 판단할 수 있다. 측정을 세 번 했고, 처음 두 번은 틀렸다.

### 1차 — 자료구조를 추측했다

```python
for jid, j in json.load(open("jobs.json"))["jobs"].items():
# AttributeError: 'list' object has no attribute 'items'
```

`jobs.json["jobs"]` 는 **리스트**다. `job_id` 는 각 원소의 필드다. 교훈 172 의
재발 — 추측하지 말고 열어보라.

### 2차 — 지표가 틀려서 무의미한 수치가 나왔다

원시 `|Δln r|` 의 컷 내 최대/최소 비율을 재봤다.

| | 선형(현행) | 로그(권고) |
|---|---|---|
| spread | 306,202 | 212,375 |

수십만 배. **이 숫자는 아무것도 말해주지 않는다.** 원인은 이징이다. 우리는
`smootherstep` 이징을 쓰는데, 이징은 컷의 시작과 끝에서 진행률 자체를 0 에
수렴시킨다. 그러니 프레임당 변화량의 최소값은 어느 보간을 쓰든 0 에 가깝고,
그 비율은 발산한다. **이징이 보간 방식의 차이를 완전히 덮어버렸다.**

### 3차 — 이징을 분리했다

측정해야 할 것은 「프레임당」이 아니라 「진행률당」 상대 변화, 즉
`d(ln r)/de` 의 컷 내 변동이다.

| 지표 | 선형(현행) | 로그(권고) |
|---|---|---|
| 평균 max/min | 1.727 | **1.000** |
| 최악 max/min | **2.630** (J_A8-01/02/03) | **1.000** |

이제 숫자가 의미를 갖는다. 현행 선형 반경은 **한 컷 안에서 「다가오는 속도」가
최대 2.63배까지 요동한다.** 로그 반경은 근사가 아니라 항등식이므로 정확히
1.000 이다 — `d(ln r)/de = ln(r1/r0)` 는 상수다.

**팀의 권고가 옳다.** 다만 전량 재렌더가 90% 진행된 시점이었으므로 채택 여부는
비용/효과를 정리해 결정권자에게 올렸다. 검증은 무료였고 오판은 3시간이었다.

### 부수 발견 — 회신을 「받는」 것도 검증해야 한다

같은 채널에서 발주 하나가 **본문 없이 멘션만** 전달돼 있었다. 원인은 CLI
인자 키였다.

```
잘못:  {"channel_id": "...", "text": "..."}      → 본문 유실, 멘션만 전송
정본:  {"channel_id": "...", "content": "..."}   → gsk genteam send --help 로 확인
```

팀은 "요청하실 항목을 보내주시면 검토하겠습니다"라고 회신했다 — 빈 본문을
받았다는 뜻이다. **발송 후 채널을 다시 읽어 본문 글자 수를 확인**하는 것으로
게이트를 세웠다.

**규칙: 팀의 권고는 「맞는 지표」로 재라. 지표가 틀리면 무의미한 수치가 나오고,
무의미한 수치는 옳은 권고를 기각하게 만든다. 그리고 발주는 「보냈다」가 아니라
「본문이 도착했다」까지 확인해야 발주다.**

즉 `CLUS_VFRAC = 0.30` 은 **간격이 아니라 간격의 하한**이다. 간격은 평면 자신의 높이를
넘어야 하고, 장 수는 `(n-1)/2·gap + hh <= 0.94` 를 만족하는 최대값이다.
장을 버려야 할 때는 **읽는 순서의 가장자리**를 버린다(문장 중간을 비우지 않는다).

## 교훈 197 — 「몇 줄이 필요한가」와 「어디서 끊는가」는 다른 질문이다 (균형 조판)

**계기**: CEO-73 — "A5 문구가 3줄이라 광각 컷에서 화면을 다 덮습니다. 2줄로 줄여도 됩니다.
시각적인 최적화 사례를 늘 참고해서 적용하세요. **단, 벤치마크를 해도 내 것으로 소화해서
우리의 목적에 맞게 더 높은 품질로 가공해야 합니다.**"

### 문제 — 그리디 랩은 첫 질문만 답한다

그리디 줄바꿈은 각 줄을 상한까지 채우고 남은 것을 다음 줄로 버린다. 그래서 A1 이
`선택지는 / 늘고 기준은 / 흐려집니다` 처럼 **2어절 줄 위에 1어절 줄 둘**로 나왔다.
「필요한 줄 수」는 맞았지만 「어디서 끊을지」는 아무도 정하지 않은 결과다.

### 1단계 — 참조 (벤치마크)

전문 조판은 이것을 **balancing** 으로 푼다.
- **Knuth-Plass line breaking** (TeX) — 문단 전체의 badness 합을 최소화
- **CSS `text-wrap: balance`** — 가장 넓은 줄을 최대한 좁게 만드는 분할점 선택

### 2단계 — 소화 (★그대로 쓰면 안 되는 이유를 실측으로 확인★)

균형만 최적화하니 A1 이 `선택지는 / 늘고 기준은 / 흐려집니다` (widest aspect **5.20**,
가장 균등한 분할)로 갔고 — **승인 밴드를 0.2152 로 이탈해 반려**됐다.
정사각형에 가까운 블록은 같은 화면 폭에서 글자가 더 커지기 때문이다.

★결정적 반례: 대표님 승인본 std3 자체★ — 본문 줄 aspect **6.830**.
즉 승인된 조판은 **의도적으로 「가장 균등」이 아니다**.

⇒ **균형 조판의 목표 함수(가장 균등한 줄)와 우리 목표(승인된 글자 크기 유지)는 다르다.**

## 교훈 198 — 게이트 함정 4종 (단위 · 여유 · 적용 구간 · 낡은 전제)

### (1) 단위 함정 (UNIT TRAP)
`gap_ndc` 는 **프레임 전체 높이**의 비율이다(`gap_m` 을 그렇게 만들었으므로).
그런데 `ndcY` 는 **반높이** 단위다. 섞어 쓰면 정확히 **2배** 어긋난다.
실측: A5 예측 half-extent 0.672(통과) vs 렌더 1.123(실패) → 3장을 유지해버렸다.
처방: `gap_half = 2.0 * gap_ndc` 로 변환한 뒤 비교한다.

★단, 2배는 **한 곳에만** 써야 한다 — 교훈 199(2) 참조.★

### (2) 여유(clearance)는 누가 주는가
분리 게이트는 `need > sep * 1.02` 즉 `sep >= need/1.02` 를 요구한다.
**2% 를 소비하는 쪽이 게이트다.** 간격 산식에 1.02 를 쓰면 여유가 0이 되어 경계에
정확히 착지한다(실측 J_A6-02: stack 0.54m vs gap 0.53m).
처방: 여유는 **우리가 주는 것**이므로 한 곳에 명시하고 넉넉히 → `CONV_CLEAR = 1.15`

### (3) 게이트는 「그 현상이 존재하는 구간」에만 적용된다
개별 평면의 off-frame 게이트는 전 프레임 유효하지만, **두 평면의 상호 관계**를 재는
게이트는 그 관계가 성립하는 구간에서만 의미가 있다.
★★단, 이 원칙을 「가드」로 구현하면 실제 결함을 가릴 수 있다 — 교훈 199 가 그 실패 사례다.
구간을 좁히기 전에 반드시 「그 구간에서 정말 안전한가」를 실측하라.★★

### (4) 게이트의 전제가 낡을 수 있다
"최소 2장" 규칙은 모든 텍스처가 짧은 단어(화면 0.11)일 때 쓰였다. 문장 텍스처에서는
2줄 0.22 / 3줄 0.46 이고, 교훈 196 에 의해 **텍스처가 1장만 허용**할 수 있다.
읽을 수 있는 한 단어는 유효한 컷이고, 잘린 단어는 아니다 ⇒ 하한을 1로.

## 교훈 199 — 가드로 덮지 말라. 「측정하지 않은 서술」은 게이트를 거짓으로 만든다

★이 교훈은 내가 교훈 198(3)에서 넣은 처방이 틀렸음을 스스로 계측으로 밝혀낸 기록이다.

### 진짜 구조
글자는 시트에서 출발해 클러스터로 모인다. 즉 **상호 간격이 `e` 와 함께 자라는데
패널 크기는 자라지 않는다.** 그러므로 **출발 간격이 패널보다 좁으면 반드시 겹친다.**
겹침은 「모이는 중」의 문제가 아니라 **「출발점 선정」의 문제**다.

### 처방 (2건)

**(1) 인쇄 상태에서 이미 떨어져 있는 시트만 글자를 싣는다**
`visible_docs()` 에서 캐리어를 고를 때, 게이트가 강제하는 것과 **같은 여유**로
연속 시트의 화면상 간격을 검사한다. 자격을 갖춘 시트가 하나뿐이면 converge 는
자연히 lift 로 degrade 한다(그것은 유효한 컷이다 — 교훈 198(4)).
그리고 **분리 게이트는 전 프레임으로 되돌린다**(가드 제거).

**(2) 2배는 한 곳에만 (교훈 198(1)의 이중 계상 적발)**
`hh_ndc` 는 반높이, `gap_m` 은 전체 높이 기준. 그래서 필요 간격은
산식에서 `hh*CLEAR`, ndcY 비교 시 `2*hh*CLEAR` 다.
두 줄에 모두 `2*hh*CLEAR` 를 쓰면 **실제 간격이 `4*hh`** — 필요량의 2배가 되어
글자를 프레임 밖으로 밀어낸다. 이것이 A7 이탈의 남은 절반이었다.
```
gap_ndc  = max(CLUS_VFRAC, hh_ndc * CONV_CLEAR)     # 산식: 전체높이 단위
gap_half = 2.0 * gap_ndc                            # 비교: 반높이 단위
```

### 결과
```

DRY OK  jobs 60  every gate passed      (레거시 회귀 무손상)
```

### 일반 규칙 (다음 사람에게)
1. **게이트를 좁히는 변경은 「그 구간이 정말 안전한가」를 실측한 뒤에만 한다.**
   좁히기는 고치기가 아니다. 실패가 사라진 것과 결함이 사라진 것은 다르다.
2. **주석에 「~이므로 안전하다」고 쓸 때, 그 문장에 수치가 없으면 그것은 추측이다.**
   (헌법 §0.0.2 R2 — 측정값 없는 근거는 근거가 아니다)
3. **같은 계수를 두 곳에 쓰기 전에 각 줄의 단위를 적어라.** 2배는 한 곳에만 있다.

### 파생 발견 2 — 글자를 실은 컷은 카메라가 그 글자를 봐야 한다

때문이다. 처방: 글자를 싣는 5개 컷에서만 캐리어를 시선점으로 이동. 카메라를 캐리어로
끌고 가지 않는다 — 그것이 애초에 「한 장면 다각도」를 만든 동작이다.

### 일반 규칙

1. **소재의 정본은 대본이다.** 잡(job)은 대본의 파생물이고, 파생 과정에서 대본 열
   (`screen_direction` / `camera_note` / `on_screen_text`)을 버리면 서사가 사라진다.
   버린 것은 렌더 결과를 봐도 보이지 않는다 — **「없는 것」은 화면에 나타나지 않기
   때문이다.**
2. **기본값을 뒤집지 말라.** 글자는 예외여야 하는데 기본값(`return "lift"`)이었다.
   **기본값이 틀리면 61컷이 조용히 틀린다.**
3. **대본에 열이 있으면 그 열을 읽는 게이트를 먼저 만들어라.** 읽지 않은 열은
   「없는 열」과 구별되지 않는다. (헌법 §0.0.2 R3)
4. **세트를 나누는 것과 시선을 나누는 것은 다른 일이다.** 장소를 10개로 늘려도 시선점이
   9개로 붕괴하면 관객이 보는 장면 수는 늘지 않는다. **관객이 세는 단위는 세트가 아니라
   시선점이다.**
5. **게이트가 레거시를 거부하는 것은 게이트가 살아있다는 증거다.** 레거시 60잡에서 46건을
   검출한 것이 이 게이트를 신뢰하는 이유다. 우회는 명시적으로
   (`PREVIZ_NO_SCRIPT_GATE=1`, 로그에 남김) — **조용한 우회가 첫 결함을 살려둔 방식이다.**

## 교훈 210 — 「크다」는 「보인다」가 아니다: 화각과 가림을 함께 물어라

### 사건

G6(FRAMING) 가 6/6 통과했는데 `J_A4-01` 의 렌더 프레임은 **완전 균일 회색**이었다.
픽셀 직독 결과 `maxside/W = 0.000` — 주연이 화면에 **한 픽셀도 없다**.
게이트는 같은 컷을 `0.175` 로 통과시켰다.

### 원인 — G6 이 재는 것은 「거리 대비 크기」뿐이다

G6 산식은 `frac = 2*max(sc0,sc1) * lens / (depth * SENSOR_MM)` 다.
이것은 **「그 물체가 광축 위에 있다면 화면의 몇 %를 차지하겠는가」** 를 답한다.
답하지 않는 것이 두 가지 있다.

1. **화각(frustum)** — 물체가 광축에서 얼마나 벗어나 있는가.
   `lens 80mm` 의 반화각은 수평 12.7° / 수직 7.2° 다. `res1` 은 광축에서
   **22.4°** 떨어져 있었다. 즉 **화면 밖**이다. 그런데 depth 는 작으니
   frac 은 크게 나온다.
2. **가림(occlusion)** — 물체와 카메라 사이에 판이 있는가.
   `S4` 의 `"floor"` 판(z 2.44, 14×11 m)은 이름만 floor 이고 실제로는
   **카메라 위를 덮는 통천장**이었다. 프레임 전체가 그 판의 밑면이었다.

### 처방 세 겹

1. **G8(가시성) 신설** — `subj_frac()` 안에서 각 후보에 대해
   `visible(cam, tgt, loc, lens, blocks)` 를 호출하고 **안 보이는 것은 크기를
   세지 않는다**. 화각은 수평 `atan(36.0/2/lens)` · 수직
   `atan(SENSOR_H_MM/2/lens)` (`SENSOR_H_MM = 36*720/1280 = 20.25`),
   가림은 `max(halfext) >= 2.0` 인 대형 판만 blocker 로 보고 slab test 한다.
2. **세트 정정** — 대본이 **"사무실 단면 위층"** 이라고 쓴다. 「단면」은 절개다.
   `room("upper")` 의 통천장을 `ceilBand`(폭 0.90 m 띠) 로 바꿨다.
   **대본이 세트의 정본이다**(교훈 200).
3. **PROPS 정정** — `A4-01` 의 흩어진 3장을 **한 서가 묶음**으로 모았다.

### 다음 작업자에게 — 일반 원칙

**게이트를 세울 때마다 「이 게이트가 못 보는 축은 무엇인가」를 물어라.**
축의 계보는 이렇게 자랐다: **크기 → 화각 → 가림**. 각 축은 앞의 축을 통과한
컷에서 결함을 찾아냈다. 산술이 통과해도 **렌더 프레임 픽셀 직독**이 최종이다 —
그것은 무료이고, 여기까지 게이트를 두 번 반증했다.

### 처방 — 게이트

`scenemap.py` 에 **Z-FIT 게이트**를 신설했다.

```python
Z_HEADROOM = 1.50        # 내용물 최상단의 1.5배까지는 「그 공간 안」으로 본다
Z_FLOOR_MIN = 1.20       # 아주 낮은 세트에서도 최소 이 높이는 허용한다

def _set_top(set_id):
    """이 세트가 담고 있는 내용물의 최상단 z (벽/천장 제외)."""
    top = 0.0
    for nm, _k, loc, sc, _c in build_spec(set_id):
        if nm.startswith(("wall", "ceil", "slab", "floor")):
            continue      # 껍데기는 「내용물」이 아니다
        top = max(top, loc[2] + sc[2])
    return top

def move_fits_height(move, set_id):
    ceil = max(Z_FLOOR_MIN, _set_top(set_id) * Z_HEADROOM)
    z0, z1 = MOVES[move][2], MOVES[move][3]
    return max(z0, z1) <= ceil + 1e-9
```

**임계값은 발명하지 않고 실측에서 골랐다.** `S4` 서가 `2.10 m` 이므로
상한 `3.15 m` → `drone_drop`(4.60) 은 거부되고 `crane_settle`(3.10) 등이 남는다.

무브 선택 pool 에서 전부 걸러지면 **필터를 풀지 않고**
「가장 낮은 무브」를 결정적으로 남긴다 — 가드로 덮지 않는다(교훈 199).

## 교훈 212 — 마스크가 대상의 색을 전제하면 픽셀 직독도 거짓말한다

### 사건 — 교훈 211 처방이 통했는데 측정은 계속 실패했다

교훈 211 처방(Z-FIT 게이트) 후 `J_A4-01` 의 무브가 `drone_drop`(z 4.60) →
`desk_graze`(z 1.66→1.56) 로 바뀌고 G6 이 `0.051 → 0.352 (451 px)` 로 올랐다.
그런데 재렌더 후 픽셀 직독은 **여전히 `0.052 / 0.059 / 0.041` (FAIL)** 이었다.

세 번 연속 같은 컷이 실패했으므로 **프레임을 눈으로 봤다**(교훈 210 의 방법).
프레임에는 이력서 세 장이 **화면 폭의 4분의 1 이상**으로 크게, 선명하게 보였다.
**베이지 · 시안 · 핑크** 색이었다.

### 원인 — 측정 도구가 대상의 색을 전제하고 있었다

`chk.py` 의 마스크는 이랬다.

```python
mask = (lum >= 120) & (sat <= 40)      # 밝고 무채색인 것 = 종이
```

`sat <= 40` 은 **「종이는 무채색이다」** 라는 전제다. 그런데 `sets.py` 의
문서 색상은 두 계열로 나뉘어 있다.

| 상수 | 값 | 채도 |
|---|---|---|
| `DOC_N` | (0.560, 0.560, 0.545) | **무채색** — 문장 카드 |
| `DOC_W` | (0.780, 0.775, 0.760) | **무채색** — 일반 A4 |
| `DOC_A` | (0.760, 0.145, 0.520) | **마젠타** — 「역할」 문서 |
| `DOC_B` | (0.130, 0.640, 0.720) | **틸** — 「방식」 문서 |
| `DOC_C` | (0.820, 0.700, 0.190) | **앰버** — 「변화」 문서 |

6컷 중 5컷의 주연은 `DOC_N`/`DOC_W`(무채색)이라 마스크에 잡혔다.
**`J_A4-01` 만 주연이 `DOC_A/B/C`(채색)** 이어서 마스크에서 통째로 빠졌다.
즉 측정 도구는 **「그 컷의 주연만 못 보는 눈」** 이었다.

### 처방

```python
# 환경(ENV_*)은 전부 저채도이고 어둡다 -> 두 갈래로 나눠 잡는다.
mask = (sat >= 55) | ((lum >= 170) & (sat <= 40))
```

- `sat >= 55` : 채색 문서(`DOC_A/B/C`) — 환경에는 채색이 없으므로 안전하다
- `(lum >= 170) & (sat <= 40)` : 무채색 문서(`DOC_N/DOC_W`) — 밝기 하한을
  120 → 170 으로 올려 회색 벽(`ENV_WALL_HI` 0.215 ≈ 55/255)을 배제

### 검증 — 다른 5컷 값이 흔들리지 않아야 한다

처방이 옳다면 **원래 통과했던 컷들의 값은 거의 그대로**여야 한다.

| 컷 | 정정 전 best | 정정 후 best |
|---|---|---|
| J_A3-13 | 0.302 | 0.300 |
| J_A3-14 | 0.320 | 0.318 |
| J_A3-15 | 0.310 | 0.309 |
| J_A3-16 | 0.189 | 0.188 |
| J_A3-17 | 0.377 | 0.376 |
| **J_A4-01** | **0.059 FAIL** | **0.234 OK** |

5컷은 ±0.002 안에서 동일하고 A4-01 만 살아났다. **처방이 정확히 결함만
고쳤다는 증거다** — 임계값을 느슨하게 풀어 억지로 통과시킨 것이 아니다.

### 다음 작업자에게 — 일반 원칙

**측정 도구도 검증 대상이다.** 픽셀 직독은 우리 신뢰도 위계에서 「실제로
보이는가」의 정본이고, 게이트를 두 번 반증했다. 그러나 그 도구 자체가
**대상에 대한 전제**를 품고 있으면 그 전제가 깨지는 케이스에서 거짓말한다.

**같은 컷이 세 번 실패하면 도구를 의심하라.** 두 번까지는 설계 결함일 수
있지만, 처방이 게이트 수치를 크게 개선했는데도 측정이 그대로면
**측정과 게이트가 다른 것을 보고 있다**는 뜻이다.

**Read 툴로 프레임을 직접 보는 것이 최종 심판이다.** 이번 결함은 숫자로는
찾을 수 없었다 — 눈으로 보니 3초 안에 명백했다(색이 있었다).

**처방의 정당성은 「고쳐진 것」이 아니라 「흔들리지 않은 것」으로 증명한다.**
5컷이 ±0.002 안에 머물렀다는 사실이, 마스크 확장이 억지 통과가 아님을 보인다.
