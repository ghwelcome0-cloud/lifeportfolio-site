## 0. 중학생 설명
시험 감독관 네 명에게 답안지를 주고 "이 학생이 안내문을 제대로 읽었는지 채점하라"고 했는데, **안내문 자체를 봉투에 넣지 않았다.** 감독관은 정직하게 "볼 자료가 없다(null)"고 적었다. 그래서 점수가 아니라 "측정 불가"가 쌓였다. 잘못은 학생(제품)이 아니라 **봉투를 싼 쪽(묶음 설계)** 에 있다. 거기에 더해, 채점기를 돌리려면 교장 도장(freeze 영수증)이 정해진 양식이어야 하는데 도장만 찍고 양식을 안 채웠다 — 이것도 **총괄의 절차 누락**이다.

## 1. 사실 — null이 어디서, 왜 생겼나

판정 스코프 192단위(8지표 × 12사례 × KO/EN) 중 **168단위**에 null이 하나 이상 있다. 최종 배열(만장일치 + adjudication) 기준으로 **check 단위 null은 13종 × 24단위 = 312개**이며, 사유는 전부 같은 한 문장으로 수렴한다: **"묶음에 그 표면이 없다."**

| 지표·check | 계약이 보라고 한 것 | 묶음에 있어야 했던 표면 | 실제 묶음 | null |
|---|---|---|---|---|
| A1 c1 | 고정 안내면의 수령물·목적·저장/재개·시작동작 | `intro` | report+program만 | 24/24 |
| A1 c4 | 안내→문항→리포트→프로그램 모순 없음 | `intro`·`items`·`response_ui` | 없음 | 24/24 |
| A2 c4 | 반대입력·일반서술 4개 대조 지지율 | 사전 봉인 반대입력 실행본 + 대조 세트 | 정방향 1개씩만 | 24/24 |
| A5.3 c1~c4 | 전수 문항·구성개념 정의·매핑, 두 AI 명료성 검토, 반대의견 로그, 별도 검수자 재현 | `items` + 제작 과정 기록 | 없음(evidenceRefs Q번호만) | 96/96 |
| A5.5 c2~c4 | 규칙·의존·변경이력, 문서–실물 전수 검수, 독립 실행 재현 | release 문서·변경이력·검수 기록 | 없음 | 72/72 |
| A5.7 c3 | 반례 포함 출력검수·위험표현 수정기록 | 검수/수정 로그 | 없음 | 24/24 |
| A5.8 c2, c4 | 주장 전수–판/범위/출처 대응표, 반대해석 점검·고지 회귀 | 주장 목록(claim inventory) + 회귀 기록 | 없음 | 48/48 |

반대로 **null이 0인 지표는 A3·A5.4 두 개뿐**이다. 둘 다 "report·program 안에서만 확인 가능한 check"다. 즉 **null의 분포가 묶음의 내용물과 정확히 일치**한다 — judge 성향이나 판정 품질 문제가 아니다.

## 2. 근본 원인 (5 Whys)

1. **왜 null인가?** judge가 볼 표면(intro·items·response_ui·제작/검수 기록·주장 목록)이 묶음에 없었다.
2. **왜 없었나?** `judge-bundle.cjs`는 설계상 봉인된 `product.json`의 **report + program 두 객체**와 그 렌더 텍스트만 담는다(소스 주석 9행). 계약 `surfaces`는 지표별로 `intro, items, response_ui, scoring, report, program`을 요구한다.
3. **왜 설계가 그랬나?** 묶음 설계 논의(Peer 5710946 · Method 5714622)는 **블라인드·격리·release 식별 제거**에 집중했고, "계약 check가 요구하는 표면의 전수 점검(check → surface 매핑표)"이 체크리스트에 없었다. 1회차 승인요청서 v3.1~v3.5 어디에도 "묶음에 포함되는 표면 목록 vs 계약 surfaces 대조"가 없다.
4. **왜 리허설에서 못 잡았나?** DEV 리허설 3회는 **하네스가 끝까지 도는지**(생성·봉인·묶음·스캔)를 봤지 **judge가 각 check를 실제로 채울 수 있는지**(mock judge 1회)를 보지 않았다.
5. **근본 원인:** **"계약 check → 필요한 증거 표면 → 묶음 내용물" 의 추적 매트릭스가 사전 결박 대상이 아니었다.** 계약·사례·judge·scorer는 결박했지만 **묶음 내용 사양**은 결박하지 않았다. 같은 뿌리에서 두 번째 결함도 나왔다: **freeze 영수증의 필수 필드**를 scorer 원문에서 미리 뽑아 결박하지 않아 R18에서 차단됐다.

한 줄: **"무엇을 재고 싶은가(계약)"와 "무엇을 재는 사람 앞에 놓을 것인가(묶음)" 사이의 대조표가 없었다.**

## 3. 세 겹의 null — 성격이 다르므로 해법도 다르다

| 겹 | 해당 | 성격 | 해소 주체 |
|---|---|---|---|
| ① **제품 표면 누락** | A1 c1·c4, A5.3 c1(items) | 제품에 **이미 존재**하는 화면(intro 안내면, 설문 문항, 응답 UI)을 묶음에 넣지 않음 | 하네스(묶음 사양) |
| ② **대조 세트 누락** | A2 c4 | 계약이 요구하는 **반대입력 실행본 + 일반서술 4개**를 하네스가 생성·봉인하지 않음 | 하네스(실행계획) |
| ③ **제작·검수 기록 누락** | A5.3 c2~c4, A5.5 c2~c4, A5.7 c3, A5.8 c2·c4 | 저장소에 **흩어져 존재**(게이트 로그·PR·changelog·금칙어 검사·docs/promise-and-limits·G17) — 묶음용으로 **수집·봉인되지 않음** | 총괄(증거 꾸러미 사양) + 하네스(봉인) |

③은 "없다"가 아니라 "묶지 않았다"다. 예: A5.7 c3 반례 출력검수 = `scripts/test-*` 금칙어·§7 검사와 CI 로그가 release마다 돈다. A5.8 c2 주장 대응표 = G17 공개 성능표 + 사이트 주장 목록. A5.5 c2 변경이력 = git log + PR 본문. 이것들을 release SHA에 묶어 **봉인 가능한 파일**로 만드는 일이 빠졌다.

## 4. 해소 계획 (2회차 · 결과 공개 전 사전 결박)

### 4-1. 묶음 사양을 계약에서 **기계적으로 유도**한다 — "check→surface 매트릭스"
- 새 파일 `judge-surface-matrix.json`: 8지표 × 4check = 32 check마다 `{required_surfaces:[…], bundle_path:[…]}`. 계약 `surfaces`와 check 문구에서 작성, Peer·Method 수락 후 SHA 결박(승인요청서 §0 추가 행).
- `judge-bundle.cjs` v3: 매트릭스의 `bundle_path`가 **하나라도 비어 있으면 `JUDGE_BUNDLE_REFUSED: SURFACE_MISSING`** — 묶음을 만들지 않는다. "일단 보내고 null 받기"를 구조적으로 금지.

### 4-2. 겹①·② — 하네스가 생성·봉인하는 표면 추가
- `intro`: 설문 시작 전 안내면 렌더 텍스트+스크린샷(KO/EN·1440/390) — 이미 A6 캡처 경로 존재, 대상 페이지만 추가.
- `items`: 해당 release의 `data/questions.json`(문항 본문·선택지·`text_en/options_en`) + `data/mapping.json` — 저장소 동결 객체 그대로(제품에 실린 것과 동일 SHA).
- `response_ui`: 설문 화면 렌더 텍스트(이미 하네스가 58단계를 통과하며 캡처 가능).
- A2 c4 대조 세트: 사례별 **반대입력 1개**(핵심 선택을 뒤집은 합성 응답, 사전 등록·SHA 봉인) 실행본 + **일반서술 4문장**(사전 등록) → judge가 지지율 차이를 계산할 수 있게.

### 4-3. 겹③ — "release 증거 꾸러미(evidence pack)" 사양
release 커밋 1개당 아래를 **단일 tar + SHA 목록**으로 봉인:
| 지표 | 꾸러미 내용(이미 존재하는 것을 모음) |
|---|---|
| A5.3 | 문항–구성개념 매핑(`mapping.json`), KO/EN 문항 명료성·극성 2-AI 독립 검토 기록(신규 1회 수행·로그 보존), 반대의견·수정 여부 로그 |
| A5.5 | `CHANGELOG`/PR 목록(release 범위), 규칙·의존 목록(`package-lock`, `data/*rules.json` SHA), 문서–실물 전수 대조(분리 AI 실행 로그), 독립 재현 로그 |
| A5.7 | 금칙어·§7 검사 실행 로그(반례 포함), 위험표현 수정 PR 링크, 이의제기 경로(RQ-04로 지면에 추가됨) |
| A5.8 | **주장 목록(claim inventory)**: 사이트·리포트·프로그램의 모든 주장 문장 ↔ 판/범위/출처/측정일(G17 연동), 독립 AI 반대해석 점검 로그, 고지 변경 회귀 테스트 로그 |
- 이 꾸러미는 **제품 품질 자료이기도 하다**(공개 성능표 G17의 원자료). 2회차 이후에도 release마다 자동 생성하도록 CI 잡으로 올린다.

### 4-4. scorer 입력 완결성 — 두 번째 뿌리 제거
- scorer 원문(`aa64b1d3…`/`648af560…`)에서 **모든 검사 순서와 필수 필드**를 추출한 `scorer-input-spec.md`를 결박(TL에 op:117로 요청). freeze 영수증·reviewer 기록·시각·blinding·caps/safety·technical 528·research 24 — 각 필드의 **출처 역할과 생성 시점**을 실행계획에 명시.
- "**모의 패키지 → scorer dry-run**"을 리허설 필수 단계로 추가: 합성 값으로 채운 패키지가 `blocked` 없이 끝까지 가는지 확인한 뒤에만 본 실행.

### 4-5. 제품 쪽에서 메울 수 있는 것(이미 착수)

## 5. 1회차 처리 (불변)
- 1회차 실행 a: `blocked · R18_owner_freeze_required`(freeze 영수증 형식 미비 — 총괄 절차 누락). 기록 보존.
- Peer·Method 판단(op:117 요청) 결과에 따라 **같은 패키지 + 올바른 영수증**으로 실행 b를 하거나, 1회차를 `미달성(사유: R18_owner_freeze_required)`로 닫는다. 어느 쪽이든 §1의 null 분포는 그대로이며, 실행 b가 돌아도 `judgment_invalid`(168/192) 계열의 차단이 예상된다 — **예단이 아니라 Method 5791310이 scorer 원문 67~71행에서 읽어 준 규칙**이다.
- 따라서 **90 도달은 2회차 과제**이며, 2회차의 성패는 §4-1~4-4의 사전 결박에 달려 있다.

## 6. 재발 방지 원칙 (G16 개정 4 후보)
1. **측정 전에 "볼 것"을 결박한다**: 계약 check → 증거 표면 → 묶음 경로 매트릭스를 사례·judge·scorer와 같은 급으로 SHA 결박.
2. **묶음은 비어 있으면 만들지 않는다**: `SURFACE_MISSING`은 STOP이지 null이 아니다.
3. **리허설은 끝에서부터 한다**: scorer dry-run(모의 패키지) → mock judge 1회 → 생성. 거꾸로가 아니라.
4. **null은 결과가 아니라 결함 신호다**: 2회차부터 "null 1건 = 묶음 사양 결함 1건"으로 §7에 기록하고 원인 열을 둔다.
