# ③축 바로 실행가능성 83→90 설계

- 작성 기준일: 2026-08-31
- 적용 대상: 76문항 진단 리포트 → 21일 체크인 → 자산 축적 흐름
- 전제 사실: 외부 제3자 심층평가 2차의 ③축 점수는 83점이다(발주문 제공값).
- 한계: 아래의 `90점 기준`은 기존 평가자의 채점식을 역산한 결과가 아니라 **출시 게이트용 제안 운영정의**다. 실제 외부 점수 90 도달 여부는 동일 평가자·동일 문항의 재평가 전까지 미확인이다.

## 1. 90점 제품과 83점 제품의 판별 기준

### 1.1 판정 단위

HTML을 렌더링한 뒤 사용자에게 보이는 **행동 카드(action card)** 단위로 판정한다. 메뉴·푸터·약관은 제외한다. 행동 카드는 제목, 지시문, 입력/CTA, 완료 상태를 하나의 DOM 컨테이너로 묶은 요소다.

아래 기준과 임계치는 모두 **제안 운영정의**다.

| ID | 지면에서 확인할 관찰 항목 | 90 게이트 | 83 수준의 전형적 실패 예시 |
|---|---|---:|---|
| O1 | 리포트 결론 직후 첫 행동 카드 존재 | 결론 섹션 종료 후 1스크롤 이내에 1개 이상 | 행동이 별도 페이지·하단에만 있음 |
| O2 | 행동 주체·동사·대상 | 모든 필수 카드가 `[사용자(생략 가능)] + 구체 동사 + 대상` 포함 | “성찰해 보세요”, “관리하세요”처럼 산출 대상 없음 |
| O3 | 시작 시점 | 필수 카드 100%에 오늘/지금/날짜/체크인 시점 중 하나 | “앞으로”, “꾸준히”만 있음 |
| O4 | 소요량 또는 횟수 | 필수 카드 100%에 분·시간·회·개·줄 등 수량 존재 | 작업 규모를 알 수 없음 |
| O5 | 완료 판정 | 필수 카드 100%에 저장·제출·체크·N개 작성 등 기계/사용자 판정 가능한 종료조건 | “충분히 생각하면 완료” |
| O6 | 즉시 실행 수단 | 첫 행동 카드에 입력창/체크박스/타이머/딥링크 중 1개 이상 | 지시만 있고 실행 화면을 다시 찾아야 함 |
| O7 | 다음 체크인 연결 | 완료 직후 다음 날짜·다음 행동·알림 설정 중 1개가 노출 | 완료 뒤 홈으로 종료 |
| O8 | 결과의 자산화 | 체크인 입력이 이름·날짜·출처와 함께 저장되고 자산 목록에서 다시 열림 | 일회성 완료 표시만 남음 |
| O9 | 실패 복구 경로 | “못 했음/건너뛰기/축소 실행” 중 1개와 재개 CTA 존재 | 미완료 시 다음 단계가 잠김 |
| O10 | 선택 과부하 제한 | 첫 화면의 ‘오늘 할 일’ 주 CTA 1개, 보조 선택지 최대 2개 | 동등한 우선순위의 과제 다수 |
| O11 | 근거-행동 경계 | 해석 문장과 실행 문장이 시각적으로 분리되고, 미증명 추론에는 상태 라벨 존재 | 해석이 사실인 것처럼 곧바로 명령으로 연결 |
| O12 | 행동 후 피드백 | 완료 시 저장 성공, 누적 수, 다음 사용처 중 2개 이상 표시 | 버튼 반응만 있고 무엇이 남았는지 불명 |

### 1.2 합격식

`axis3_ready = O1 ∧ O2 ∧ O3 ∧ O4 ∧ O5 ∧ O6 ∧ O7 ∧ O8 ∧ O9 ∧ O10 ∧ O11 ∧ O12`

- O2~O5의 분모는 `data-action-required="true"`인 카드로 고정한다. 선택 팁까지 분모에 넣으면 페이지 구성에 따라 점수가 흔들린다.
- O1·O6·O7·O8·O9·O10·O12는 DOM/E2E 검사, O2~O5·O11은 텍스트 검사로 나눈다.
- 접근성·Core Web Vitals 통과는 별도 품질축이며, ③축 합격의 대체 증거로 사용하지 않는다.
- **판정:** 83과 90의 핵심 차이는 “좋은 조언이 존재함”이 아니라, 첫 행동의 발견→실행→완료→저장→재개의 전 구간이 관찰 가능하게 닫혀 있는지다. 이는 본 설계의 정의이지 외부 검증 사실이 아니다.

## 2. 실행 지시문 자동 판정 규칙

### 2.1 입력 계약

게이트의 결정론을 위해 작성자가 카드에 다음 속성을 부여한다.

```html
<section data-action-card data-action-required="true" data-action-id="report-first-action">
  <p data-action-text>오늘 10분 동안 최근 성취 사례 1개를 3줄로 작성하세요.</p>
  <textarea data-action-input></textarea>
  <button data-action-complete>저장하고 오늘 체크인 완료</button>
</section>
```

정규식만으로 일반 본문에서 ‘지시문’을 추정하지 않는다. 렌더링 후 `textContent.normalize('NFKC')`, 연속 공백 축약, 앞뒤 공백 제거를 적용한다. 마침표 기준 문장 분할은 약어 오탐이 있으므로 카드 전체를 1개 판정 단위로 쓴다.

### 2.2 패턴 상수(ECMAScript)

```js
const RX = {
  START: /(?:오늘|지금|바로|이번\s*(?:체크인|회차|주)|\d{4}[.-]\d{1,2}[.-]\d{1,2}|\d{1,2}[./-]\d{1,2}|(?:오전|오후)\s*\d{1,2}(?::\d{2})?)/u,
  AMOUNT: /(?:\d+|한|두|세)\s*(?:초|분|시간|회|번|개|가지|줄|문장|명|쪽|페이지|원|%)/u,
  ACTION_VERB: /(?:작성|기록|선택|저장|제출|체크|표시|예약|전송|공유|분류|삭제|추가|수정|비교|요약|붙여넣|업로드|다운로드|말하|묻|읽|연락|열기|닫기|정하|옮기|캡처)(?:하|해|하세요|십시오|기|고|면|여)/u,
  NEGATED_ACTION: /(?:작성|기록|선택|저장|제출|체크|표시|예약|전송|공유|분류|삭제|추가|수정|비교|요약|붙여넣|업로드|다운로드|말하|묻|읽|연락|열기|닫기|정하|옮기|캡처)[^.!?]{0,12}지\s*마(?:세요|십시오)/u,
  VAGUE_ONLY: /^(?:잘|충분히|적극적으로|꾸준히|깊이)?\s*(?:생각|성찰|관리|노력|고민|개선|실천)(?:하|해)?(?:세요|보세요|기)?[.!?]?$/u,
  DONE: /(?:저장|제출|체크|완료|등록|전송|업로드|\d+\s*(?:개|가지|줄|문장|회).*(?:작성|선택|기록)|작성.*\d+\s*(?:개|가지|줄|문장))/u,
  CTA: /(?:시작|작성|기록|저장|제출|완료|예약|추가|다음|체크인)/u,
  EPISTEMIC_LABEL: /(?:가설|추정|탐색|참고|미증명|내용타당도\s*진행\s*중|구성(?:·|\s*)예측타당도\s*미증명)/u,
  UNSUPPORTED_CERTAINTY: /(?:당신은\s*[^.!?]{0,20}(?:형|유형)이다|반드시\s*성공|최적의?\s*(?:선택|직업|진로)|결과가\s*(?:보장|확실)|과학적으로\s*증명|타당성이\s*입증|정확도\s*\d+\s*%|재검사\s*신뢰도.{0,10}(?:확보|증명|입증))/u,
  INFERENCE: /(?:결과|점수|응답|진단|분석).{0,30}(?:의미|보여|시사|때문|따라서|이므로)/u,
  EXPERIMENT_FRAME: /(?:가설로|시험해|실험|맞는지\s*확인|실행\s*후\s*검토|조정할\s*수)/u
};
```

`ACTION_VERB`는 형태소 분석기 버전에 따른 비결정성을 피하기 위한 폐쇄형 허용목록이다. 새 동사는 코드리뷰로만 추가한다. 부정문(“저장하지 마세요”)이 동사 검사를 통과하지 않도록 `/지\s*마(?:세요|십시오)/u`가 행동동사 뒤 12자 이내에 있으면 실패시킨다.

### 2.3 규칙과 판정 로직

| 규칙 | 결정론적 판정 | 실패 코드 |
|---|---|---|
| R1 카드 식별 | 필수 카드마다 `data-action-id`가 있고 문서 내 유일 | `ACTION_ID_MISSING_OR_DUPLICATE` |
| R2 구체 동사 | `ACTION_VERB.test(text) && !VAGUE_ONLY.test(text)` | `ACTION_VERB_NOT_CONCRETE` |
| R3 시작 시점 | `START.test(text)` | `ACTION_START_MISSING` |
| R4 작업 크기 | `AMOUNT.test(text)` | `ACTION_AMOUNT_MISSING` |
| R5 완료조건 | `DONE.test(text + ' ' + completeButtonText)` | `ACTION_DONE_CRITERION_MISSING` |
| R6 실행 수단 | 카드 안에 `[data-action-input]`, `[data-action-complete]`, 유효한 내부 링크, 타이머 중 하나 | `ACTION_CONTROL_MISSING` |
| R7 CTA 대응 | 완료 버튼이 존재하고 `CTA.test(button.textContent)` | `ACTION_CTA_UNCLEAR` |
| R8 부정 지시 차단 | 검출된 행동동사 뒤 12자 이내 `지 마세요/지 마십시오`면 해당 동사를 불인정 | `ACTION_NEGATED_VERB` |
| R9 단정 차단 | `!UNSUPPORTED_CERTAINTY.test(text)` | `UNSUPPORTED_CERTAINTY` |
| R10 추론 라벨 | `INFERENCE.test(text)`이면 카드 또는 직전 해석 블록에 `EPISTEMIC_LABEL` 필요 | `INFERENCE_STATUS_MISSING` |
| R11 실험 가능성 | 개인화 추천이 있으면 `EXPERIMENT_FRAME` 또는 대안/건너뛰기 CTA 필요 | `RECOMMENDATION_NOT_REVERSIBLE` |
| R12 저장 연결 | 완료 컨트롤에 `data-save-target`이 있고 값이 허용목록(`checkin`,`asset`) 중 하나 | `SAVE_TARGET_MISSING` |

```js
function judgeActionCard(card, seenIds) {
  const norm = s => (s ?? '').normalize('NFKC').replace(/\s+/gu, ' ').trim();
  const id = card.dataset.actionId;
  const text = norm(card.querySelector('[data-action-text]')?.textContent);
  const button = card.querySelector('[data-action-complete]');
  const buttonText = norm(button?.textContent);
  const personalized = card.dataset.personalized === 'true';
  const hasAlternative = Boolean(card.querySelector('[data-action-skip],[data-action-alternative]'));
  const errors = [];

  if (!id || seenIds.has(id)) errors.push('ACTION_ID_MISSING_OR_DUPLICATE');
  if (id) seenIds.add(id);
  if (!RX.ACTION_VERB.test(text) || RX.VAGUE_ONLY.test(text)) errors.push('ACTION_VERB_NOT_CONCRETE');
  if (RX.NEGATED_ACTION.test(text)) errors.push('ACTION_NEGATED_VERB');
  if (!RX.START.test(text)) errors.push('ACTION_START_MISSING');
  if (!RX.AMOUNT.test(text)) errors.push('ACTION_AMOUNT_MISSING');
  if (!RX.DONE.test(`${text} ${buttonText}`)) errors.push('ACTION_DONE_CRITERION_MISSING');
  if (!card.querySelector('[data-action-input],[data-action-complete],[data-action-timer],a[data-action-link]')) errors.push('ACTION_CONTROL_MISSING');
  if (!button || !RX.CTA.test(buttonText)) errors.push('ACTION_CTA_UNCLEAR');
  if (RX.UNSUPPORTED_CERTAINTY.test(text)) errors.push('UNSUPPORTED_CERTAINTY');
  if (RX.INFERENCE.test(text) && !RX.EPISTEMIC_LABEL.test(norm(card.previousElementSibling?.textContent) + ' ' + text)) errors.push('INFERENCE_STATUS_MISSING');
  if (personalized && !RX.EXPERIMENT_FRAME.test(text) && !hasAlternative) errors.push('RECOMMENDATION_NOT_REVERSIBLE');
  if (!['checkin', 'asset'].includes(button?.dataset.saveTarget)) errors.push('SAVE_TARGET_MISSING');
  return { id, pass: errors.length === 0, errors };
}
```

### 2.4 합격·실패 고정 예시

- 합격: `오늘 10분 동안 최근 성취 사례 1개를 3줄로 작성하세요.` + 버튼 `저장하고 오늘 체크인 완료` + `data-save-target="asset"`.
- 실패(R3/R4/R5): `강점을 깊이 성찰해 보세요.`
- 실패(R5): `오늘 10분 동안 우선순위를 생각해 보세요.`
- 실패(R9): `이 결과는 당신에게 최적의 직업을 보여줍니다.`
- 합격 가능한 개인화: `이 추천은 현재 응답에서 만든 가설입니다. 오늘 10분간 역할 1개를 시험하고, 맞지 않으면 다음 체크인에서 조정하세요.`

게이트 자체의 한계: 정규식 통과는 문장 품질의 충분조건이 아니다. 이 규칙은 누락과 금지표현을 재현 가능하게 잡는 정적 검사다. 의미 적합성은 별도의 사람 리뷰가 필요하다.

## 3. 21일 체크인의 이탈 구조 가설

현재 이벤트 데이터가 제시되지 않았으므로 아래 날짜별 이탈은 모두 **미확인(추정)**이다.

### 3.1 데이터를 보기 전 세울 수 있는 구조 가설

| 예상 이탈 구간 | 미확인(추정) 원인 | 관찰 가능 신호 | 선제 설계 |
|---|---|---|---|
| 리포트→Day 1 | 첫 과제 탐색·재입력 비용, 시작 시점 불명 | 리포트 열람 후 Day 1 미시작 | 리포트 결론 안에서 첫 체크인을 미리 채우고 1클릭 시작 |
| Day 1→2 | 재방문 트리거 부재, 첫 저장의 보상 불명 | Day 1 완료 후 Day 2 미접속 | 완료 화면에서 다음 시점 선택 + 저장된 자산 즉시 노출 |
| Day 3~4 | 새로움 감소, 반복 문항으로 인식 | 접속은 하나 입력/완료 전 종료 | 전일 입력을 불러와 ‘추가/수정’하는 누적 과제로 전환 |
| Day 7~8 | 첫 주 경계에서 성과가 보이지 않음 | Day 7 완료 후 Day 8 시작 감소 | 7일 요약 자산 1개 자동 생성 + 2주차 선택권 제공 |
| Day 10~14 | 과제 비용 누적, 결손일이 복귀 장벽으로 변함 | 연속 미완료 후 복귀율 저하 | 연속일 대신 누적 완료를 표시하고 2분 축소 과제 제공 |
| Day 20→21 | 완료 기대효용 또는 이후 경로 불명 | Day 20 완료 후 최종 미완료 | Day 21 산출물 미리보기와 내보내기/다음 21일 경로 노출 |

위 구간은 달력상 실제 요일이 아니다. 가입일에 따라 주말 위치가 달라지므로 “Day 7=주말”로 해석하면 안 된다.

### 3.2 데이터가 있어야만 판정할 가설

다음은 로그 없이는 결론을 내릴 수 없다.

1. **실제 최대 이탈일:** Day별 `eligible → view → start → save → next-day return` 퍼널이 필요하다.
2. **주말 효과:** 사용자 현지시간·가입 요일이 필요하다. Day 번호만으로 분리할 수 없다.
3. **과제 난이도 효과:** 카드별 예상 시간, 글자 수, 체류시간, 저장 성공 여부가 필요하다.
4. **알림 효과:** 알림 배정/발송/도달/클릭 로그와 무작위 배정 또는 교란 통제가 필요하다. 단순 클릭 사용자 비교로 인과효과를 주장하지 않는다.
5. **리포트 유형별 차이:** 리포트 버전·추천 유형·유입 채널·기기별 코호트가 필요하다.
6. **결손 후 복구 효과:** `skip`, `resume`, 축소 과제 노출과 이후 완료 이벤트가 필요하다.

최소 이벤트 스키마:

```text
user_pseudo_id, report_version, action_id, day_index,
event_name(view|start|save|skip|resume|asset_open|asset_export),
event_ts_utc, user_tz, session_id, assignment_variant,
input_length_bucket, save_status, asset_id
```

권장 지표(운영정의):

- `start_rate[d] = unique(start,d) / unique(eligible,d)`
- `completion_rate[d] = unique(save_success,d) / unique(start,d)`
- `survival[d] = unique(users with any save on or after d) / Day1 starters`
- `recovery_rate[k] = users resuming within 48h after k missed days / users with k missed days`
- 개인정보 최소화를 위해 원문 입력 대신 길이 구간을 분석 로그에 두고, 자산 본문 저장소와 행동분석 로그를 분리한다(제안).

## 4. 리포트 → 체크인 → 자산 축적 연결 단절 3개와 대안

### 단절 1: 리포트의 해석이 첫 체크인 입력으로 변환되지 않음

- **관찰 조건:** 리포트 CTA 뒤 빈 체크인 폼이 열리거나, 추천 내용을 사용자가 다시 입력해야 한다.
- **대안:** 리포트의 근거 문장 1개와 선택한 행동 1개를 Day 1 초안으로 넘긴다. 사용자가 `수정 후 시작`해야 확정되게 하며 자동 확정을 금지한다.
- **검증 이벤트:** `report_action_selected → checkin_prefilled → checkin_saved`.

### 단절 2: 체크인 완료가 일회성 상태값으로 끝남

- **관찰 조건:** 완료 여부만 저장되고 입력이 재사용 가능한 개별 자산으로 생성되지 않는다.
- **대안:** 저장 때 `asset_id`, 제목, 생성일, 출처 체크인, 버전을 만들고 “자산에 추가됨” 링크를 제공한다. 7일마다 관련 체크인을 하나의 초안으로 묶되 사용자가 병합을 승인한다.
- **검증 이벤트:** `checkin_saved → asset_created → asset_opened_within_7d`.

### 단절 3: 축적 자산이 다음 행동의 입력으로 돌아오지 않음

- **관찰 조건:** 자산 목록은 있으나 다음 체크인·내보내기·공유에서 불러올 수 없다.
- **대안:** 다음 카드에 `이전 자산 1개 선택 → 한 줄 수정/추가 → 새 버전 저장` 흐름을 넣는다. 자산마다 사용 횟수와 마지막 사용처를 표시한다.
- **검증 이벤트:** `asset_selected_for_checkin → asset_revised → asset_exported/shared`.

세 대안의 공통 게이트: 모든 `save_success`는 하나의 `asset_id` 또는 명시적 `non_asset_reason`을 가져야 한다. 고아 저장(`save_success && !asset_id && !non_asset_reason`)이 1건이라도 E2E fixture에서 발생하면 실패시킨다.

## 5. 구체적 실행 지시와 미증명 타당도의 경계

### 5.1 선을 긋는 원칙

**절차는 구체적으로, 개인에 대한 결론은 조건부로 쓴다.** 시간·횟수·버튼·완료조건을 단정하는 것은 사용 절차의 명료화다. 반면 응답으로 성향·성과·최적 선택을 확정하는 것은 현재의 미증명 범위를 넘는다.

| 허용 | 조건부 허용 | 금지 |
|---|---|---|
| “오늘 10분 동안 사례 1개를 3줄로 기록하세요.” | “현재 응답에서 나온 가설로 A를 1회 시험하고 다음 체크인에서 유지 여부를 정하세요.” | “당신은 A형이므로 반드시 A 직무를 선택하세요.” |
| “저장 버튼을 누르면 자산 초안에 추가됩니다.” | “이 패턴이 맞는지 실제 사례 2개와 비교하세요.” | “이 결과가 최적 진로를 알려줍니다.” |
| “부담되면 2분 버전으로 축소하거나 건너뛸 수 있습니다.” | 고위험 분야는 정보 제공과 전문가 상담 경로까지만 | 건강·법률·재무 결과를 개인 점수만으로 확정 지시 |

### 5.2 제품 문안의 상태 라벨

- 계산 재현성: **증명됨**
- 재검사 신뢰도: **미증명**
- 내용타당도: **진행 중**
- 구성·예측타당도: **미증명**

해석 블록에는 해당 상태를 표시하되, 모든 저위험 UI 명령에 “추정”을 반복할 필요는 없다. 예를 들어 “저장하세요”는 측정결과에 대한 주장이 아니므로 라벨 대상이 아니다.

### 5.3 출시 차단 조건

다음 중 하나면 텍스트 게이트 실패로 처리한다.

1. 미증명 특성·결과를 확정형으로 서술한다.
2. 개인화 추천에 시험·검토·수정·거절 경로가 없다.
3. 추천 근거가 리포트 점수인데 근거 상태 라벨이 없다.
4. 고위험 의사결정을 단일 점수로 지시한다.
5. 실제 기능이 보장하지 않는 저장·알림·자산 생성 결과를 약속한다.

## 6. 구현·검증 우선순위

1. `data-action-*` 입력 계약과 고정 fixture(합격 10, 실패 코드별 3개 이상)를 먼저 만든다.
2. `action_text_gate.mjs`에 R1~R12를 구현하고 실패 코드를 스냅샷 테스트한다.
3. Playwright E2E로 O1·O6~O10·O12와 고아 저장을 검사한다.
4. 실제 배포 전 문안 변경 PR에서 텍스트 게이트와 E2E를 필수 체크로 설정한다.
5. 출시 후 Day별 퍼널을 수집하되, 90점 도달 주장은 동일 외부 평가의 재측정 결과와 분리한다.

## 근거와 적용 범위

아래 문헌은 행동을 상황·시점과 연결하거나, 행동변화 기법을 명시적으로 기술하고, 습관 형성 기간의 개인차가 큼을 보여주는 일반 근거다. 본 제품의 21일 이탈일 또는 외부평가 90점 달성을 직접 검증한 자료는 아니다.

1. Gollwitzer, P. M. (1999). *Implementation Intentions: Strong Effects of Simple Plans*. American Psychologist, 54(7), 493–503. https://doi.org/10.1037/0003-066X.54.7.493
2. Michie, S. et al. (2013). *The Behavior Change Technique Taxonomy (v1) of 93 Hierarchically Clustered Techniques*. Annals of Behavioral Medicine, 46, 81–95. https://doi.org/10.1007/s12160-013-9486-6
3. Lally, P. et al. (2010). *How are habits formed: Modelling habit formation in the real world*. European Journal of Social Psychology, 40(6), 998–1009. https://doi.org/10.1002/ejsp.674
4. Nielsen Norman Group. *Visibility of System Status (Usability Heuristic #1)*. https://www.nngroup.com/articles/visibility-system-status/

문헌에서 본 설계로 직접 가져온 범위는 실행 계획의 구체화, 행동기법의 명시, 진행 상태 피드백의 필요성이다. 12개 관찰항목, 정규식, 합격식, 날짜별 이탈 구간은 제품용 제안 또는 미확인 가설이며 외부 문헌이 보증하는 수치가 아니다.
